# Windows Service-Based Persistence via SCM — SYSTEM-Context Autostart Through the Service Control Manager

## Summary

Windows service-based persistence registers or modifies an entry in the Service Control Manager database so the SCM relaunches the implant at boot under the LocalSystem account. The operator calls the advapi32 service APIs — OpenSCManager, CreateService, and ChangeServiceConfig — to create a new auto-start service or to repoint an existing service's ImagePath/binPath at attacker-controlled code, and optionally arms SERVICE_FAILURE_ACTIONS via ChangeServiceConfig2 so a crash or termination re-executes a configured command. The technique rests on two OS primitives: the SCM's role as the authoritative manager of service lifecycles, and the fact that service objects are securable objects whose DACLs can be rewritten via SDDL to hide the service from sc.exe, PowerShell Get-Service, and similar enumeration tools without a kernel driver or function hooking. The training material frames it as the action to take once administrative or SYSTEM privileges are held, because it survives reboot, runs as SYSTEM, and provides SCM-managed restart semantics that user-context persistence lacks. The primary detection surface is service enumeration and the services registry hive, which the SDDL DACL-hiding step directly targets.

## Mechanism

1. Gate on privilege. The material states that creating a service is the appropriate action once administrative and/or SYSTEM privileges are held; opening the local SCM with the access needed to create services (SC_MANAGER_CREATE_SERVICE or SC_MANAGER_ALL_ACCESS) requires elevation.
2. Open the SCM database with OpenSCManager (lpMachineName NULL for the local machine, lpDatabaseName NULL for SERVICES_ACTIVE_DATABASE), which returns an SC_HANDLE used by every subsequent call.
3. When modifying rather than creating, interrogate existing services first: QueryServiceStatusEx (hService, SC_STATUS_TYPE InfoLevel, lpBuffer, cbBufSize, pcbBytesNeeded) returns runtime state, and QueryServiceConfig (hService, QUERY_SERVICE_CONFIG, cbBufSize, pcbBytesNeeded) returns the persisted configuration of a chosen target.
4. Create the service with CreateService. The material specifies the parameter contract: lpBinaryPathName must be the full path to the executable, and command-line arguments may be appended after the executable name in the same string; lpLoadOrderGroup is optional (NULL); lpdwTagId applies only to kernel drivers; lpDependencies is an optional list of services this service depends on; lpServiceStartName selects the run-as account (NULL yields LocalSystem) with lpPassword for that account. dwStartType of SERVICE_AUTO_START produces the boot-time persistence; dwServiceType for a user-mode implant is a Win32 service type rather than SERVICE_KERNEL_DRIVER.
5. Build the service binary to the SCM contract. main() constructs a SERVICE_TABLE_ENTRY array — rows of {ServiceName, ServiceMain} terminated by a {NULL, NULL} row — and passes it to StartServiceCtrlDispatcher. The material notes the table supports multiple services sharing one process address space. ServiceMain (the material's example is `VOID WINAPI EvilMain(...)`) must register a control handler and report status; the SCM terminates services that do not answer to it.
6. Alternatively, hijack an existing service with ChangeServiceConfig. The material names three modification points: ImagePath (the registry key holding the absolute path to the service binary on disk), binPath (typically matches ImagePath; the value and its arguments are passed to the executable), and FailureCommand (what happens when the service does not start or is terminated). All three are reachable through sc.exe as well as the API.
7. Arm the failure trigger by populating a SERVICE_FAILURE_ACTIONS structure — dwResetPeriod, lpRebootMsg, lpCommand, cActions, lpsaActions — and applying it with ChangeServiceConfig2(hService, SERVICE_CONFIG_FAILURE_ACTIONS, &sfa). The material's pseudo-code zeroes the struct with SecureZeroMemory, sets dwResetPeriod = INFINITE, lpRebootMsg = "", lpCommand to a re-execution command (the example given is "ping C2"), cActions = 0, lpsaActions = NULL.
8. The trigger condition is defined by the SCM: a service is considered failed when it terminates without reporting SERVICE_STOPPED to the SCM, or when the Win32ExitCode member of its SERVICE_STATUS structure is not ERROR_SUCCESS. At that point the configured failure actions fire, giving the implant a re-execution path on crash or defensive kill.
9. Hide the service by rewriting the service object's DACL. Manually this is sc.exe sdset \<name\> \<SDDL\>; programmatically it is SetNamedSecurityInfo (aclapi.h), with SetSecurityDescriptorControl (securitybaseapi.h) for descriptor control flags. The material provides a real engagement string from SANS instructor Joshua Wright: `D:(D;;DCLCWPDTSD;;;IU)(D;;DCLCWPDTSD;;;SU)(D;;DCLCWPDTSD;;;BA)(A;;CCLCSWLOCRRC;;;IU)(A;;CCLCSWLOCRRC;;;SU)(A;;CCLCSWRPWPDTLOCRRC;;;SY)(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;BA)S:(AU;FA;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;WD)`.
10. Clean up before removal: restore the descriptor with sc.exe sdset using a restore SDDL (the material's SWCUEngine example grants full control to SY and BA and limited rights to IU and SU), then DeleteService, then CloseServiceHandle on both the service handle and the SCM handle.

## OS Internals Context

The SCM (services.exe) is the user-mode authority for service lifecycles. The advapi32 stubs — OpenSCManager, CreateService, ChangeServiceConfig, ChangeServiceConfig2, QueryServiceStatusEx, QueryServiceConfig — marshal over RPC into services.exe, which maintains the persistent service database in the registry under HKLM\SYSTEM\CurrentControlSet\Services\\<ServiceName\>. The ImagePath value in that key is what the SCM reads to locate the binary, which is why the material treats ImagePath/binPath modification of an existing service as equivalent in effect to creating a new one. Because the SCM starts the binary and then waits for the process to connect back via StartServiceCtrlDispatcher, a service binary is structurally different from a scheduled-task action or a COM hijack payload: it must speak the dispatcher protocol and continually report SERVICE_STATUS, or the SCM kills it.

Service objects are securable kernel objects. Every SCM operation performs an access check against the service's security descriptor, and the descriptor itself is viewable with sc.exe sdshow. SDDL is the string format consumed by ConvertStringSecurityDescriptorToSecurityDescriptor and produced by ConvertSecurityDescriptorToStringSecurityDescriptor; the header declares Owner (O:), Group (G:), DACL (D:), and SACL (S:), and each ACE follows the layout (ace_type;ace_flags;rights;object_guid;inherit_guid;account_sid). The material enumerates ace types A (access allowed), D (access denied), OA, OD, AU (audit), AL; inheritance flags CI, OI, NP, IO, ID, SA; generic rights GA/GR/GW/GX; and standard rights RC (read control), SD (delete), WD (write DACL), WO (write owner). The service-specific right letters in the Wright string map to documented service access rights: CC is SERVICE_QUERY_CONFIG, DC is SERVICE_CHANGE_CONFIG, LC is SERVICE_QUERY_STATUS, SW is SERVICE_ENUMERATE_DEPENDENTS, RP is SERVICE_START, WP is SERVICE_STOP, DT is SERVICE_PAUSE_CONTINUE, LO is SERVICE_INTERROGATE, CR is SERVICE_USER_DEFINED_CONTROL.

The hiding effect comes from canonical ACL ordering: deny ACEs precede allow ACEs, so the deny wins for overlapping rights. In the Wright string, the three leading deny ACEs strip DC, LC, WP, DT, and SD — change-config, query-status, stop, pause/continue, and delete — from IU (Interactive User), SU (Service logon accounts), and BA (Built-in Administrators). Because query-status is denied, enumeration-driven tools fail against the object and the service disappears from sc.exe and the other tools the material names, even for administrators. The allow ACE for SY (LocalSystem) grants the full right set, so the SCM itself continues to start, stop, and manage the service normally; persistence keeps working while visibility is gone. The trailing SACL — (AU;FA;...;;;WD) — audits failed access attempts by Everyone. The material emphasizes that this concealment requires no kernel driver and no function hooking; it is purely an access-control effect on the SCM's own checks. The same deny-first construction is reusable against any service the operator installs, which is why the DACL primitive is the durable tradecraft in this cluster.

The failure-action channel is a second SCM-internal behavior with offensive value. A service that exits without reporting SERVICE_STOPPED, or whose SERVICE_STATUS.Win32ExitCode is not ERROR_SUCCESS, is declared failed by the SCM; the SERVICE_FAILURE_ACTIONS configuration then determines the response. lpCommand supplies an arbitrary command line, giving a re-execution trigger that fires on crash, on a defender killing the process, or on a failed start — a redundancy mechanism distinct from the start-type itself.

On process model: SERVICE_WIN32_OWN_PROCESS gives the implant its own process; SERVICE_WIN32_SHARE_PROCESS hosts the service DLL inside a shared svchost, and the multi-row SERVICE_TABLE_ENTRY exists for the shared case. Kernel driver services (SERVICE_KERNEL_DRIVER) bypass the dispatcher contract entirely and load through the I/O manager; the material notes lpdwTagId is meaningful only for that driver class.

## Key Implementation Details

**No current implementation in the HUGIN source.** This card documents the technique for future implementation. See the atlas material for reference implementations in C (SEC670 service module: SERVICE_TABLE_ENTRY, StartServiceCtrlDispatcher, ChangeServiceConfig2 pseudo-code) and sc.exe command-line.

The nearest existing code is `dark_crystal/crowd/src/byovd.rs`, which exercises the same SCM API family for a different purpose: it opens the SCM with OpenSCManagerW(SC_MANAGER_ALL_ACCESS), registers a vulnerable driver as SERVICE_KERNEL_DRIVER | SERVICE_DEMAND_START via CreateServiceW, starts it with StartServiceW, and then unwinds with ControlService(SERVICE_CONTROL_STOP), DeleteService, and a three-pass file shred. That pipeline is explicitly transient — its comments state "no persistence in boot sequence" — so it does not implement this technique. `client_rust/src/browser_hook.rs` persistence layers use schtasks, Run keys, and shortcut patching, not SCM services. An implementation would be a `persist/service.rs` module beside T-017's layers: winapi winsvc bindings for OpenSCManagerW/CreateServiceW with SERVICE_AUTO_START, ChangeServiceConfig2W with a SERVICE_FAILURE_ACTIONS struct whose lpCommand repoints at the implant, ConvertStringSecurityDescriptorToSecurityDescriptorW plus SetNamedSecurityInfoW to apply the hiding DACL, and registration inside `install_all` with the resilience monitor re-installing the service if the registry key or descriptor is reverted.

## Why It Matters

T-017's five layers execute in user context or on user-triggered events; none provides an SCM-managed, boot-time layer running as LocalSystem. Service persistence fills the elevated-context gap: default SYSTEM execution, auto-start across reboots, SCM-enforced restart semantics, and a failure-command channel that re-executes on crash or defensive termination. The SDDL DACL-hiding primitive is reusable against any operator-installed service and requires no kernel driver or hooking, which separates it from the concealment approaches documented elsewhere in the vault. SEC670 dedicates a full module to this layer — Services Revisited, Lab 4.1 PersistentService, and Lab 4.4 NotInService — which the vault previously did not surface.

## Detection Considerations

- **Telemetry sources**: The training material frames the detection surface as enumeration: sc.exe query, PowerShell Get-Service, services.msc, and direct descriptor review via sc.exe sdshow (the material demonstrates sdshow against BITS). It does not discuss ETW providers, Sysmon, or kernel-callback telemetry for this technique. Independently of the material, Microsoft documentation records new service installation in the System event log as Event ID 7045 from the Service Control Manager.
- **Bypass options**: The material's primary evasion is the SDDL DACL hide — deny ACEs against IU, SU, and BA remove query, stop, delete, and change-config rights while SY retains full control, removing the service from standard enumeration without a driver or hooks. The material also observes that most users do not pay attention to new or modified services, which is the stated rationale for modifying an existing service's ImagePath/binPath rather than creating a new one.
- **Residual artifacts**: The services registry key (ImagePath value and the FailureCommand configuration), the binary on disk referenced by lpBinaryPathName, and the modified security descriptor itself. The descriptor remains visible to direct sc.exe sdshow inspection by any principal retaining read control, and anomalous deny ACEs on a service are themselves an indicator; the material's cleanup pattern restores the original descriptor via sc.exe sdset before deleting the service for this reason.
