# WDAC Dynamic Code Trust Query via WldpQueryDynamicCodeTrust — Pre-flight CIG enforcement probe before committing executable allocations

## Summary

`WldpQueryDynamicCodeTrust` is the user-mode Windows Lockdown Policy (WLDP) API exported by `wldp.dll` that an implant calls to query whether a candidate executable memory region `(base, size)` would survive Code Integrity Guard (CIG) / Windows Defender Application Control (WDAC) enforcement *before* committing the allocation or stomping a module. The function consults the in-memory Code Integrity policy — the binary `.cip` files parsed at boot by `ci.dll` from `C:\Windows\System32\CodeIntegrity\CiPolicies\Active\` via `CiInitializeSigned` — and returns a trust verdict without performing the allocation itself. When CIG is enabled on the target process — set via `SetProcessMitigationPolicy(ProcessSignaturePolicy = 7, ...)` or inherited at process creation via `PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY` with the `PROCESS_CREATION_MITIGATION_POLICY_SIGNATURE_CIG = 0x40000000` flag, reflected into `_EPROCESS.MitigationFlags` and the per-process signature policy subrecord — every executable allocation, image-section map, and protection flip to executable is gated by the memory manager consulting `MmCiValidateImage` / `CiValidateImageOptions` against the kernel CI callbacks chain registered at boot through `CiInitialize`. A naïve allocation attempt on a CIG-enforced process fails with `STATUS_INVALID_IMAGE_HASH (0xC0000428)` and emits an event through the `Microsoft-Windows-CodeIntegrity` ETW provider (image validation failure events in the 30xx range); under strict policy with audit-mode disabled, the protection flip is silently rejected and the operator gains nothing but a SOC signal. `WldpQueryDynamicCodeTrust` lets the implant gate before the kernel-ETW event fires: query verdict → if trusted, proceed with module stomping / shellcode-to-PIC transition; if untrusted, fall back to a CIG-agnostic delivery vector (signed carrier DLL stomping, non-CIG sibling process, in-process RWX-on-trusted-section path). The API is distinct from `WldpIsClassApproved` (COM class trust enumeration, consults a different rule set keyed on CLSID) and from `WldpQueryLicenseSecurityPolicy` (policy enumeration at the document level). The query operates against a `(PVOID base, SIZE_T size)` tuple and returns an `HRESULT` where `S_OK` means trusted, `S_FALSE` means explicitly untrusted but the call succeeded, and any failure `HRESULT` indicates a query-path error (missing `ci.dll`, malformed address range). Memory-only regions (anonymous `VirtualAlloc` allocations backed only by the pagefile) are *never* trusted under default WDAC policy — the policy rule set is file-identity-keyed, so the API's operational value is realized only against file-backed sections. The vault's T-016 card documents the broader CIG mitigation surface and the canonical module-stomping bypass, but does not cover the pre-flight query API that makes those bypasses operationally safe on hardened estates.

## Mechanism

### Variant 1: Pre-flight Trust Query (read-only verdict)

1. Resolve `wldp.dll`. The module is typically already mapped in any process that touched COM; if absent, `LoadLibraryW(L"wldp.dll")`. Resolve `WldpQueryDynamicCodeTrust` via `GetProcAddress(hModule, "WldpQueryDynamicCodeTrust")`. Export is forwarded through the `api-ms-win-security-wldp-l1-1-0` API set schema; direct `GetProcAddress` on `wldp.dll` works because `wldp.dll` is the host for that API set.
2. Confirm CIG is actually enabled on the *calling* process (or, for cross-process operations, on the target) before paying the WLDP round-trip cost. Use `NtQueryInformationProcess(ProcessMitigationPolicy = 0x34, &buffer, sizeof(PROCESS_MITIGATION_INFORMATION), NULL)`. Inspect `SignaturePolicy.SignatureRequirementsUpgraded` and `SignaturePolicy.MicrosoftSignedOnly` bitfields. If both are clear, CIG is not active — the query will always return `S_OK` for any file-backed section that has a valid PE signature under the user-mode CI signer chain, and pure RWX allocation is not gated.
3. Distinguish CIG from `ProhibitDynamicCode`. Query `NtQueryInformationProcess(ProcessDynamicCodePolicy = 0x32, &buffer, ...)` separately. If `ProhibitDynamicCode` bit is set, *no* dynamic code path exists for unsigned code — the target blocks all executable allocations including signed ones. `WldpQueryDynamicCodeTrust` will still return a verdict, but no `WldpSetDynamicCodeTrust` (or equivalent trust-grant path) can rescue the operation. Bail to a non-`ProhibitDynamicCode` sibling process.
4. Compute the candidate region `(base, size)`. For module stomping, this is the `.text` section of the target module — parse `IMAGE_DOS_HEADER.e_lfanew` at offset `0x3C` to locate `IMAGE_NT_HEADERS64`, walk `OptionalHeader.DataDirectory`, then iterate `IMAGE_SECTION_HEADER` entries (immediately after the optional header at offset `e_lfanew + sizeof(DWORD) + sizeof(IMAGE_FILE_HEADER) + OptionalHeader.SizeOfHeaders`-derived bound). Locate the section with `Characteristics & IMAGE_SCN_MEM_EXECUTE = 0x20000000`. The (base, size) tuple is `(module_base + section.VirtualAddress, section.Misc.VirtualSize)` rounded up to page granularity.
5. Call `WldpQueryDynamicCodeTrust(base, size, &verdict, &trustProviderSid)`. The function marshals into `ci.dll` (user-mode copy loaded by `kernelbase.dll`) which transitions to the kernel via `NtQuerySystemInformation(SystemCodeIntegrityInformation, ...)` or an IOCTL to `\Device\CodeIntegrity` (the kernel device exposed by `ci.dll`'s `CioDeviceControl` dispatch table).
6. The kernel CI module walks the parsed `SiPolicy` tree in kernel memory: `PolicyInfo` → rule lists — `CDFileRule` (file-hash allow/deny), `CDSignerRule` (signer-cert allow/deny), `CDWindowsHelloRule` (biometric-gated signers). For a file-backed region, the `_SECTION`'s `_CONTROL_AREA->FilePointer` is dereferenced to obtain the `_FILE_OBJECT`, and the file's Authenticode certificate chain / PE image hash is matched against allow rules. For a memory-only region with no file backing, the verdict is `S_FALSE` untrusted under any default policy — there is no rule path that blesses anonymous RWX heap.
7. Branch on the verdict:
   - **`S_OK` (trusted)**: proceed with `VirtualProtectEx(hTarget, base, size, PAGE_EXECUTE_READWRITE = 0x40, &oldProtect)` or `NtProtectVirtualMemory`. The CI callbacks will pass the executable transition without firing `Microsoft-Windows-CodeIntegrity` validation failure events.
   - **`S_FALSE` (untrusted)**: defer the allocation. Pick a fallback: (a) target a sibling process without CIG (e.g., a non-protected `svchost.exe` instance, `RuntimeBroker.exe`); (b) deliver via stomping a different Microsoft-signed DLL whose signer chain matches an allow rule in the policy (try the query against the alternate carrier before stomping); (c) drop the payload as a file-backed section backed by a Microsoft-signed carrier DLL on disk, then re-query.
   - **Failure `HRESULT`**: do not proceed. Inspect `GetLastError()`; common causes: `ERROR_MOD_NOT_FOUND (126)` if `ci.dll` is missing, `STATUS_ACCESS_DENIED`-derived codes if the kernel CodeIntegrity device cannot be opened.

### Variant 2: Post-allocation Verify-then-Execute

1. Allocate the candidate region with `NtAllocateVirtualMemory(..., PAGE_READWRITE = 0x04)` — *not* executable. RW allocations are not CI-gated because no execution is requested at allocation time.
2. Write the payload bytes via `NtWriteVirtualMemory` or in-process `memcpy`.
3. *Before* flipping protection to executable, call `WldpQueryDynamicCodeTrust(base, size, ...)` to query the verdict for the now-populated region. This is operationally useful when the candidate region is a file-backed section created via `NtCreateSection(SEC_IMAGE = 0x01000000, ...)` + `NtMapViewOfSection` — the backing file's signer chain can be evaluated against the policy before the executable protection flip is attempted.
4. If trusted: `VirtualProtect(base, size, PAGE_EXECUTE_READWRITE, &old)` — the protection flip proceeds without CI failure.
5. If untrusted: leave the region RW, free it (`NtFreeVirtualMemory`), pick the fallback. No ETW CI failure event fires because no executable protection was ever requested.
6. The advantage over Variant 1 is that the file backing can be inspected after content is written — for a payload DLL constructed on disk first and then mapped as a section, the post-write query reflects the actual image's signature rather than a hypothetical one. The disadvantage is the cost of an unused allocation if the verdict is negative.

## OS Internals Context

The WLDP API set (`wldp.dll`) is the user-mode façade over the kernel Code Integrity subsystem. At boot, `ntoskrnl.exe` invokes `CiInitialize` (exported by `ci.dll`, loaded as a boot-start kernel module), which registers a callback chain used by the memory manager, the loader, and the object manager to consult Code Integrity policy at every code-introduction boundary. The callbacks populate `nt!MmCodeIntegrityCallbacks` — a structure of function pointers including `CiValidateImageHeader`, `CiValidateImageOptions`, `CiQueryInformation`, `CiInitializeSignedPolicy`, etc. These are called by `MiMapViewOfImageSection` during section creation, by `MiInitializeImageFailure` during failed image loads, by the `MmProtectSection` / `NtProtectVirtualMemory` path when protection flips to executable on a section that did not previously permit execution, and by `LdrpMapDllNtFileName` during dynamic DLL loads.

The policy itself lives in `C:\Windows\System32\CodeIntegrity\CiPolicies\Active\` as compiled binary `.cip` files. Each file begins with the `0x49435030` ("CIP0") magic header followed by a series of policy elements; each element carries a 16-bit `wMajorVersion` / `wMinorVersion` and serialized rule data (`CDFileRule` for hash allow/deny, `CDSignerRule` for signer-based rules with `EKUs[]` and `RequiredElements` sublists, `CDWindowsHelloRule` for biometric-gated signers). The base policy file is `{00000000-0000-0000-0000-000000000000}.cip`; supplemental policies are appended with their own GUID filenames. At boot, `CiInitializeSigned` parses these files, verifies the policy signature against the policy-signing certificate chain (rooted in `HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy` and `CI_ROOT`), and constructs the in-memory `SiPolicy` structure that the CI callbacks walk on every query. The `WldpQueryDynamicCodeTrust` API call eventually reaches `CiQueryInformation` with a `CodeIntegrityQueryInformation` info class selecting `DynamicCodeTrust` — the kernel function traverses the `SiPolicy.RuleOptions`, the `SiPolicy.FileRules` list, and the `SiPolicy.Signers` list comparing the candidate region's backing `_FILE_OBJECT->FileName` and any Authenticode signing certificate chain against the policy's allow/deny rules.

The CIG mitigation on the target process is enforced through `_EPROCESS.MitigationFlags` (a `_EPROCESS` bitfield) and a separate per-process signature-policy subrecord. The mitigation is set via `NtSetInformationProcess(ProcessMitigationPolicy = 0x34, &PROCESS_MITIGATION_SIGNATURE_POLICY_IMAGE, sizeof(...))` and reflected into the `EPROCESS` via `PspComputeMitigationPolicy` updating `MitigationFlagsValues.SignaturePolicy` (bits in the `SignaturePolicy` field) and the dedicated `SignaturePolicyEnableFlags`. Once set, the mitigation persists for the lifetime of the process; it cannot be turned off. Critically, CIG is most-often settable at process creation via the attribute list passed to `CreateProcess` — `STARTUPINFOEX.lpAttributeList` with `PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY` (attribute number `0x00020000`) carrying the `PROCESS_CREATION_MITIGATION_POLICY_SIGNATURE_CIG = 0x40000000` bitfield flag. A process cannot retroactively add CIG to itself; CIG-enforced targets are either self-imposed by the binary at its own startup (Edge, Microsoft 365 apps call `SetProcessMitigationPolicy` early in main) or imposed by a CIG-enforcing parent. This is why operational probing matters — the operator does not get to choose whether the target has CIG; the target's binary chose it.

Memory-only regions (anonymous `NtAllocateVirtualMemory` allocations backed only by the pagefile) are *never* trusted under default WDAC policy. The CI policy rule set is file-identity-keyed — `CDFileRule` matches against PE image hashes computed at `CiComputeImageHash` time (SHA-256 / SHA-1 / SHA-384 depending on the rule's `HashAlgorithm` field), `CDSignerRule` matches against PE signer certificate chain (the `WTD_CERTCHAIN` returned by `WinVerifyTrust`). There is no rule class that blesses an anonymous RWX heap region. This is the central tension: pure shellcode-on-the-heap cannot be blessed via `WldpQueryDynamicCodeTrust`; the implant must use a file-backed section. The canonical CIG-bypass pattern is to (a) map a Microsoft-signed DLL as a section into the target process (`NtMapViewOfSection` from a section created against a Microsoft-signed carrier DLL), (b) `WldpQueryDynamicCodeTrust` the carrier's `.text` to confirm the file's signer chain will pass policy, (c) `VirtualProtectEx` the section's `.text` from `PAGE_EXECUTE_READ` to `PAGE_READWRITE` (this requires `PROCESS_VM_OPERATION = 0x0020` on the target handle), (d) overwrite `.text` bytes with the shellcode via `WriteProcessMemory`, (e) flip back to `PAGE_EXECUTE_READ` or `PAGE_EXECUTE_READWRITE`, (f) `RtlCreateUserThread` / `NtCreateThreadEx` into the stomped `.text`. The CIG mitigation accepts the section because the underlying file's signer chain matches the WDAC policy allow rule; the in-memory bytes have been replaced but the CI subsystem does not re-validate content at execution time — the trust was established at section-map time against the file's signing identity.

The kernel device `\Device\CodeIntegrity` is exposed via `CiInitializeDevice` at kernel init and reachable from user mode through `\\.\CodeIntegrity` or via the `NtQuerySystemInformation` system call path with `SystemCodeIntegrityInformation`. The device IOCTL interface accepts query operations carrying a `CI_QUERY_INFORMATION_INPUT` header that selects the info class (the `DynamicCodeTrust` info class for this technique) and a `CI_DYNAMIC_CODE_TRUST_INPUT` payload containing the `(base, size)` tuple. The kernel-side handler `CidpQueryDynamicCodeTrust` walks the per-process `_EPROCESS` for the calling process, resolves the `_CONTROL_AREA` for any file-backed section overlapping the requested range via the VAD tree (`_EPROCESS.VadRoot`, `_MMVAD_SHORT.StartingVpn` / `EndingVpn`), and consults the policy tree. Anonymous VADs (subtree with no `_CONTROL_AREA->FilePointer`) yield immediate `S_FALSE`; mapped-image VADs trigger the full policy walk.

The user-mode `ci.dll` (loaded into user-mode processes by `kernelbase.dll` for CI queries — distinct from the kernel `ci.dll` image even though they share a name and binary lineage) is a hard dependency for `WldpQueryDynamicCodeTrust`. If the user-mode `ci.dll` is missing (extremely rare on a healthy system) or the API set forwarder `api-ms-win-security-wldp-l1-1-0` is unresolvable, the call returns a failure HRESULT derived from `ERROR_MOD_NOT_FOUND`. The function does not gracefully degrade — there is no fallback to a heuristic verdict. On WOW64, the 32-bit `wldp.dll` forwarder marshals via the WOW64 transition layer to the 64-bit kernel; pointer truncation bugs in the bridge mean callers should always pass page-aligned 64-bit-clean `base` values. Pre-Query-period side effects are essentially nil — no page protection changes, no allocation, no handle table growth (the WLDP API internally reuses a per-thread CI query context).

## Key Implementation Details

Privilege prerequisites for *querying* trust are minimal: the calling process needs no special privileges to call `WldpQueryDynamicCodeTrust` against a region it can already read. The function operates on a `PVOID base` and `SIZE_T size`; the base must be page-aligned (`base & 0xFFF == 0`) or the kernel query path silently truncates `base` downward to the enclosing page boundary. Sizes smaller than one page (`0x1000` bytes on x64) still consume one query but only the page containing `base` is checked — operators querying multi-page regions must round `size` up to the next page boundary or the trailing pages go unverified. For file-backed sections, the verdict reflects the policy evaluation of the *file* (the backing `_FILE_OBJECT` and its Authenticode signing chain), not the in-memory content — so stomping a Microsoft-signed DLL's `.text` *after* mapping yields a "trusted" verdict because the CI policy has not been re-queried against the modified bytes.

The CIG mitigation's `PAGE_READONLY` enforcement on signed sections complicates the stomp path: when an image section is mapped as `PAGE_EXECUTE_READ`, the underlying `_MMPTE` entries carry the `CopyOnWrite` bit only if the section was mapped with `PAGE_WRITECOPY` semantics; standard `PAGE_EXECUTE_READ` mapping produces read-only PTEs that trap on write with `STATUS_ACCESS_VIOLATION`. The attacker must `VirtualProtectEx(hTarget, base, size, PAGE_READWRITE, &old)` first — and this is exactly the protection flip that CIG gates. The flip *succeeds* only if the section's `_CONTROL_AREA`-backed file passes CI; otherwise the kernel rejects the protection change with `STATUS_INVALID_IMAGE_HASH`. This is the operational crux of `WldpQueryDynamicCodeTrust` — call it before the protection flip to learn whether the flip will succeed, so the operator does not leave a noisy failure on the wire.

GOTCHA: `WldpQueryDynamicCodeTrust` against a region with no file backing (anonymous `VirtualAlloc` memory) returns `S_FALSE` with `*trustProviderSid == NULL` — explicitly untrusted, not an error. Operators who treat `S_FALSE` as "function failed, try anyway" trigger the CIG failure event they were trying to avoid. Always branch on the explicit `S_OK` (trusted) vs `S_FALSE` (untrusted) vs failure `HRESULT` (call failed — check `ci.dll` load state and `wldp.dll` resolution).

GOTCHA: the canonical `WldpQueryDynamicCodeTrust` export queries the *calling* process's policy context — it does not accept a target process handle parameter on the public export signature. Cross-process verdict queries require either (a) injecting a small stub into the target process that calls `WldpQueryDynamicCodeTrust` locally on behalf of the operator (the typical pattern — a bootstrapper shellcode that resolves the API, queries the verdict, and returns it via a shared section), or (b) calling the underlying `NtQuerySystemInformation(SystemCodeIntegrityInformation, ...)` path with a constructed input buffer referencing the target PID — this path is not exposed via the public WLDP export surface and requires reverse-engineering the `wldp.dll` dispatch internals to find the input buffer layout.

GOTCHA: the EDR-hookable boundary on this technique is the `GetProcAddress(hWldp, "WldpQueryDynamicCodeTrust")` call and the `wldp.dll` module load via `LdrLoadDll`. Once the function pointer is resolved, subsequent calls go through the resolved pointer without traversing the loader or the export table — so the EDR's first-line hook is the export resolution, not the API invocation. Operators who delay-load `wldp.dll` via `LdrLoadDll` trigger the `Microsoft-Windows-Kernel-Process` (event ID 1) module load event and a potential EDR hook callback (`PsSetCreateProcessNotifyRoutine` does not cover this, but the user-mode `LdrpDllNotificationList` callbacks registered by EDR DLLs do).

## Why It Matters

CIG-enabled processes are increasingly the default for high-value targets: Microsoft Edge, Microsoft 365 apps, Microsoft Teams, and a growing list of LOB applications enable CIG at creation via `PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY = PROCESS_CREATION_MITIGATION_POLICY_SIGNATURE_CIG`. Operating against these targets with naïve injection primitives (`VirtualAllocEx` + `WriteProcessMemory` + `CreateRemoteThread`) now commonly fails on hardened estates, and the failure is loud — the `Microsoft-Windows-CodeIntegrity` provider emits events that EDRs forward to the SOC as high-severity CodeIntegrity policy violations. `WldpQueryDynamicCodeTrust` is the surgical primitive that closes the gap: query verdict, branch on trust, fall back gracefully. It is the difference between an implant that gets terminated by CIG on day one of the engagement and one that survives the hardened estate by delivering payloads only where they will execute.

The card composes naturally with module-stomping primitives — the canonical CIG bypass is to stomp a Microsoft-signed DLL's `.text` because the file's signer chain passes CI even though the in-memory bytes have been replaced — and with discovery techniques for enumerating which estate processes have CIG enabled. It also pairs with `NtQueryInformationProcess(ProcessMitigationPolicy = 0x34)` for the pre-flight CIG detection step and with the signed-section creation primitive (`NtCreateSection(SEC_IMAGE)` + `NtMapViewOfSection` against a Microsoft-signed carrier DLL). The vault's T-016 documents the CIG mitigation surface and bypass primitives; this card fills the pre-flight query gap that makes T-016-class bypasses operationally safe — without the query, the operator is guessing whether the carrier will pass policy, and a guess that fails is a SOC signal.

## Detection Considerations

- **Telemetry sources**: The `Microsoft-Windows-CodeIntegrity` ETW provider emits events for image validation *failures* (event IDs in the 30xx range — 3033, 3034, 3076, 3077 are the canonical CIG failure signatures). These fire only if the implant proceeds with an allocation or protection flip that fails CIG — exactly the failure path that `WldpQueryDynamicCodeTrust` is designed to avoid. The `Microsoft-Windows-CodeIntelligence` ETW provider emits audit events for trust-*grant* operations but is silent on pure query operations under default configuration; verbose query logging can be enabled via the WDAC policy XML `<Rules>` `AuditMode` flag, but most estates do not enable it. The strongest signal is at the user-mode loader / export resolution layer: `LdrLoadDll` of `wldp.dll` in a process that has not previously loaded it (recorded in the `Microsoft-Windows-Kernel-Process` event ID 1 module load event and observable via `LdrpDllNotificationList` callbacks registered by EDR DLLs), followed by `GetProcAddress` resolution of `WldpQueryDynamicCodeTrust` (hookable at the `GetProcAddress` boundary).
- **Bypass options**: Resolve `WldpQueryDynamicCodeTrust` without traversing `GetProcAddress` — by manually parsing `wldp.dll`'s export table via raw PE walk (`IMAGE_EXPORT_DIRECTORY` located at `OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT = 0].VirtualAddress`), indexing into `AddressOfNames` / `AddressOfNameOrdinals` / `AddressOfFunctions` arrays directly. Or bypass `wldp.dll` entirely and call the underlying kernel IOCTL to `\Device\CodeIntegrity` via `NtDeviceIoControlFile` (or the equivalent `NtFsControlFile`-style dispatch) — `IOCTL_CODEINTEGRITY_QUERY_INFORMATION` with `CiQueryInformationType = DynamicCodeTrust`. Or read the parsed policy from kernel memory directly via a kernel primitive (requires ring-0 access; out of scope for user-mode-only operators). To avoid `wldp.dll` load being recorded, ensure the module is already loaded — many Windows processes that touch COM already have `wldp.dll` mapped as a side effect of COM class activation, so a pre-flight `GetModuleHandleW(L"wldp.dll")` check before `LoadLibraryW` avoids the fresh-load event.
- **Residual artifacts**: The query itself leaves no on-disk artifacts — no `.cip` policy changes, no registry writes, no files written. In-memory residue: a `wldp.dll` module load entry recorded in the calling process's `PEB.Ldr.InLoadOrderModuleList` / `InMemoryOrderModuleList` / `InInitializationOrderModuleList` (if `wldp.dll` was not already loaded — observable by EDR via the `LdrpDllNotificationList` chain). If the `\Device\CodeIntegrity` IOCTL path is used directly, a handle to `\Device\CodeIntegrity` is recorded in the `System` process's handle table (`PspCidTable`) and is observable via `NtQuerySystemInformation(SystemHandleInformation)` enumeration — EDRs that enumerate per-process handles will see the CodeIntegrity device handle in the implant process, which is unusual for normal application traffic and a strong IOC.

## Composition with Other Techniques

Realistic kill chain on a hardened estate where Microsoft Edge is CIG-enforced and the operator wants to deliver shellcode into Edge's process:

1. **Discovery**: enumerate running processes via `NtQuerySystemInformation(SystemProcessInformation = 0x05)`. For each candidate, open with `PROCESS_QUERY_LIMITED_INFORMATION = 0x1000` and call `NtQueryInformationProcess(ProcessMitigationPolicy = 0x34)` to identify CIG-enforced targets. Distinguish CIG from `ProhibitDynamicCode` via `ProcessDynamicCodePolicy = 0x32`.
2. **Carrier selection**: pick a Microsoft-signed carrier DLL that the operator will force-load into the Edge process via section mapping. Common carriers: `C:\Windows\System32\notepad.exe` (Microsoft-signed, loads cleanly as a section), `C:\Windows\System32\kernel32.dll` (already loaded, but its `.text` may already be in use; safer to use a not-already-loaded signed DLL). For the chosen carrier, open the file with `CreateFileW(..., FILE_READ_DATA, ...)` and create a section with `NtCreateSection(SEC_IMAGE = 0x01000000, ...)`.
3. **Pre-flight probe**: in the implant process, query the carrier's `.text` via `WldpQueryDynamicCodeTrust(carrier_text_rva + carrier_base_in_implant_view, carrier_text_size, ...)`. If `S_OK`, the carrier's signer chain matches the WDAC policy — proceed. If `S_FALSE`, switch carriers or pivot to a non-CIG sibling process.
4. **Map-and-stomp**: in the target (Edge) process, `NtMapViewOfSection(hSection, hTarget, &baseAddr, ...)` to map the carrier. `VirtualProtectEx(hTarget, baseAddr + text_rva, text_size, PAGE_READWRITE = 0x04, &old)` — this protection flip succeeds because the carrier's file passes CIG. `WriteProcessMemory(hTarget, baseAddr + text_rva, shellcode, shellcodeSize, ...)` to overwrite `.text`. `VirtualProtectEx(..., PAGE_EXECUTE_READ = 0x20, &old)` to restore execution semantics.
5. **Execution**: `RtlCreateUserThread(hTarget, ..., (LPTHREAD_START_ROUTINE)(baseAddr + text_rva), ...)` or `NtCreateThreadEx(...)`. The thread creation does not re-validate CI — the kernel CI callbacks fire only on section map and protection flip, not on thread start. The shellcode now executes in the CIG-enforced Edge process.
6. **Failure path**: if the pre-flight query returns untrusted, fall back to a sibling process. The sibling `RuntimeBroker.exe` (running as the same user, typically not CIG-enforced) accepts standard `VirtualAllocEx`-style injection without the carrier-stomp overhead. Or pivot to the user's `sihost.exe` / `taskhostw.exe` which are commonly CIG-unenforced.

## Common Mistakes

1. **Treating `S_FALSE` as failure**: `WldpQueryDynamicCodeTrust` returns `S_OK` (trusted), `S_FALSE` (untrusted but the call succeeded), or a failure `HRESULT`. Operators who collapse `S_FALSE` into "error, try anyway" trigger the CIG failure event the query was designed to avoid. Always branch on the explicit three-way return.
2. **Querying an anonymous RWX region**: a memory-only `NtAllocateVirtualMemory` allocation has no file backing, so the verdict is *always* `S_FALSE` under any default WDAC policy — the rule set is file-identity-keyed, there is no rule class that blesses anonymous heap. The query is meaningful only for file-backed sections (mapped via `NtMapViewOfSection` from a section object backed by a file). Operators who query their heap shellcode region see consistent `S_FALSE` and conclude the API is broken.
3. **Forgetting to align and round the (base, size) tuple**: the kernel query path silently truncates `base` to the enclosing page (`base & ~0xFFF`) on x64 and silently truncates `size` downward to the page boundary — so querying `(0x180001234, 0x500)` is treated as `(0x180001000, 0x1000)` and only the page containing the start address is checked. Always round `base` down to page granularity and `size` up to the next page boundary before querying, or trailing pages go unverified.
4. **Confusing CIG with ProhibitDynamicCode**: `ProcessSignaturePolicy` (CIG, value 7) allows signed dynamic code; `ProcessDynamicCodePolicy` (value 0x32) with `ProhibitDynamicCode` bit set blocks *all* dynamic code, signed or not — including any code that `WldpQueryDynamicCodeTrust` would bless. Operators who check only CIG and miss a `ProhibitDynamicCode` setting proceed with allocation that fails immediately with `STATUS_ACCESS_DENIED`-derived codes.
5. **Expecting the public API to take a target PID**: the canonical `WldpQueryDynamicCodeTrust` export operates against the *calling* process's policy context — it does not accept a target process handle. Cross-process queries require injecting a small stub into the target process that calls the API locally, or reverse-engineering the underlying `NtQuerySystemInformation` / IOCTL dispatch to construct a query targeting another PID (not on the public export surface).
6. **Not handling the WOW64 boundary**: the 32-bit `wldp.dll` forwarder marshals the query through the 64-bit kernel via the WOW64 transition layer. Pointer truncation bugs in the bridge silently corrupt the query — passing a 64-bit `base` from a 32-bit caller drops the upper 32 bits. Compile the implant as 64-bit when targeting 64-bit processes, or use `NtWow64ReadVirtualMemory64`-style handling for the cross-bits pointer marshaling.
7. **Neglecting the post-map protection flip**: the CI gate fires on the `VirtualProtectEx(..., PAGE_EXECUTE_READWRITE)` call, not on the section map. Operators who map the section successfully but skip the `WldpQueryDynamicCodeTrust` pre-flight on the protection-flip step trigger the CIG failure at the protection flip — the section is mapped but the executable transition is rejected, leaving an orphan mapped section and an ETW event.
