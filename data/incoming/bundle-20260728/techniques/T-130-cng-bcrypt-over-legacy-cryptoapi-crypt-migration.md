# CNG (BCrypt*) over Legacy CryptoAPI (Crypt*) Migration — Windows-native AES-GCM for payload encryption

## Summary

Operator's deliberate selection of the Cryptography Next Generation (CNG) `BCrypt*` API family (`bcrypt.dll`) over the deprecated CryptoAPI `Crypt*` family (`advapi32.dll` / `rsaenh.dll`) for symmetric payload encryption in C or C++ shellcode loaders. The CNG sequence for AES-GCM is: `BCryptOpenAlgorithmProvider` with `BCRYPT_AES_ALGORITHM` (`L"AES"`) under `MS_PRIMITIVE_PROVIDER` → `BCryptSetProperty(hAlg, BCRYPT_CHAINING_MODE, BCRYPT_CHAIN_MODE_GCM)` before key generation → `BCryptGenerateSymmetricKey` with a 32-byte key → `BCryptEncrypt` supplying a populated `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO` struct carrying the 12-byte nonce, the 16-byte tag output buffer, and optional AAD. This replaces the CryptoAPI path `CryptAcquireContextA(PROV_RSA_AES=24)` → `CryptDeriveKey(CALG_AES_256=0x00006610)` → `CryptEncrypt`, which the Windows SDK has marked deprecated since Windows Vista and which cannot perform authenticated encryption in any mode — GCM, CCM, Poly1305 are all unavailable through the legacy surface. The tradeoff versus the Rust-native `aes-gcm` crate (documented in T-021) is operator portability across C/C++ toolchains that lean on the OS FIPS-validated primitive versus a zero-dependency self-contained binary that carries its own AES tables. No privilege is required beyond the calling process token; the CNG user-mode shim `bcrypt.dll` either fast-paths the algorithm in-process via `bcryptprimitives.dll` or forwards to the kernel `ksecdd.sys` provider when FIPS policy is enforced. The vault's T-021 card documents Rust-native AES-GCM for the `dark_crystal` crate but does not cover the Windows CNG path for C/C++ operators.

## Mechanism

### Variant 1: CNG AES-GCM (BCrypt*) — the recommended path

1. Call `BCryptOpenAlgorithmProvider(&hAlg, BCRYPT_AES_ALGORITHM, MS_PRIMITIVE_PROVIDER, 0)`. `BCRYPT_AES_ALGORITHM` is the wide string `L"AES"`. `MS_PRIMITIVE_PROVIDER` is `L"Microsoft Primitive Provider"`. Returns `STATUS_SUCCESS` (`0x00000000`). On FIPS-enabled systems the provider instance routes through the FIPS-validated algorithm implementation.
2. Optionally query block length: `BCryptGetProperty(hAlg, BCRYPT_BLOCK_LENGTH, ...)`. For AES this returns 16. Informational only for GCM because GCM is a stream mode.
3. Query the key object length: `BCryptGetProperty(hAlg, BCRYPT_OBJECT_LENGTH, &cbKeyObject, ...)`. This value is provider-dependent — AES-256 on Windows 10/11 reports on the order of 704 bytes. Never hardcode; query at runtime.
4. Set the chaining mode: `BCryptSetProperty(hAlg, BCRYPT_CHAINING_MODE, (PUCHAR)BCRYPT_CHAIN_MODE_GCM, sizeof(BCRYPT_CHAIN_MODE_GCM), 0)`. `BCRYPT_CHAINING_MODE` is `L"ChainingMode"`, `BCRYPT_CHAIN_MODE_GCM` is `L"ChainingModeGCM"`. **This must be set before `BCryptGenerateSymmetricKey`** — the mode is captured into the key object at generation time.
5. Prepare the 32-byte raw symmetric key. For shellcode use this is typically derived via `BCryptDeriveKeyPBKDF2` over a passphrase, fetched from a side channel, or generated by the loader at runtime via `BCryptGenRandom`.
6. Generate the key object: `BCryptGenerateSymmetricKey(hAlg, &hKey, pbKeyObject, cbKeyObject, pbSecret, 32, 0)`. The function populates the caller-supplied `pbKeyObject` buffer with the round-expanded key schedule and the GHASH accumulator state for GCM. Mis-sizing `cbKeyObject` returns `STATUS_INVALID_PARAMETER`.
7. Allocate and zero a `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO` struct. Initialize: `cbSize = sizeof(BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO)`, `dwInfoVersion = BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO_VERSION` (= 1), `pbNonce` pointing at the 12-byte nonce, `cbNonce = 12`, `pbTag` pointing at the 16-byte output tag buffer, `cbTag = 16`, `pbAuthData` / `cbAuthData` set if AAD is used.
8. Call `BCryptEncrypt(hKey, pbPlaintext, cbPlaintext, pAuthInfo, NULL, 0, pbCiphertext, cbCiphertext, &cbResult, 0)`. For GCM the `pbIV` parameter is NULL — the nonce lives inside the auth info struct. `cbCiphertext` equals `cbPlaintext`; GCM produces no padding.
9. The tag is written to the `pbTag` buffer. Save it alongside the ciphertext; it is required for decryption and tamper detection. Failure to capture the tag is unrecoverable.
10. Decryption: same setup, `pbTag` is the input tag, then `BCryptDecrypt`. Check the return value explicitly: `STATUS_AUTH_TAG_MISMATCH` (`0xC000A002`) indicates tampered ciphertext or wrong key — do not commit the decrypted output in this case.
11. Cleanup: `BCryptDestroyKey(hKey)`, then `BCryptCloseAlgorithmProvider(hAlg, 0)`. `SecureZeroMemory` the key object buffer and the raw key material before `HeapFree`. The round-expanded key schedule is reversible.

### Variant 2: Legacy CryptoAPI (Crypt*) — what not to ship

1. `CryptAcquireContextA(&hProv, NULL, NULL, PROV_RSA_AES, CRYPT_VERIFYCONTEXT)` where `PROV_RSA_AES = 24` and `CRYPT_VERIFYCONTEXT = 0xF0000000`. Returns a CSP handle for AES support via the Microsoft Enhanced RSA and AES Cryptographic Provider (`rsaenh.dll`).
2. `CryptCreateHash(hProv, CALG_SHA_256, 0, 0, &hHash)` then `CryptHashData` to populate a hash object.
3. `CryptDeriveKey(hProv, CALG_AES_256, hHash, 0, &hKey)` where `CALG_AES_256 = 0x00006610`. The hash output is reduced to a 256-bit AES key.
4. `CryptSetKeyAttribute(hKey, KP_MODE, &dwMode, sizeof(dwMode))` with `dwMode = CRYPT_MODE_CBC`. GCM is unavailable through this API.
5. `CryptEncrypt(hKey, NULL, TRUE, 0, pbData, &pdwDataLen, dwBufLen)`. With `Final = TRUE` the function pads the buffer to a block boundary. There is no tag, no nonce, no AAD path.
6. `CryptDestroyKey(hKey)`, `CryptReleaseContext(hProv, 0)`.

The CryptoAPI path lacks authenticated encryption entirely. Any operator shipping `CryptEncrypt`'d payloads ships ciphertext that an analyst can modify in transit without detection — CBC padding-oracle attacks, bit-flipping, ciphertext substitution all become viable against the loader. Microsoft deprecated the `Crypt*` family at the introduction of CNG; the SDK headers mark `CryptAcquireContext` and `CryptEncrypt` as deprecated and recommend the `BCrypt` equivalents. The functions remain present in `advapi32.dll` for backward compatibility but receive no new algorithms or modes.

### Variant 3: Rust `aes-gcm` crate — T-021

For Rust toolchains, the native `aes-gcm` crate (documented in T-021 for the `dark_crystal` crate) provides AES-GCM without OS linkage. This is preferred for Rust-based loaders because: no `bcrypt.dll` import in the static analysis output, no CNG provider enumeration, constant-time audited implementation. Tradeoff: the binary carries the AES tables and the GHASH multiply routine, inflating stripped size by ~30-50 KB, and the operator must trust the crate's audit trail rather than the Microsoft FIPS-validated kernel module. The two variants are operationally equivalent at the cryptographic level — both produce NIST SP 800-38D compliant AES-96-GCM ciphertext — and the choice reduces to supply-chain trust versus dependency footprint.

## OS Internals Context

The CNG architecture splits cleanly between user-mode and kernel-mode components. The user-mode shim `bcrypt.dll` exports the `BCrypt*` API surface and either fast-paths the algorithm through `bcryptprimitives.dll` (the in-process Microsoft Primitive Provider implementation, loaded as a dependency of `bcrypt.dll`) or forwards the request through `NtDeviceIoControlFile` against the kernel-mode CNG provider `ksecdd.sys` at `\Device\Ksecdd`. The decision between fast-path and kernel forward is governed by FIPS policy: when `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\FIPSAlgorithmPolicy\Enabled = 1`, the user-mode fast-path is bypassed and the algorithm is computed in kernel mode against the FIPS-validated implementation. AES and AES-GCM are FIPS-validated, so this code path succeeds — algorithms like RC4 and MD5 return `STATUS_NOT_SUPPORTED` (`0xC00000BB`) under FIPS.

Provider pluggability is the architectural delta between CNG and CryptoAPI. CryptoAPI providers (CSPs) are loaded by `advapi32.dll` into the calling process address space; the AES CSP `rsaenh.dll` lives in System32 and the algorithm is computed in-process. CNG providers are isolated: `BCryptResolveProviders` walks the provider registry at `HKLM\SOFTWARE\Microsoft\Cryptography\Defaults\Provider Categories` to dispatch algorithm requests to the correct provider. The default algorithm for AES resolves to the Microsoft Primitive Provider, but the registry allows alternate providers (third-party HSMs, smart-card KSPs) to be substituted for any algorithm namespace.

The `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO` struct is the load-bearing structure for AEAD modes. Field order from `bcrypt.h`:

```
ULONG    cbSize;            // must equal sizeof(BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO)
ULONG    dwInfoVersion;     // must equal BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO_VERSION (1)
PUCHAR   pbNonce;           // pointer to the 12-byte nonce buffer
ULONG    cbNonce;           // 12 for GCM
PUCHAR   pbAuthData;        // pointer to AAD buffer, or NULL
ULONG    cbAuthData;        // length of AAD
PUCHAR   pbTag;             // pointer to 16-byte tag (output on encrypt, input on decrypt)
ULONG    cbTag;             // 16 for full-strength GCM tag
PUCHAR   pbMacContext;      // internal state for multi-call AEAD, NULL for single-shot
ULONG    cbMacContext;      // 0 for single-shot
ULONGLONG cbAAD;            // cumulative AAD bytes processed (multi-call state)
ULONGLONG cbData;           // cumulative plaintext bytes processed (multi-call state)
ULONG    dwFlags;           // BCRYPT_AUTH_MODE_IN_PROGRESS for multi-call, else 0
```

The struct layout uses natural alignment — pointer fields are 8 bytes on x64, 4 bytes on x86 — so `sizeof` differs across architectures. Always use `sizeof(BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO)` for `cbSize`; hardcoding `0x40` or `0x60` will fail the validation check at the ksecdd boundary and return `STATUS_INVALID_PARAMETER` before any crypto work begins. The `dwInfoVersion` field is checked second; any value other than 1 is rejected.

Key object lifetime is non-obvious. `BCryptGenerateSymmetricKey` populates the caller-supplied `pbKeyObject` buffer with the round-expanded AES key schedule, the GHASH accumulator state (the H matrix, the J0 counter, and the running MAC for GCM), and the chaining mode metadata. The buffer is opaque to the caller and must be sized via `BCryptGetProperty(hAlg, BCRYPT_OBJECT_LENGTH, ...)`; the value differs across Windows versions, so runtime query is mandatory. The key schedule is never written to disk unless the operator explicitly persists it via the `NCrypt*` API family against the Key Storage Provider — that path ties the key to a user or machine context, with the key material encrypted via DPAPI and stored under `%APPDATA%\Microsoft\Crypto\Keys` (user) or `%ALLUSERSPROFILE%\Microsoft\Crypto\Keys` (machine). For shellcode use, transient symmetric keys are preferred — they never touch disk and leave no DPAPI-encrypted blob behind.

ETW coverage of CNG is exposed through the `Microsoft-Windows-CryptoCNG` provider (GUID `{E20194C4-9CE2-436D-BD7B-B58B658329E4}`). The provider emits events at algorithm provider open, key generation, and encrypt/decrypt boundaries. The legacy CryptoAPI family has its own provider, `Microsoft-Windows-CryptoApi` (formerly `Microsoft-Windows-CryptoApi-DPAPI`), which similarly emits provider-open and key-derive events. Both providers are enabled by default in many EDR configurations; the CNG telemetry is denser because it captures per-call encrypt/decrypt events whereas the CryptoAPI provider historically only captures provider and key-lifecycle events.

## Key Implementation Details

The single most common operator mistake is setting `BCRYPT_CHAINING_MODE` after `BCryptGenerateSymmetricKey`. The mode is bound into the key object at generation time; setting the property afterwards has no effect on the already-generated key. The result is silent AES-CBC execution against a buffer the operator intended as GCM — `STATUS_SUCCESS` returned, no error surfaced, but the decrypted payload is garbage and the loader crashes on execution with no diagnostic clue pointing back at the crypto layer. The fix is strictly ordering: open provider, set chaining mode, generate key.

The nonce length for GCM is conventionally 12 bytes. CNG accepts nonces of any length but the NIST SP 800-38D fast path (which avoids the GHASH-based nonce derivation) requires exactly 96 bits. Using `cbNonce != 12` triggers an internal GHASH invocation that consumes an additional ~50 cycles per call and produces an IV that is not interoperable with most third-party AES-GCM implementations. For loader tradecraft, always use 12 — and always generate it freshly via `BCryptGenRandom` per encryption, never reuse a nonce with the same key.

The tag buffer must be sized to exactly the tag length expected on decrypt. `cbTag = 16` (full 128-bit tag) is the recommended value. Truncated tags (`cbTag = 12`, `cbTag = 8`) are supported by CNG but reduce forgery resistance from `2^-128` to `2^-96` or `2^-64` per attempt — for high-value payloads that may face repeated adaptive forgery attempts, the full 16-byte tag is the correct choice.

Key material scrubbing is non-negotiable. After `BCryptDestroyKey`, the `pbKeyObject` buffer still contains the round-expanded AES key schedule until the heap page is reused. `SecureZeroMemory(pbKeyObject, cbKeyObject)` before `HeapFree` is mandatory. Forensic memory analysis can locate un-scrubbed key schedules by signature-scanning for recognizable AES round constants — the AES S-box byte `0x63` at index zero, the inverse S-box `0x52`, and the round constants (rcon values 0x01, 0x02, 0x04, 0x08, 0x10, 0x20, 0x40, 0x80, 0x1B, 0x36 for the 10 rounds of AES-128) appear in predictable positions in the schedule. `bcryptprimitives.dll` internally uses `RtlSecureZeroMemory` on its own allocations, but the caller's `pbKeyObject` buffer is the caller's responsibility.

WOW64 boundary: 32-bit processes calling `bcrypt.dll` use the 32-bit `bcrypt.dll` in `System32`, which thunks through to the 64-bit kernel. The struct layout is identical across architectures after `sizeof` expansion, so the same source compiles. The `cbKeyObject` return value from `BCryptGetProperty` differs in size across Windows versions — Windows 7 reports different sizes than Windows 11 for AES-256 — so always query at runtime, never hardcode.

## Why It Matters

CNG AES-GCM is the correct Windows-native crypto primitive for operators building C or C++ loaders that need to ship encrypted payloads. The presence of authentication (the tag) closes the entire class of ciphertext-substitution attacks that plague CryptoAPI's CBC path: an analyst cannot flip bits in the ciphertext to mutate the decrypted payload without producing `STATUS_AUTH_TAG_MISMATCH` at decrypt. The `bcrypt.dll` import, while not invisible to static analysis, is part of the Windows baseline import set for many legitimate binaries — `lsass.exe`, `svchost.exe`, and a wide range of system services import bcrypt — and does not raise the suspicion index of a loader the way a statically linked OpenSSL or mbedtls does.

The technique composes directly with payload staging (encrypted shellcode in `.rdata` or fetched from C2), with key-derivation primitives (`BCryptDeriveKeyPBKDF2`, `BCryptKeyDerivation` for HKDF) that derive the symmetric key from a passphrase shared with the implant, and with the equivalent Rust-native path in T-021 when the loader is Rust-based. The same primitive enables encrypted C2 channels (`T1573.001`) when the loader additionally uses `BCryptEncrypt` on outbound traffic — the API surface is identical, only the buffer origin differs. One bcrypt.dll import set covers payload-at-rest encryption, C2 channel encryption, key derivation, and random number generation, which is the operational density that justifies the migration away from CryptoAPI.

## Detection Considerations

- **Telemetry sources**: ETW `Microsoft-Windows-CryptoCNG` provider emits events at algorithm provider open, key generation, and encrypt/decrypt. EDRs hooking `bcrypt.dll`'s export table intercept `BCryptEncrypt` / `BCryptDecrypt` in user mode; some additionally place inline hooks on the ALPC dispatch through `ntdll!NtDeviceIoControlFile` against `Device\Ksecdd` to capture the kernel-bound variant under FIPS. Memory forensics can locate `bcryptprimitives!AES_GCM` code regions in loaded module lists and identify residual key schedules on heap. The legacy `Crypt*` family has separate but parallel coverage via `Microsoft-Windows-CryptoApi`.
- **Bypass options**: load a private copy of `bcrypt.dll` from a sideloaded path (defeats export-table hooks on the system copy, but not the kernel ETW emission); implement AES-GCM in-process from a vendored implementation (no `bcrypt.dll` import, no ETW — equivalent to the Rust crate path in T-021); invoke kernel-mode CNG directly through a driver IOCTL to `Device\Ksecdd` (requires kernel access, bypasses user-mode hooks entirely); counter-intuitively, fall back to the `Crypt*` family — CNG detection coverage is denser than CryptoAPI coverage in modern EDRs, and the deprecated path can sometimes evade better for low-sophistication loaders.
- **Residual artifacts**: the `bcrypt.dll` entry in the binary's import table; `Microsoft-Windows-CryptoCNG` event log entries with the calling process PID; heap pages containing the round-expanded AES key schedule if not scrubbed (identifiable by the S-box value `0x63` and the round constants `0x01..0x36` in predictable positions); the algorithm provider handle kept open in the process handle table until `BCryptCloseAlgorithmProvider` is called.

## Common Mistakes

1. **Setting `BCRYPT_CHAINING_MODE` after `BCryptGenerateSymmetricKey`**. The mode is bound to the key object at generation; setting it later has no effect. Result: silent AES-CBC execution against a buffer expected as GCM, no error code, garbage payload at decrypt.
2. **Mismatched nonce length between encrypt and decrypt**. CNG runs GHASH-based nonce derivation if `cbNonce != 12`; the derived IV is deterministic given the nonce bytes but a different nonce length produces a different IV. Receiver must use the same nonce length as sender.
3. **Undersized key object buffer**. Hardcoding `cbKeyObject` to a value observed on one Windows version and shipping on another produces `STATUS_INVALID_PARAMETER`. Always query at runtime via `BCryptGetProperty(hAlg, BCRYPT_OBJECT_LENGTH, ...)`.
4. **Forgetting to scrub the key object buffer**. The round-expanded AES schedule contains the original key material in reversible form (the inverse key schedule exists in the same buffer for decryption paths). `SecureZeroMemory` before `HeapFree` is mandatory.
5. **Passing the nonce through the `BCryptEncrypt pbIV` parameter**. For GCM the `pbIV` pointer is NULL — the nonce lives inside `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO.pbNonce`. Passing a non-NULL `pbIV` with a GCM key returns `STATUS_INVALID_PARAMETER`.
6. **Ignoring `STATUS_AUTH_TAG_MISMATCH` on decrypt**. The function may write partial plaintext to the output buffer before failing. Operators must not commit this partial output; allocate the output buffer and only surface it to the caller after `STATUS_SUCCESS`.

## Composition with Other Techniques

A realistic kill chain that uses this card end-to-end:

1. Operator generates a 256-bit AES key locally and stages it in the C2 staging server. The key is delivered to the implant out-of-band at beacon time.
2. Loader payload (Reflective DLL or position-independent shellcode) is encrypted using CNG AES-GCM with a freshly-generated 12-byte nonce per payload. The nonce and tag are prepended to the ciphertext blob: `[12B nonce][16B tag][N bytes ciphertext]` — a self-describing blob format the loader can parse at runtime.
3. The encrypted blob is embedded in the loader's `.rdata` section (T1027.009 embedded payload).
4. At runtime the loader calls `BCryptOpenAlgorithmProvider` → `BCryptSetProperty(GCM)` → `BCryptGenerateSymmetricKey` with the staged key, then `BCryptDecrypt` on the embedded blob. On `STATUS_SUCCESS` the decrypted buffer is passed to a process injection primitive (e.g. `NtCreateSection` + `ZwMapViewOfSection` for hollow-process injection, or `NtProtectVirtualMemory` to flip `PAGE_EXECUTE_READWRITE` on a fresh allocation).
5. The same AES-GCM key is used to encrypt C2 traffic by feeding `BCryptEncrypt` with per-message nonces, satisfying T1573.001 encrypted-channel requirements without shipping OpenSSL or mbedtls.

This composition minimizes new crypto code in the loader: the `bcrypt.dll` import set covers payload-at-rest encryption, C2 channel encryption, key derivation, and CSPRNG in a single ~600 KB dependency. The FIPS-validated primitive satisfies enterprise security policy that may reject non-FIPS binaries at the EDR layer, and the key schedule is never persisted to disk.
