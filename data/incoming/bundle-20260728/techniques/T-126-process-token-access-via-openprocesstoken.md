# Process Token Access via OpenProcessToken — The foundational handle-grant primitive for every access-token manipulation chain

## Summary

`OpenProcessToken` is the Win32 user-mode gateway to a process's access token — the kernel object (`_TOKEN`) that carries the user SID, group SIDs, privilege bitmap, integrity level, logon session LUID, and default DACL for every thread in that process. The call is a thin wrapper over `NtOpenProcessTokenEx`, which performs an `ObOpenObjectByPointer` against the `ExFastRef` token pointer stored in `EPROCESS.Token` and returns a user-mode handle into the caller's `HANDLE_TABLE` with the requested access mask. A successful open requires `PROCESS_QUERY_LIMITED_INFORMATION` (`0x1000`) on the process handle (acquired via `OpenProcess` or inherited), and the resulting token handle carries rights such as `TOKEN_QUERY` (`0x0008`), `TOKEN_DUPLICATE` (`0x0002`), `TOKEN_ASSIGN_PRIMARY` (`0x0001`), `TOKEN_IMPERSONATE` (`0x0004`), and `TOKEN_ADJUST_PRIVILEGES` (`0x0020`). From that handle, three downstream primitives compose: enumeration via `GetTokenInformation` (`TokenUser`, `TokenGroups`, `TokenPrivileges`, `TokenStatistics`, `TokenElevation`, `TokenOrigin`), duplication via `DuplicateTokenEx` (which calls `NtDuplicateToken` and produces either a `TokenPrimary` or `TokenImpersonation` copy at a chosen `SECURITY_IMPERSONATION_LEVEL`), and application via `SetThreadToken` (`NtSetInformationThread(ThreadImpersonationToken)`) or `ImpersonateLoggedOnUser` for impersonation, or `CreateProcessWithTokenW` / `NtSetInformationProcess(ProcessAccessToken)` for primary-token use. Cross-process token theft — opening `services.exe`, `wininit.exe`, `lsass.exe`, or a SYSTEM-privileged service host — is gated behind `SeDebugPrivilege` (`luid 20`) enforced by `SeAccessCheck` against the target process's security descriptor (typically `System`:`System`, `SACL` empty by default). The vault's T-015 card documents the multi-hop token impersonation chain end-to-end and T-017 documents persistence via token replay, but neither unpacks the `OpenProcessToken` enumeration-and-duplication sequence that both depend upon; this card fills that gap and covers the three operational variants (enumeration, impersonation theft, primary swap) under a single primitive.

## Mechanism

### Variant 1: Token Enumeration (reconnaissance)

1. Acquire a process handle. For self-enumeration use `GetCurrentProcess()` (a macro alias for `(HANDLE)-1` — `NtCurrentProcess()` resolves to `CurrentProcess` in the handle table without a lookup). For cross-process enumeration use `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION = 0x1000, FALSE, pid)`. On Vista+ `PROCESS_QUERY_LIMITED_INFORMATION` is sufficient and avoids the `PROCESS_QUERY_INFORMATION` (`0x0400`) requirement that historically triggered more aggressive audit logging.
2. Call `OpenProcessToken(hProcess, TOKEN_QUERY = 0x0008, &hToken)`. The returned handle grants read-only access to the kernel `_TOKEN` object via the info-class query path.
3. Call `GetTokenInformation(hToken, TokenUser, buf, cbBuf, &cbNeeded)`. `TokenUser` (info class `1`) returns a `TOKEN_USER` structure containing a pointer-and-SID pair: `User.Sid` points into the same buffer, `User.Attributes` is reserved zero for the user SID. Parse with `ConvertSidToStringSidW` to obtain `S-1-5-18` (`SYSTEM`), `S-1-5-19` (`LOCAL SERVICE`), `S-1-5-20` (`NETWORK SERVICE`), or an arbitrary domain user SID.
4. Repeat for `TokenGroups` (class `2`) — returns `TOKEN_GROUPS` with a `GroupCount` followed by `SID_AND_ATTRIBUTES[]`. Bit flags: `SE_GROUP_MANDATORY` (`0x00000001`), `SE_GROUP_ENABLED` (`0x00000004`), `SE_GROUP_USE_FOR_DENY_ONLY` (`0x00000010`), `SE_GROUP_LOGON_ID` (`0xC0000000` — the locally unique identifier for the logon session).
5. Repeat for `TokenPrivileges` (class `3`) — returns `TOKEN_PRIVILEGES` with `PrivilegeCount` and an array of `LUID_AND_ATTRIBUTES`. Each `Luid` is a 64-bit value (locally unique, machine-boot-scoped); attributes are `SE_PRIVILEGE_ENABLED` (`0x00000002`), `SE_PRIVILEGE_ENABLED_BY_DEFAULT` (`0x00000001`), `SE_PRIVILEGE_REMOVED` (`0x00000004`). Map luid 20 → `SeDebugPrivilege`, 9 → `SeAssignPrimaryTokenPrivilege`, 10 → `SeIncreaseQuotaPrivilege`, 11 → `SeTcbPrivilege`, 17 → `SeImpersonatePrivilege`, 18 → `SeCreateGlobalPrivilege`.
6. Query `TokenStatistics` (class `10`) for `AuthenticationId` (the logon-session LUID — same value as the `SE_GROUP_LOGON_ID` group), `TokenType`, `ImpersonationLevel`, `DynamicCharged` / `DynamicAvailable` (default-DACL budget), and `ModifiedId` (rotated on every privilege/group adjustment — useful as a "this token was tampered with" sentinel).
7. Query `TokenElevationType` (class `20`) to distinguish `TokenElevationTypeDefault` (`1`, UAC off or non-admin user), `TokenElevationTypeFull` (`2`, elevated split token), `TokenElevationTypeLimited` (`3`, filtered non-elevated split token). Pair with `TokenLinkedToken` (class `19`) to fetch the other half of the split token pair — requires `TOKEN_DUPLICATE` on the source and `SeTcbPrivilege` to actually open it.
8. Close with `CloseHandle(hToken)` — without this the handle leaks into the `HANDLE_TABLE` and the `_TOKEN` object's `PointerCount` never decrements to zero.

### Variant 2: Token Theft to Impersonation (the RoguePotato / Potato family core)

1. Enable `SeDebugPrivilege` (luid `20`) on the calling thread's own primary token via `OpenProcessToken(GetCurrentProcess(), TOKEN_ADJUST_PRIVILEGES, &hSelf)` → `LookupPrivilegeValueW(NULL, SE_DEBUG_NAME, &luid)` → `AdjustTokenPrivileges(hSelf, FALSE, &tp, ...)` where `tp.Privileges[0] = {luid, SE_PRIVILEGE_ENABLED}`. Without this step, `OpenProcess` on a system process returns `ERROR_ACCESS_DENIED` (`0x5`) because `SeAccessCheck` rejects the caller.
2. `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ, FALSE, pid_of_services)` — `services.exe` (PID 552 typical on Win10/11) runs as `NT AUTHORITY\SYSTEM` and exposes a primary token that is the most common theft target on a single-host engagement.
3. `OpenProcessToken(hProc, TOKEN_DUPLICATE | TOKEN_QUERY, &hSysToken)`. `TOKEN_DUPLICATE` (`0x0002`) is the right that `NtDuplicateToken` checks against on the source.
4. `DuplicateTokenEx(hSysToken, MAXIMUM_ALLOWED, NULL, SecurityImpersonation, TokenImpersonation, &hDupToken)`. `SecurityImpersonation` (level `2`) is the minimum level that permits local object access under the impersonated identity; `SecurityDelegation` (level `3`) is required only for outbound remote access. `TokenImpersonation` (type `2`) is mandatory — `SetThreadToken` rejects primary tokens with `STATUS_BAD_TOKEN_TYPE` (`0xC00000A0`).
5. `SetThreadToken(NULL, hDupToken)` — `NULL` thread handle targets the current thread. The kernel stores the impersonation token pointer in `KTHREAD.ImpersonationInfo` (a `_PS_IMPERSONATION_INFO` containing the token, copy-on-open flag, effective-only flag, and impersonation level). A side effect: the thread's `ClientSecurity` cache is invalidated and the next `SeAccessCheck` re-resolves against the impersonation token.
6. Verify with `OpenThreadToken(GetCurrentThread(), TOKEN_QUERY, TRUE, &hVerify)` — `TRUE` for `OpenAsSelf` bypasses the impersonation context to read the thread's own token. Parse `TokenUser` to confirm `S-1-5-18`.
7. Optionally restore the original context with `SetThreadToken(NULL, NULL)` (`RevertToSelf` is the Win32 wrapper) — leaving the thread impersonating SYSTEM past the operation window is the single most common detection footprint.

### Variant 3: Primary Token Swap for Child-Process Spawning

1. Steps 1–3 of Variant 2 unchanged (acquire `hSysToken` with `TOKEN_DUPLICATE`).
2. `DuplicateTokenEx(hSysToken, TOKEN_ALL_ACCESS, NULL, SecurityAnonymous, TokenPrimary, &hPrimaryToken)`. `SecurityAnonymous` (level `0`) is sufficient because a primary token is not used for impersonation-style access checks within the spawning thread — its `ImpersonationLevel` field is ignored at `TokenType == TokenPrimary`. `TokenPrimary` (type `1`) is mandatory for the spawn paths.
3. **Path A** — `CreateProcessWithTokenW(hPrimaryToken, LOGON_WITH_PROFILE, NULL, cmdline, 0, NULL, NULL, &si, &pi)`. Requires `SeAssignPrimaryTokenPrivilege` (luid `9`) **or** `SeIncreaseQuotaPrivilege` (luid `10`) on the calling process. Internally invokes `NtCreateUserProcess` with the explicit token as `ProcessParameters.Token` — the child starts with the SYSTEM token as primary.
4. **Path B** — `NtSetInformationProcess(GetCurrentProcess(), ProcessAccessToken = 9, &hPrimaryToken, sizeof(hPrimaryToken))`. Replaces the calling process's primary token in-place. Requires `SeTcbPrivilege` (luid `11`) — far rarer than the create-process path. Affects every subsequent thread spawn in the process and is detectable as a `ModifiedId` rotation.
5. **Path C** — `ImpersonateLoggedOnUser(hPrimaryToken)`. Unlike `SetThreadToken`, this wrapper accepts either primary or impersonation tokens (it duplicates internally to an impersonation token first). The thread then runs as SYSTEM for the lifetime of the impersonation, and any child spawned via `CreateProcessW` will inherit the *process primary token*, not the impersonation token — so the impersonation does not propagate to children without explicit duplication. This is the historical "Potato" trick used when the operator lacks `SeAssignPrimaryTokenPrivilege` but has `SeImpersonatePrivilege`.

## OS Internals Context

`OpenProcessToken` is exported by `kernel32.dll` as a forwarder to `advapi32.OpenProcessToken`, which in turn invokes `NtOpenProcessTokenEx(ProcessHandle, DesiredAccess, ObjectAttributes_flags, TokenHandle)`. The syscall is `NtOpenProcessTokenEx` (SSN dependent on Windows build — there is no exported SSN constant). The kernel-side path is `NtOpenProcessTokenEx` → `ObReferenceObjectByHandle` on the process handle (validated against the caller's `HANDLE_TABLE` and the `OBJ_PROTECT_CLOSE` / `OBJ_INHERIT` attributes) → resolve `EPROCESS.Token` (an `EX_FAST_REF` packed pointer; low 4 bits encode a refcount-mutation mask) → `ObOpenObjectByPointer` on the `_TOKEN` object, gating with `SeAccessCheck` against the token object's security descriptor.

The `_TOKEN` kernel structure (size varies by build, ~0x180–0x1C0 bytes on modern Win10/11) carries the fields an operator cares about: `TokenSource` (`TOKEN_SOURCE` — `LUID` + 8-byte name like `"User32"`), `TokenId` / `UserTokenId` (per-token and per-logon `LUID`s), `ExpirationTime`, `DynamicCharged` / `DynamicAvailable` (default-DACL bucket), `User` (`SID_AND_ATTRIBUTES` — the primary user SID), `UserAndGroups` (`PTOKEN_GROUPS` — array including the user), `RestrictedSids`, `PrimaryGroup` (`PSID`), `Privileges` (`PTOKEN_PRIVILEGES`), `DefaultDacl`, `TokenType`, `ImpersonationLevel`, `Flags` (`TOKEN_WRITE_RESTRICTED`, `TOKEN_SANDBOX_INERT`, `TOKEN_HAS_RESTORE_PRIVILEGE` etc.), `TokenFlags`, and `SessionId` (the WTS session, used for `ProcessAccessToken` checks during `NtCreateUserProcess`).

When `GetTokenInformation(TokenPrivileges)` is called, the syscall `NtQueryInformationToken` performs an `ObReferenceObjectByHandle` with the requested `TOKEN_QUERY` right, then reads the `Privileges` pointer directly into the caller's buffer (the kernel does a `ProbeForWrite` + `RtlCopyMemory` from kernel `PTOKEN_PRIVILEGES` to the user buffer). For `TokenUser`, the SID is copied in-place so that the `User.Sid` field in the returned `TOKEN_USER` points within the user-mode buffer (not back into kernel memory) — the caller must therefore not free or reuse the buffer before parsing.

`DuplicateTokenEx` calls `NtDuplicateToken(ExistingTokenHandle, DesiredAccess, ObjectAttributes, EffectiveOnly, TokenType, NewTokenHandle)`. The kernel `SeDuplicateToken` allocates a fresh `_TOKEN` via `ExAllocatePoolWithTag('Toke')` (or the equivalent pool), copies the SID arrays and privilege array, generates new `TokenId` / `ModifiedId` `LUID`s via `ExUuidCreate`, optionally copies the default DACL, and stores the new token in the caller's handle table with the requested `TokenType` and `ImpersonationLevel` encoded in the new object's flags. The original token's `PointerCount` is decremented; the new token inherits the source's `SessionId` unless explicitly modified.

For `SetThreadToken(NULL, hImpToken)`, the syscall `NtSetInformationThread(ThreadImpersonationToken = 5)` calls `PsImpersonateClient` on the calling `KTHREAD`. `PsImpersonateClient` allocates a `_PS_IMPERSONATION_INFO` (a small structure containing `Token`, `CopyOnOpen`, `EffectiveOnly`, `ImpersonationLevel`), stores it at `KTHREAD.ImpersonationInfo`, and sets the `KTHREAD.MiscFlags.Impersonating` bit. The previous impersonation info, if any, is dereferenced (`ObDereferenceObject`) — losing the previous impersonation context. A subsequent access check in this thread (any `NtCreateFile`, `NtOpenProcess`, etc.) now resolves through `SeAccessCheck` against the impersonation token rather than the process primary token, except for `OpenAsSelf=TRUE` paths (`NtOpenThreadToken(..., TRUE, ...)`) which deliberately re-resolve against the *process* token to allow introspection of the thread's own impersonation state.

The `SeDebugPrivilege` enforcement is a special case. The privilege check at the top of `NtOpenProcess` (`PsOpenProcess`) bypasses the standard DACL on the process object if the caller has `SeDebugPrivilege` enabled — this is the "debugger" carve-out that lets debuggers attach to system processes. Without it, the process's security descriptor (which for `services.exe` is `System:System`, full control to SYSTEM, no access to anyone else) rejects the open with `STATUS_ACCESS_DENIED`. `SeAccessCheck` is the function that ultimately evaluates both the DACL and the privilege override.

The ETW Threat Intelligence provider (`{F4E1897C-BB5C-5F11-0AA0-FF6DE9B1D7F0}` or in kernel `EtwTi` provider GUID `{E598487D-AB4F-4FAB-A23E-8F9B4D7F3C6E}`) publishes event opcodes for token manipulation:
- `EventID 6` — `TOKEN_GUID_PRIVILEGES` adjustment (`NtAdjustPrivileges` and similar) — the privilege bitmap before/after
- `EventID 7` — group/session adjustments (`NtAdjustGroups`, `NtSetInformationProcess(ProcessSessionId)`)
- `EventID 8` — `NtCreateProcess*` with explicit token (parent spawns child as a different identity than parent)
- `EventID 9` — process-token-replacement event, fires when `NtSetInformationProcess(ProcessAccessToken)` is invoked or when `CreateProcessWithTokenW`-equivalent spawns occur

EDR vendors that subscribe to the TI provider (`Microsoft-Windows-Kernel-Event` ETW channel is the kernel TI publisher) get these events at ring 0 with full caller `EPROCESS` context. The events are *not* available via normal user-mode ETW consumers — they require PPL (Protected Process Light, antimalware) signature or kernel-resident consumer registration, which is why the red-team community treats TI events as "near-host-IDS" telemetry.

## Key Implementation Details

**Access-rights matrix** — every operation against a token has a specific minimum right, and asking for more than you need amplifies your detection footprint. `TOKEN_QUERY` (`0x0008`) is sufficient for all `GetTokenInformation` classes — never ask for `TOKEN_ALL_ACCESS` (`0x000F01FF`) when enumerating. `TOKEN_DUPLICATE` (`0x0002`) is required for `DuplicateTokenEx` on the *source*; the *destination* rights come from the `DesiredAccess` parameter of `DuplicateTokenEx` itself. `TOKEN_ADJUST_PRIVILEGES` (`0x0020`) is required for `AdjustTokenPrivileges`. `TOKEN_ADJUST_SESSIONID` (`0x0100`) — required for `SetTokenInformation(TokenSessionId)` — additionally requires `SeTcbPrivilege`. Asking for `TOKEN_ALL_ACCESS` on a token you opened with `PROCESS_QUERY_LIMITED_INFORMATION` succeeds but the resulting handle's effective rights are filtered by the source token's DACL, which for `SYSTEM` tokens grants full control only to `SYSTEM` itself — meaning you get a handle but the only meaningful operations are `TOKEN_QUERY` and `TOKEN_DUPLICATE`. This is why the impersonation-theft chain always opens with `TOKEN_DUPLICATE | TOKEN_QUERY`.

**Privilege prerequisites** — for self-privilege adjustment, the calling process must already hold the privilege in its token (enabled or disabled). `AdjustTokenPrivileges` cannot grant privileges the token doesn't have; it only flips the `SE_PRIVILEGE_ENABLED` bit. A medium-IL user process without UAC elevation cannot enable `SeDebugPrivilege` because the filtered token strips it. The split-token mechanism (UAC) is why elevation is a prerequisite for any cross-process token theft — not a bug, a deliberate design choice that limits token theft to already-elevated contexts. The exception is `SeImpersonatePrivilege`, which Microsoft added after MS08-067-era token-theft worms: any process granted `SeImpersonatePrivilege` (which includes all `LOCAL SERVICE` and `NETWORK SERVICE` processes, plus any process that has spawned an RPC server) can impersonate any client that connects to its RPC pipe. This is the primitive the entire "Potato" family exploits.

**WOW64 boundary** — a 32-bit process calling `OpenProcessToken` on a 64-bit target goes through the WOW64 thunk layer (`wow64.dll` → `NtWow64ReadVirtualMemory64` is *not* involved; token access is handled in `advapi32` directly), but the `TOKEN_INFORMATION_CLASS` enum values are identical on both architectures, and `GetTokenInformation`'s buffer formats are pointer-sized (`PSID` and `PVOID`) — meaning a 32-bit caller gets 4-byte pointers in the returned `TOKEN_USER`/`TOKEN_GROUPS` structures even when querying a 64-bit SYSTEM token. Always marshal with the matching pointer width or use the `*W` variants and parse from a byte buffer with explicit offset arithmetic; the `windows` crate's `TOKEN_USER` struct is conditionally pointer-sized by target arch.

**Handle-table leakage** — every unclosed `OpenProcessToken` handle adds an entry to the calling process's `HANDLE_TABLE`, which is enumerable via `NtQuerySystemInformation(SystemHandleInformation)`. A reconnaissance sweep that opens `services.exe`, `lsass.exe`, and `wininit.exe` and forgets to close leaks three persistent handles; tools like `Process Hacker` surface these as "suspicious handle to SYSTEM process" indicators and are a reliable detection point for engagement recon.

**Impersonation-level footgun** — `SecurityIdentification` (level `1`) and `SecurityAnonymous` (level `0`) impersonation tokens cannot be used to access local objects (`SeAccessCheck` returns `STATUS_ACCESS_DENIED` for any object access at these levels). Operators who pass the wrong `SECURITY_IMPERSONATION_LEVEL` to `DuplicateTokenEx` get a token that "looks like SYSTEM" on inspection but produces `ACCESS_DENIED` on every actual operation. Always use `SecurityImpersonation` (`2`) for local work; only `SecurityDelegation` (`3`) is needed for outbound RPC/SMB to remote hosts, and `SeImpersonatePrivilege` is required to even create a level-2-or-higher impersonation token of an identity other than your own.

## Why It Matters

`OpenProcessToken` is the load-bearing primitive for nearly every Windows privilege-escalation chain that does not involve an exploit or kernel-mode code. The Potato family (RottenPotato, JuicyPotato, RoguePotato, PrintSpoofer, GodPotato, EfsPotato) all reduce to: acquire a SYSTEM token via `OpenProcessToken` on an elevated process, duplicate it to a useful type, and apply it to the current thread or a new process. The technique is uniquely powerful because it does not modify the target process — the victim `services.exe` keeps running untouched, the caller simply clones its identity. From the defender's perspective this is asymmetric: the only artifacts are a `PROCESS_QUERY_LIMITED_INFORMATION` open (visible via `NtQuerySystemInformation` if actively swept) and the caller's new impersonation context.

Operationally, this card composes with T-015 (token impersonation chains) — which extends the single-hop theft here into multi-hop delegation chains across RPC pipes — and with T-017 (privilege-escalation persistence) — which uses the duplicated SYSTEM token to install a service or scheduled task that survives reboot. The single-hop path documented here is the prerequisite for both. It also composes with handle-hijack primitives (opening a process whose token we want to clone often requires stealing a handle with the right access from another process that already has it open — a common anti-detection refinement). Reach for this card whenever you have `SeDebugPrivilege` or `SeImpersonatePrivilege` and need to operate as SYSTEM on the current host without injecting code into the SYSTEM process itself.

## Detection Considerations

- **Telemetry sources**: ETW Threat-Intelligence provider (kernel-only, requires PPL consumer) publishes `EventID 6` (privilege adjustment) and `EventID 9` (process-token replacement) — these fire on `DuplicateTokenEx` + `SetThreadToken` and on `NtSetInformationProcess(ProcessAccessToken)`. Sysmon `EventID 10` (ProcessAccess) fires on `OpenProcess` with `GrantedAccess` containing `PROCESS_QUERY_INFORMATION` (`0x0400`) or `PROCESS_QUERY_LIMITED_INFORMATION` (`0x1000`) — but does not itself distinguish "token recon" from legitimate process introspection, so behavioral correlation with a subsequent `DuplicateTokenEx` is required. Kernel object-access auditing (SACL on the process object with `ReadPermissions` ACE) emits `EventID 4663` from `Microsoft-Windows-Security-Auditing` — disabled by default, often enabled on Domain Controllers. Handle-table sweeps via `NtQuerySystemInformation(SystemHandleInformation)` are themselves detectable as the info class requires `SeDebugPrivilege`.
- **Bypass options**: Use `PROCESS_QUERY_LIMITED_INFORMATION` rather than `PROCESS_QUERY_INFORMATION` — Sysmon's `EventID 10` rule predicates are typically tuned to the broader right, and the limited-information variant does not enable `VirtualQueryEx` / `ReadVirtualMemory` operations that more aggressive rules look for. Use `NtOpenProcessTokenEx` directly via syscall stubs (Hell's Gate / Halo's Gate pattern) to bypass `advapi32.dll` IAT hooks placed by userland-hooking EDRs — `NtOpenProcessTokenEx` is not in the standard `ntdll` exported-table subset that most EDRs hook because token-open is rare in benign software. Reuse an inherited handle (e.g., open `services.exe` via `NtGetNextThread` chain or via a handle-table sweep that finds an existing `PROCESS_QUERY_LIMITED_INFORMATION` handle held by an AV scanner) to avoid the `OpenProcess` entirely. For the impersonation step, use `ImpersonateLoggedOnUser` rather than `SetThreadToken` — the resulting `KTHREAD.ImpersonationInfo` is identical, but the user-mode call site is less aggressively hooked because `ImpersonateLoggedOnUser` is a benign-looking advapi32 export used by COM infrastructure.
- **Residual artifacts**: (a) The duplicated token object lives in the kernel `PspCidTable` and the caller's `HANDLE_TABLE` — detectable by `SystemHandleInformation` sweeps showing a `Token` type handle in a non-system process with a source token `AuthenticationId` matching a SYSTEM logon session. (b) `TokenStatistics.ModifiedId` on the duplicated token differs from the original but `AuthenticationId` matches — a forensic tell when comparing the caller's impersonation token to the victim's primary token. (c) `KTHREAD.ImpersonationInfo` on the calling thread is set — visible via `NtQueryInformationThread(ThreadImpersonationToken)` which returns a non-zero handle when the thread is impersonating. (d) If `CreateProcessWithTokenW` was used, the spawned child's `ParentProcessId` is the *calling* process but its `ProcessToken.AuthenticationId` is SYSTEM's — a mismatch visible in `EventID 4688` (Process Creation with token information, when "Include command line" and token-data audit subcategory are enabled).

## Common Mistakes

1. **Asking for `TOKEN_ALL_ACCESS` on a SYSTEM token opened with `PROCESS_QUERY_LIMITED_INFORMATION`** — succeeds in `OpenProcessToken` but the handle is silently filtered to the rights the SYSTEM-token DACL grants the caller (typically only `TOKEN_QUERY` and `TOKEN_DUPLICATE` because the caller is not SYSTEM). Subsequent `AdjustTokenPrivileges` on the resulting handle fails with `ERROR_ACCESS_DENIED`. Always request the specific right you need.
2. **Passing `TokenPrimary` to `SetThreadToken`** — `NtSetInformationThread(ThreadImpersonationToken)` validates `TokenType == TokenImpersonation` and rejects with `STATUS_BAD_TOKEN_TYPE` (`0xC00000A0`). For a primary token, use `ImpersonateLoggedOnUser` (which duplicates-to-impersonation internally) or take the spawn-child path.
3. **Forgetting to enable `SeDebugPrivilege` before `OpenProcess`** — `AdjustTokenPrivileges` only flips the `SE_PRIVILEGE_ENABLED` bit; the privilege must already be in the token. Operators on a medium-IL non-elevated session cannot enable it. Run elevated first, or pivot via `SeImpersonatePrivilege` + RPC-server potato technique.
4. **Using `SecurityAnonymous` or `SecurityIdentification` for `DuplicateTokenEx`** — the duplicated token passes type checks and `GetTokenInformation` returns a valid SYSTEM SID, but every subsequent access check (`OpenFile`, `RegOpenKey`, `OpenProcess`) fails with `ERROR_ACCESS_DENIED`. Use `SecurityImpersonation` (level `2`) for all local work.
5. **Not restoring the thread token after operations** — leaving `KTHREAD.ImpersonationInfo` set to a SYSTEM token past the operation window is the highest-confidence host-IDS tell. Pair every `SetThreadToken` with a `RevertToSelf()` (or `SetThreadToken(NULL, NULL)`) at the end of the privileged operation, ideally in a `Drop` guard.
6. **Buffer too small on `GetTokenInformation`** — calling with a stack-allocated 512-byte buffer for `TokenGroups` on a token in 30+ group SIDs (typical for an enterprise admin) returns `ERROR_INSUFFICIENT_BUFFER`; the call must be retried with `cbNeeded` bytes. Use `LocalAlloc` on the second call and free after parsing — the SID pointers in the returned `TOKEN_GROUPS` point into the same buffer, so do not free before parsing.
7. **Opening `lsass.exe` when `services.exe` would do** — `lsass.exe` is a Protected Process Light (`PsProtectedSigner-Lsa`); `OpenProcess` on it returns `ERROR_ACCESS_DENIED` even with `SeDebugPrivilege` unless the caller is also PPL-signed (which no red-team tool is). `services.exe`, `wininit.exe`, and unguarded service hosts (`svchost.exe -k netsvcs`) are the correct theft targets.
8. **WOW64 pointer-width mismatch** — a 32-bit Rust process calling `GetTokenInformation(TokenUser)` on a 64-bit Windows token gets 4-byte `PSID` pointers in the returned struct. If the operator casts the buffer to `TOKEN_USER64`, parsing is wrong by offset 4. Always use the architecture-matched structure or parse via byte offsets against `sizeof(PVOID)` of the calling process.

## Composition with Other Techniques

A representative single-host SYSTEM chain operates as follows:

1. **Initial access**: medium-IL user shell on a host where the user is in the local Administrators group (UAC active, so the user's process token does not carry `SeDebugPrivilege`).
2. **Bypass UAC** via an auto-elevated COM hijack or `ICMLocalUtilManageList::CreateManagedApp` (use a UAC-bypass card) — produces an elevated `cmd.exe` with the full token including `SeDebugPrivilege` (disabled but present).
3. **Enable `SeDebugPrivilege`** via `AdjustTokenPrivileges` on the elevated process's own token — `SE_PRIVILEGE_ENABLED` bit set on luid `20`.
4. **This card, Variant 2**: `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, services.exe_pid)` → `OpenProcessToken(TOKEN_DUPLICATE | TOKEN_QUERY)` → `DuplicateTokenEx(SecurityImpersonation, TokenImpersonation)` → `SetThreadToken(NULL, hDup)`. Thread is now impersonating `NT AUTHORITY\SYSTEM`.
5. **T-017 (privesc persistence)**: while impersonating SYSTEM, write a service binary via `CreateServiceW` to `%SystemRoot%\system32\drivers\svc_helper.sys` (or a scheduled task via `NetScheduleJobAdd` / `ITaskScheduler` COM interface) that runs at boot — the create-on-behalf-of-SYSTEM bypasses the "must be admin" check that a normal user-mode attempt would hit.
6. **T-015 (token impersonation chains)**: if persistence is not the goal but cross-host movement is, use the impersonated SYSTEM token to bind to `cifs` on a remote host via `WNetAddConnection2` or `RpcBindingSetAuthInfoEx` — the SMB/RPC client picks up the thread's impersonation token automatically and authenticates as the SYSTEM account of the remote host (which on a domain-joined box is the domain `SYSTEM$` / machine account).
7. **Cleanup**: `RevertToSelf()` to clear the thread's impersonation context, `CloseHandle` on both duplicated and original token handles, `CloseHandle` on the process handle. Failure to do all three leaves persistent handle-table entries that forensics tools flag.

The whole chain from step 2 to step 7 takes ~30 lines of Rust; the detection surface, if ETW-TI is not present (the common case for non-Defender-ATP hosts), is essentially the Sysmon `EventID 10` for the `services.exe` open and `EventID 1` for the spawned child if Variant 3 was used. Neither is high-confidence without the token-side ETW event.

## Related Techniques

- **T-015 Token Impersonation Chains** — extends the single-hop theft documented here into multi-hop delegation across RPC pipes; this card is the prerequisite first hop of any T-015 chain.
- **T-017 Privilege Escalation Persistence** — consumes the SYSTEM impersonation context produced by this card to write boot-surviving services or scheduled tasks that would otherwise require group-membership in the local Administrators group.

- **NtSetInformationProcess(ProcessAccessToken)** — the direct-syscall path for Variant 3, Path B; bypasses `advapi32` IAT hooks and is the kernel-level enforcement surface for in-place primary token swap.
