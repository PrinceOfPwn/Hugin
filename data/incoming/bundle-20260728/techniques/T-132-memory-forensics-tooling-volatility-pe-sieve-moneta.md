# Memory Forensics Tooling (Volatility, PE-sieve, Moneta) — The Residual Detection Surface After EDR Evasion

## Summary

Memory forensics tooling — Volatility, PE-sieve (hasherezade), and Moneta — is the residual detection layer that catches an operator *after* the EDR's runtime hooks, the `EtwThreatIntProv` provider, and the `PsSetCreateProcessNotifyRoutineEx` / `ObRegisterCallbacks` callback surface have been silenced. Unlike EDR products that observe live via `ETWThreatIntProv` registration or `MiSystemCall` instrumentation, these tools operate either on (a) a raw physical-memory dump acquired out-of-band (`winpmem`, hypervisor snapshot, `LiveKD`), or (b) a live `NtReadVirtualMemory` sweep of every loaded image in every process. PE-sieve walks each process's `PEB.Ldr.InLoadOrderModuleList`, reads the in-memory `IMAGE_NT_HEADERS64` for every module, reads the on-disk `.text` bytes via `CreateFileW` + `ReadFile` from `SetFilePointer(PointerToRawData)`, and XORs them against the in-memory `.text` bytes (`NtReadVirtualMemory(proc, DllBase + section.VirtualAddress, ...)`) — any divergence flags a hollowed, scraped, or post-load patched image. Volatility parses the kernel's `_EPROCESS` list from a captured dump, walks each process's `VadRoot` (`_RTL_AVL_TREE` of `_MMVAD_SHORT` / `_MMVAD_LONG` nodes), and reconstructs module lists from `PEB.Ldr.InMemoryOrderModuleList` plus `PEB.ImageBaseAddress`; its `malfind`, `hollowfind`, and `ldrmodules` plugins surface executable pages that lack section-object backing. Moneta performs a live `NtQueryVirtualMemory(MemoryBasicInformation)` enumeration of every process's VA space, flags committed regions whose `Type == MEM_PRIVATE` (0x20000) with execute protection, and reports the canonical write-then-flip footprint — `AllocationProtect == PAGE_READWRITE` (0x04) followed by `Protect == PAGE_EXECUTE_READ` (0x20). The vault's T-016 (ETW-TI evasion), T-013 (kernel callback bypass), and T-007 (user-mode hook evasion) document how to defeat the *runtime* monitoring layer; this card documents the layer that catches the operator when a memory image is taken minutes-to-hours later. It is unusual in the vault: a defender-tooling survey written for the operator, so that every artifact each tool keys on is also a roadmap of what to erase or camouflaged.

## Mechanism

### Variant 1: PE-sieve — Live In-Memory vs On-Disk `.text` Diff

1. PE-sieve enumerates processes via `EnumProcesses` or `NtQuerySystemInformation(SystemProcessInformation, class 0x05)`.
2. For each PID, it opens the target with `OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ, FALSE, pid)`. `PROCESS_VM_READ = 0x0010`. Against an elevated target in another session this requires `SeDebugPrivilege` (LUID `20`); without it the open returns `ERROR_ACCESS_DENIED`.
3. It locates the PEB via `NtQueryInformationProcess(ProcessHandle, ProcessBasicInformation, &pbi, sizeof(pbi), NULL)` — `pbi.PebBaseAddress` is the 64-bit PEB VA. On WoW64 targets it queries `ProcessWow64Information` (class `26`) to fetch the 32-bit PEB; PE-sieve scans *both* PEBs to catch 32-bit reflectively-loaded DLLs.
4. `NtReadVirtualMemory(proc, pbi.PebBaseAddress + 0x18, &ldr, sizeof(ldr))` reads `PEB.Ldr` (offset `0x18` on x64). Then `NtReadVirtualMemory(proc, ldr + 0x10, &flink, sizeof(flink))` reads `PEB_LDR_DATA.InLoadOrderModuleList.Flink`.
5. It walks the doubly-linked list via `CONTAINING_RECORD(flink, LDR_DATA_TABLE_ENTRY, InLoadOrderLinks)`. Each entry exposes `DllBase` (entry offset `0x30` on x64), `FullDllName` (UNICODE_STRING at offset `0x80`), and `BaseDllName` (offset `0x90`).
6. For each module, it reads the in-memory PE headers: `NtReadVirtualMemory(proc, DllBase, header_buf, 0x400, &ret)`. It parses `IMAGE_DOS_HEADER.e_lfanew` (offset `0x3C`) to locate `IMAGE_NT_HEADERS64`, verifies the `0x00004550` ("PE\0\0") signature, then walks `IMAGE_FILE_HEADER` (20 bytes) + `IMAGE_OPTIONAL_HEADER` (240 bytes for PE32+) + the `IMAGE_SECTION_HEADER[]` array immediately following.
7. For each section flagged `IMAGE_SCN_MEM_EXECUTE` (0x20000000) — typically `.text` — it reads the in-memory bytes: `NtReadVirtualMemory(proc, DllBase + section.VirtualAddress, in_mem_buf, section.Misc.VirtualSize, &ret)`. **Note: in-memory reads use `VirtualAddress` (RVA), not `PointerToRawData`.**
8. In parallel it opens the on-disk file via `CreateFileW(FullDllName.Buffer, GENERIC_READ, FILE_SHARE_READ | FILE_SHARE_DELETE, NULL, OPEN_EXISTING, 0, NULL)`. `SetFilePointerEx(file, section.PointerToRawData, ...)`. `ReadFile(file, on_disk_buf, section.SizeOfRawData, &bytesRead, NULL)`. **Note: on-disk reads use `PointerToRawData` (file offset) and `SizeOfRawData`.**
9. It compares the two buffers byte-by-byte. Divergence produces one of three tags: `WITHOUT_HEADER` (file not found on disk — manually mapped), `UNMAPPED` (no VAD section backing), or `IMP/HOLLOWED` (headers match but `.text` diverges — post-load patching, IAT rewrite, or `.text`-section replacement).
10. For modules in the loader list that have no on-disk counterpart (reflectively loaded DLLs), PE-sieve classifies as `UNMAPPED` — these survive only as in-memory artifacts.
11. With `/imp` or `/dump` flags, PE-sieve dumps the diverging in-memory region to disk as a `.exe`/`.dll`/`.shc` for analyst triage. The dump itself is an artifact on the defender's host, not the operator's.

### Variant 2: Volatility — Offline Full-Memory Dump Analysis

1. Volatility operates on a raw physical-memory image acquired out-of-band via `winpmem`, `LiveKD`, hypervisor snapshot, or `C:\Windows\MEMORY.DMP` (Kernel / Complete dump). The tool never touches the live system.
2. It locates the kernel base by scanning the captured physical space for the Windows kernel PE header signature, then walks `PsActiveProcessHead` (a global in `nt!PsActiveProcessHead` pointing at the first `_EPROCESS.ActiveProcessLinks.Flink`) to enumerate every `_EPROCESS`.
3. For each `_EPROCESS`, Volatility extracts fields by build-specific profile offsets (Windows 10 x64 representative values): `DirectoryTableBase` (~`0x28` — the process's `CR3`), `UniqueProcessId` (~`0x440`), `ImageFileName` (~`0x450`, 15-char `char[15]` truncated basename), `Peb` (~`0x550`, pointer to user-mode `_PEB`), `InheritedFromUniqueProcessId` (~`0x540`), `VadRoot` (~`0x7D8`, `_RTL_AVL_TREE` of VAD nodes), `ActiveProcessLinks` (intrusive list entry), `ObjectTable` (HANDLE_TABLE pointer).
4. To translate user-mode VAs in the dump, Volatility reads the captured page tables. With `CR3` from `DirectoryTableBase`, it walks PML4 → PDPT → PD → PT: for a 48-bit VA, it indexes each level by 9 bits × 8 bytes per entry. At each level, the entry's `PageFrameNumber` (bits 12-51) × 0x1000 gives the next table's physical address in the dump. The final PTE's PFN × 0x1000 + the page offset yields the physical byte offset to read.
5. The `malfind` plugin walks the VAD tree. Each node is `_MMVAD_SHORT` or `_MMVAD_LONG`, discriminated by `u.VadFlags.ShortFlag` (offset ~`0x28` on Win10 x64; `1`=short, `0`=long). For each node, `u.VadFlags.Protection` encodes the granted page protection. Values for execute protections: `PAGE_EXECUTE` (`0x10`), `PAGE_EXECUTE_READ` (`0x20`), `PAGE_EXECUTE_READWRITE` (`0x40`), `PAGE_EXECUTE_WRITECOPY` (`0x80`). Any executable VAD whose `Subsection` chain (in the long form) does not link back to a `_CONTROL_AREA` whose `_FILE_OBJECT` is in the loaded-module list is flagged as a potential injection.
6. `ldrmodules` correlates three loader lists — `PEB.Ldr.InLoadOrderModuleList` (PEB_LDR_DATA offset `0x10`), `InMemoryOrderModuleList` (`0x20`), `InInitializationOrderModuleList` (`0x30`) — against the VAD's section-backed image entries. A module present in the VAD's section objects (i.e., mapped via `NtMapViewOfSection` with `SEC_IMAGE`) but absent from all three loader lists is a manually-mapped / reflective DLL.
7. The `hollowfind` plugin performs the same in-memory `.text` vs on-disk byte-diff primitive as PE-sieve, but on captured dump bytes. It surfaces `CreateProcess` hollowing — where, for example, `svchost.exe`'s in-memory image base in process N's address space has been unmapped and replaced with a different binary's bytes while keeping the original image path.
8. Volatility also runs `pslist` (linear walk of `ActiveProcessLinks`), `pstree` (parent-child via `InheritedFromUniqueProcessId`), `cmdline` (reads `PEB.ProcessParameters.Buffer` and `.CommandLine`), `netscan` (walks pool tags `TcpE` / `UdpA` for `_LOCAL_ENDPOINT_INFO`), `handles` (walks `_EPROCESS.ObjectTable` HANDLE_TABLE entries, decoding object types via `ObpObjectTypes`), and `malfind` (VAD scan).
9. Because Volatility reads from a snapshot, the operator cannot defeat it by terminating threads, restoring hooks, or unmapping payload *after* the dump is taken — the dump is frozen at capture time T. The only defenses are (a) keep payload encrypted-at-rest at time T (T-020 sleep obfuscation), or (b) ensure the payload's memory layout at T is indistinguishable from a legitimate image (T-005 process hollowing with byte-perfect image replacement).

### Variant 3: Moneta — Live Unbacked Executable Memory Scan

1. Moneta enumerates processes with the same `NtQuerySystemInformation(SystemProcessInformation)` pattern as PE-sieve.
2. For each PID, it opens with `OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ, ...)`. For elevated targets, `SeDebugPrivilege` is required.
3. It walks the target's VA space by repeatedly calling `NtQueryVirtualMemory(proc, base, MemoryBasicInformation (class 0), &mbi, sizeof(mbi), NULL)`. Each call returns `MEMORY_BASIC_INFORMATION{ BaseAddress, AllocationBase, AllocationProtect, RegionSize, State, Protect, Type }`. After each call, `base += mbi.RegionSize` until `base > MM_HIGHEST_USER_ADDRESS` (`0x7FFFFFFEFFFF` on x64).
4. For each committed region (`State == MEM_COMMIT` `0x1000`), Moneta inspects `AllocationProtect` (the protection the region was *created* with — survives subsequent `VirtualProtect` calls) and `Protect` (the *current* protection). The shellcode-staging pattern is `AllocationProtect == PAGE_READWRITE (0x04)` or `PAGE_EXECUTE_READWRITE (0x40)` and `Protect == PAGE_EXECUTE_READ (0x20)` — the operator `VirtualAlloc`'d writable, wrote payload, then flipped to RX.
5. Moneta resolves backing by inspecting `MEMORY_BASIC_INFORMATION.Type`: `MEM_IMAGE` (`0x1000000`) is a section backed by a file or pagefile; `MEM_MAPPED` (`0x40000`) is a data section; `MEM_PRIVATE` (`0x20000`) is private commit with no `_CONTROL_AREA`. Any `MEM_PRIVATE` region with execute protection is highly suspicious — the canonical shellcode footprint.
6. For `MEM_IMAGE` regions, Moneta reads the in-memory PE headers (`NtReadVirtualMemory`) and resolves the on-disk file via the VAD's `_CONTROL_AREA._FILE_OBJECT.Filename`. If the file has been deleted or renamed, the region is flagged as orphaned.
7. Moneta reports a structured table: PID, base VA, size, allocation protect, current protect, type (private/mapped/image), backing path or `[unbacked]`. The output is post-processed by the defender into a triage queue.

## OS Internals Context

The VAD (`_MMVAD` family) is the kernel's per-process accounting of every committed VA range. Each process has a single `EPROCESS.VadRoot` (`_RTL_AVL_TREE`) of `_MMVAD_SHORT` and `_MMVAD_LONG` nodes. The node is keyed by `StartingVpn` (virtual page number — multiply by `0x1000` for the byte address); `EndingVpn` bounds the range. The discriminating field is `u.VadFlags.ShortFlag`: `1` for short, `0` for long. The short variant tracks only the range, protection, and commit state. The long variant additionally carries `Subsection` (a pointer to the first `_SUBSECTION` for image/file-backed regions), `FirstPrototypePte` (pointer into the prototype PTE array), and `LastContiguousPte`. When PE-sieve reads a region via `NtReadVirtualMemory`, the memory manager traverses the VAD, finds the controlling node, and either (a) for `MEM_PRIVATE` pages, reads the PFN directly from the hardware PTE (`_MMPTE_HARDWARE`); or (b) for `MEM_IMAGE` pages, follows the prototype PTE chain (`_MMPTE_SOFTWARE.Valid == 0`, `PrototypePointer` set) to the underlying `_SUBSECTION` → `_CONTROL_AREA` → `_FILE_OBJECT` backing store, faults the page in via `MiDispatchFault` if necessary, and returns the bytes.

The `_CONTROL_AREA` is the glue between a section object (created by `NtCreateSection` with `SEC_IMAGE = 0x01000000` or `SEC_COMMIT = 0x8000000`) and the on-disk file. It holds `Segment` (`_SEGMENT` pointer), `u.Flags.FileBased` / `.Image`, `NumberOfSectionReferences`, `NumberOfUserReferences`, and a doubly-linked list of `_SUBSECTION` structures. Each subsection corresponds to a contiguous run of prototype PTEs and stores `PtesInSubsection`, `SubsectionBase` (pointer to the first `_MMPTE` in the subsection's prototype array), `StartingSectorNumber`, and `FullFlink`/`FullBlink` for the loaded-list linkage. When `NtReadVirtualMemory` reads a `MEM_IMAGE` page, the kernel finds the prototype PTE for the VA, reads the PFN from it (or faults the page from disk via `MiDispatchFault` → `MiPurgeImageSection` / `MiCopyOnWrite` paths), and returns the bytes. The `_FILE_OBJECT.Filename` (a UNICODE_STRING inside the file object) is what Volatility's `ldrmodules` and Moneta use to attribute a section-backed region to an on-disk file.

The PTE layer carries the protection bits that EDRs and forensic tools actually read. A valid hardware PTE on x64 is 8 bytes, decoded as `_MMPTE_HARDWARE` with bitfields: `Valid` (bit 0), `Write` (bit 1), `Owner` (bit 2, user vs supervisor), `WriteThrough` (bit 3), `CacheDisable` (bit 4), `Accessed` (bit 5), `Dirty` (bit 6), `LargePage` (bit 7), `Global` (bit 8), `CopyOnWrite` (bit 9, software-emulated on x64), `PageFrameNumber` (bits 12-51), `NX` (bit 63, No-Execute). The VAD's `Protection` field is the *granted* protection; the hardware PTE reflects the *materialized* protection after any copy-on-write split. **The NX bit (63) is what actually enforces non-executable pages on x64** — the VAD protection is accounting; the PTE NX is enforcement. Forensic tools read the VAD because it is a stable record (the VAD node survives PTE invalidation, paging-out, and TLB flushes), whereas PTEs are mutable to the running system. When an operator patches a `.text` byte of a loaded image via `VirtualProtect` → write → `VirtualProtect` restore, the kernel splits the page: it allocates a new PFN, copies the original page bytes, applies the patch to the new page, and rewrites the hardware PTE's `PageFrameNumber` field while clearing `CopyOnWrite` and setting `Dirty`. The original PFN (shared across all processes that loaded that image at the same RVA) is unchanged. **This COW split is the artifact PE-sieve detects by comparing in-memory bytes to on-disk bytes** — the in-memory read returns the patched page, the on-disk read returns the original shared page.

For `MEM_PRIVATE` regions (`PAGE_READWRITE` or `PAGE_EXECUTE_READWRITE` allocated via `NtAllocateVirtualMemory`), there is no `_CONTROL_AREA` backing. The VAD node is a `_MMVAD_SHORT` with `Subsection == NULL`. The hardware PTE points to a PFN whose entry in `MmPfnDatabase` (`_MMPFN` array indexed by PFN) has `u3.e1.PrototypePte == 0` and `u4.PageFileAllocation == 0` (no pagefile backing either — pure RAM-resident private pages). Moneta keys off exactly this: a committed region with execute protection whose VAD node has `Subsection == NULL` is unbacked executable memory — the canonical shellcode footprint. The same detection is performed by Volatility's `malfind` plugin against the dump, except Volatility reads the VAD from the captured `_EPROCESS` rather than calling `NtQueryVirtualMemory`.

The loader side: when `LdrpInitializeProcess` (in `ntdll.dll`, the user-mode phase of process creation) walks the import table and maps each imported DLL via `LdrpMapDllNtFileName`, it calls `NtCreateSection(SEC_IMAGE = 0x01000000)` then `NtMapViewOfSection`. The kernel inserts a long-form `_MMVAD_LONG` node with `Subsection` pointing at the new `_CONTROL_AREA`, and `ntdll!LdrpInsertDataTableEntry` links a `_LDR_DATA_TABLE_ENTRY` into all three loader lists (`InLoadOrderModuleList`, `InMemoryOrderModuleList`, `InInitializationOrderModuleList`). A reflectively-loaded DLL (manual `NtCreateSection`/`NtMapViewOfSection` from user code, or a hand-rolled `memcpy`-then-fixup loader) creates the `_MMVAD_LONG` node and `_CONTROL_AREA` but does *not* insert into the loader lists — Volatility's `ldrmodules` plugin catches exactly this asymmetry. Conversely, an operator who only `VirtualAlloc`s + `memcpy`s shellcode creates a `_MMVAD_SHORT` node (no `Subsection`) — caught by `malfind` and Moneta. A third pattern — `NtCreateSection(SEC_IMAGE)` + `NtMapViewOfSection` + manual `LdrpInsertDataTableEntry`-equivalent linkage into all three lists — produces a VAD node that looks like a legitimately loaded DLL at the VAD level, but is still caught by PE-sieve's `.text` diff if the bytes were modified post-load.

Volatility's offline analysis bypasses user-mode entirely. It reads `_EPROCESS.DirectoryTableBase` (the process's `CR3`) — a physical address pointing at the process's PML4 table. It then walks the captured physical memory dump as a flat file: a 48-bit VA is split as `PML4_INDEX[47:39] × 8` into the PML4 table, the entry's PFN gives the next table (PDPT), `PDPT_INDEX[38:30] × 8` indexes it, then `PD_INDEX[29:21] × 8` into the PD, then `PT_INDEX[20:12] × 8` into the PT, and the final PTE's PFN × 0x1000 + the 12-bit page offset yields the physical byte offset to read in the dump. This is why a *physical* memory dump is required — `winpmem` captures physical RAM, not virtual memory, and Volatility reconstructs virtual addressability per-process. A `process memory` Volatility dump (the `.dmp` format produced by `procdump -ma` or Process Explorer) contains only the process's committed VA space, skips the CR3 walk, but is only useful for that single process.

The `Peb` field (`_EPROCESS.Peb` at offset ~`0x550` on Windows 10 x64) is the user-mode PEB VA — Volatility reads it by walking the page tables under that process's `CR3`. From there `PEB.ImageBaseAddress` (offset `0x10` on x64) gives the image base of the main executable, and `PEB.Ldr` (offset `0x18`) points to the `_PEB_LDR_DATA` whose first three list-head fields are `InLoadOrderModuleList` (offset `0x10` in `_PEB_LDR_DATA`), `InMemoryOrderModuleList` (offset `0x20`), and `InInitializationOrderModuleList` (offset `0x30`). Walking these from a snapshot gives the same module list PE-sieve reads live — the loader entries persist in memory until `LdrUnloadDll` runs and unlinks the node, and even then the VAD node may persist briefly before `VadFreeRoot` reclaims it.

## Key Implementation Details

Privilege prerequisites are uniform across the three tools. PE-sieve and Moneta both require `SeDebugPrivilege` (LUID `20`) to open elevated or cross-session targets with `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` (`0x0400 | 0x0010 = 0x0410`). Volatility has no privilege requirement on the analysis host (it operates on a captured file), but the *acquisition* step (`winpmem` driver load, `LiveKD` kernel-mode access, or a hypervisor snapshot) requires `SeLoadDriverPrivilege` or kernel / hypervisor privilege. On systems protected by PPL (Protected Process Light) — typically with a WER-protected binary such as `MsMpEng.exe` (Defender) or the LSASS process when `RunAsPPL=1` is set in the `HKLM\SYSTEM\CurrentControlSet\Control\Lsa` registry key — `OpenProcess` returns `ERROR_ACCESS_DENIED` even with `SeDebugPrivilege`, because PPL enforces a signing-level check at the kernel `PspOpenProcess` path (signature level `PsProtectedSignerAuthenticode-Lite` or higher). PE-sieve cannot scan PPL-protected processes via `NtReadVirtualMemory`. Volatility *can* — the captured dump contains the PPL process's `_EPROCESS` and VAD tree as raw bytes, and the page tables resolve regardless of PPL.

The WoW64 boundary is the second-most-common tripping point. On x64 Windows running a 32-bit process, there are *two* PEBs: the 64-bit PEB at `EPROCESS.Peb` (offset ~`0x550`) and the 32-bit PEB at `EPROCESS.Wow64Process` → `EWOW64PROCESS.ProcessPeb` (a 32-bit VA reachable via the 32-bit page tables, which use a *different* CR3 — `EWOW64PROCESS.ProcessPeb` actually points into the 32-bit address space below `0x7FFE0000`). The 64-bit PEB's `Ldr` list contains the 64-bit DLLs (`ntdll.dll`, `kernel32.dll`, etc.); the 32-bit PEB's `Ldr` list (at 32-bit PEB offset `0x0C`) contains the 32-bit DLLs (`ntdll.dll` 32-bit, `kernel32.dll` 32-bit, `wow64.dll`, etc.). PE-sieve scans both; an operator who reflectively loads a 32-bit payload into a 32-bit process and assumes PE-sieve only checks the 64-bit PEB will be caught — PE-sieve queries `ProcessWow64Information` (info class `26`) and recursively scans the 32-bit module list.

Dump timing is the operator's primary defense surface against Volatility. The snapshot is frozen at time T. If the payload is in an encrypted-at-rest state at T — i.e., the operator is in a sleep cycle (T-020 sleep obfuscation: the working set is paged or XOR'd with a key, the executable region transitions to `PAGE_NOACCESS` or `PAGE_READWRITE` non-executable), the VAD node's `Protection` may still record `PAGE_EXECUTE_READWRITE` — `malfind` flags it — but the bytes themselves are ciphertext, defeating `hollowfind`'s `.text` diff and the analyst's manual review. If the operator has *unmapped* the payload entirely (called `VirtualFree` with `MEM_RELEASE`) before T, the VAD node is gone — but the physical pages may persist in the pagefile or in freed-pool regions recoverable by Volatility's `pagefiles` / `pool scanner` plugins. The operator must `VirtualFree` with `MEM_RELEASE` *and* overwrite the freed pages with zeroes before T, or rely on a sleep cycle that wipes the executable region.

## Why It Matters

This card fills the gap left by the vault's runtime-evasion cards (T-016 ETW-TI, T-013 kernel callbacks, T-007 user-mode hooks, T-008 indirect syscalls). Those cards document how to defeat the *live* monitoring layer — the EDR's hooks, the threat-intelligence ETW provider, the `PsSetCreateProcessNotifyRoutineEx` / `ObRegisterCallbacks` callback surface. They leave the post-capture forensic layer untouched. An operator who silences the EDR at runtime is *still* caught if a memory image is taken minutes-to-hours later — and on a mature incident-response engagement, that image will be taken. `winpmem` is a 1.5 MB executable that runs in seconds; Velociraptor / KAPE / `Get-ForensicVolatility` automate acquisition across hundreds of hosts; EDRs increasingly schedule periodic memory captures on suspicious processes. The operator who survives only the runtime layer is the operator who is caught at the forensic layer.

The card's value is bidirectional. For the operator, it is a roadmap of what each tool keys on — every artifact documented above is also a target to erase or camouflage. For the detection engineer reading the vault out-of-band, it documents the residual detection surface that survives even a perfect runtime evasion. The composition with T-020 (sleep obfuscation) is load-bearing: the only reliable defense against a Volatility capture is to ensure the payload is in an encrypted-at-rest state at the moment of capture, which requires careful coordination with the sleep cycle. T-005 (process hollowing) composes directly with this card's threat model — PE-sieve's `.text` diff is the canonical detector for hollowed processes, and surviving it requires either a byte-perfect image replacement (preserve the original `.text` bytes, modify only `.data` and IAT) or a payload that lives entirely in `MEM_PRIVATE` non-executable memory (which Moneta then catches).

## Detection Considerations

- **Telemetry sources**: PE-sieve keys on `NtReadVirtualMemory` reads of in-memory `.text` sections XORed against on-disk file bytes, and on PEB `Ldr` list membership vs VAD section-backed regions. Volatility keys on `_EPROCESS.VadRoot` walks in captured physical memory, `_MMVAD_LONG.Subsection` → `_CONTROL_AREA` → `_FILE_OBJECT` chain resolution, and PEB `Ldr` list cross-correlation (`malfind`, `hollowfind`, `ldrmodules` plugins). Moneta keys on `NtQueryVirtualMemory(MemoryBasicInformation)` walks flagging `Type == MEM_PRIVATE` with execute protection and `AllocationProtect != Protect` (write-then-flip pattern). EDRs that incorporate forensic sweeps (Elastic Endpoint's `memory_thread` scanner, Microsoft Defender's `MsMpEng.exe` periodic `MEM_IMAGE`-vs-file diff) reuse the same primitives.
- **Bypass options**: Against PE-sieve, preserve the on-disk `.text` bytes in memory (data-only persistence: stage the payload as `.data`-section modifications, IAT rewrites via RWX `.data`, or post-`NtProtectVirtualMemory` writes that are restored before the scan). Against Volatility, ensure the payload is in encrypted-at-rest state at the moment of capture (T-020 sleep obfuscation: XOR the executable region with a key, transition the VAD protection to `PAGE_NOACCESS`, or unmap the section entirely). Against Moneta, avoid `MEM_PRIVATE` executable allocations entirely — back the payload with a `NtCreateSection(SEC_IMAGE)` mapping of a legitimate-looking file, and use `NtAllocateVirtualMemory` with `PAGE_EXECUTE_READ` as the *initial* protection (the `AllocationProtect` then records `RX`, not `RW`), writing via `NtWriteVirtualMemory` (which internally does `VirtualProtect(RW)` → write → restore, leaving no allocation-protect footprint of the write window).
- **Residual artifacts**: After a clean execution that defeats all three tools, residual artifacts include: (a) the section-object's `_CONTROL_AREA._FILE_OBJECT` for any file-backed mapping — the file must exist on disk at the moment of Volatility capture, which means the operator must drop a decoy file (which itself becomes a disk artifact); (b) the `_EPROCESS.ObjectTable` HANDLE_TABLE entries for any `NtCreateSection` / `NtMapViewOfSection` handles — these persist until the operator closes the handles, and Volatility's `handles` plugin decodes them by object type; (c) the working-set / standby list pages backing the payload — even after `VirtualFree(MEM_RELEASE)`, the physical pages may persist in `MmPfnDatabase` as standby pages until reclaimed, recoverable by Volatility's `poolscanner` / `pagefiles` plugins; (d) the `PEB.Ldr` loader list entries if the operator inserted the payload into the lists — these persist until `LdrUnloadDll` unlinks the entry; (e) the VAD node itself — `VadFreeRoot` does not immediately erase the node struct, which sits in pool memory recoverable by `poolscanner`.

## Detection Evasion Ladder

Strategies in increasing sophistication, each defeating the previous tier's detector:

1. **VirtualAlloc(RWX) + memcpy + execute** — caught by Moneta's `AllocationProtect == RWX` record and by Volatility `malfind` (unbacked executable).
2. **VirtualAlloc(RW) + write + VirtualProtect(RX)** — defeats the RWX-`AllocationProtect` heuristic, but Moneta still sees `AllocationProtect == RW` and `Protect == RX` (write-then-flip).
3. **NtAllocateVirtualMemory(RX) initial + NtWriteVirtualMemory write** — `NtWriteVirtualMemory` internally flips to RW then restores, so `AllocationProtect == RX`. Moneta still flags `MEM_PRIVATE` executable as unbacked.
4. **NtCreateSection(SEC_COMMIT) + NtMapViewOfSection(PAGE_EXECUTE_READ)** — section-backed, so `MEM_MAPPED` not `MEM_PRIVATE`. Moneta no longer flags unbacked. Volatility `ldrmodules` catches the loader-list mismatch (the section is mapped but no `_LDR_DATA_TABLE_ENTRY` exists).
5. **Reflective DLL injection with manual `LdrpInsertDataTableEntry` into all three loader lists** — defeats `ldrmodules` (loader lists now match the VAD). PE-sieve catches if `.text` was modified post-load.
6. **Process hollowing with byte-perfect image replacement** (T-005) — preserves the original `.text` bytes, defeats PE-sieve's diff. Only `.data` and IAT are modified; payload code lives in `.data`-section stubs executed via `.data`-section allocation that is also file-backed. Survives PE-sieve.
7. **Data-only persistence in a legitimately loaded system DLL's `.data` section** (modify only `.data` bytes via `VirtualProtect(RW)` → write → `VirtualProtect(R)`) — the `.text` bytes are pristine, the modification is in `.data` which PE-sieve may or may not diff depending on `/imp` flags. The COW-split PFN still betrays the modification to a Volatility `malfind`-style page-diff, but no plugin currently automates this. **The current ceiling.**

## Composition with Other Techniques

A realistic kill chain that defeats all three forensic tools requires layering five vault techniques. Assume a target running Defender for Endpoint (MDE) with `RunAsPPL=1`:

1. **T-007 (EDR user-mode hook evasion)** — unhook or use direct syscalls to bypass MDE's `ntdll!Nt*` user-mode hooks. This silences the runtime layer but leaves in-memory artifacts: the patched `.text` bytes of `ntdll.dll` are exactly what PE-sieve's `.text` diff catches. Counter-composition: use T-008 (indirect syscalls) instead, which leaves no `ntdll` `.text` patch.
2. **T-013 (kernel callback evasion) + T-016 (ETW-TI bypass)** — silence `PsSetCreateProcessNotifyRoutineEx` (so the hollowing's process-create callback doesn't fire) and disable the `EtwThreatIntProv` provider (so `NtCreateSection` / `NtMapViewOfSection` / `VirtualProtect` events aren't logged). The runtime layer is now fully silenced, but the memory layout is unchanged.
3. **T-005 (process hollowing)** — replace a sacrificial `svchost.exe`'s image with the payload binary. To survive PE-sieve: byte-perfect image replacement (preserve the original `.text` section, place payload in a custom `.data`-section stub). To survive Volatility `ldrmodules`: the hollowed image is `svchost.exe`, which is legitimately in all three loader lists.
4. **T-020 (sleep obfuscation)** — during sleep cycles, encrypt the payload's executable region with a key derived from the system timer, transition the VAD protection to `PAGE_NOACCESS`, or unmap the section entirely. If the IR team captures memory during a sleep cycle, the bytes are ciphertext and `hollowfind`'s `.text` diff fails. The VAD node still exists but its protection is no longer execute — `malfind` no longer flags it.
5. **(This card) Memory forensics awareness** — throughout the engagement, periodically run the same primitives PE-sieve uses (`NtReadVirtualMemory` on `ntdll.dll`'s `.text` and compare against the on-disk file) to verify the operator's own `ntdll` is pristine; if any hook has been re-applied by MDE's integrity check, the operator sees it before the defender does.

Expected artifacts at end-of-engagement: a hollowed `svchost.exe` with byte-perfect `.text`, a payload living in `.data`-section modifications, a sleep cycle that XORs the executable region every 60 seconds, and a fully silenced runtime layer. The residual artifacts that survive even this chain are: the section-object's `_CONTROL_AREA` for the hollowed `svchost.exe` (pointing at the original file on disk — pristine), the `_EPROCESS.ObjectTable` handle entries (close them with `NtClose` before exiting), and the physical pages in `MmPfnDatabase` if the operator's payload was ever paged to the pagefile (use `VirtualLock` to keep it resident, then overwrite before exit).

## Common Mistakes

1. **VirtualAlloc(RWX) then VirtualProtect(RX)** — the most common shellcode-staging mistake. `AllocationProtect` in the VAD *records the original protection* and survives `VirtualProtect`. Moneta and Volatility `malfind` both key on this. Use `NtAllocateVirtualMemory` with `PAGE_EXECUTE_READ` as the initial protection and write via `NtWriteVirtualMemory` (which internally does `VirtualProtect(RW)` → write → restore, leaving no `AllocationProtect` record of the write window).
2. **Reflectively loading a DLL without inserting it into the loader lists** — Volatility `ldrmodules` is specifically designed to catch this asymmetry. The VAD shows a section-backed image, but `PEB.Ldr.InLoadOrderModuleList` has no corresponding entry. Either insert the entry manually (replicating `LdrpInsertDataTableEntry`'s three-list linkage) or accept that `ldrmodules` will flag it.
3. **Patching `ntdll.dll` `.text` for unhooking** — PE-sieve's `.text` diff catches the divergence between in-memory `ntdll.dll` and the on-disk file. Either restore the original `.text` bytes from a clean copy before the capture window, or use T-008 (indirect syscalls) which leaves `ntdll` pristine.
4. **Staging payload in `MEM_PRIVATE` then executing** — Moneta flags `MEM_PRIVATE` with execute protection as the canonical shellcode footprint. Always back the payload with a `NtCreateSection(SEC_IMAGE)` mapping of a file, even a decoy file.
5. **Forgetting the WoW64 32-bit PEB** — on a 64-bit Windows host running a 32-bit payload, the 32-bit PEB (queried via `ProcessWow64Information`) has its own `Ldr` list. PE-sieve scans both; an operator who only erases 64-bit loader entries leaves the 32-bit entry for PE-sieve to find.
6. **Assuming `VirtualFree(MEM_RELEASE)` erases the page** — the VAD node is freed, but the physical page backing the payload may persist in `MmPfnDatabase` as a standby page until memory pressure forces reclamation, and the pagefile may contain a copy. `VirtualLock` the payload to keep it resident, then overwrite with zeroes before `VirtualFree`, to ensure no recoverable pagefile or standby copy survives for Volatility's `poolscanner` / `pagefiles` plugins.

## Related Techniques

- **T-007 EDR Hook Evasion** — defeats user-mode `ntdll!Nt*` hooks but leaves the patched `.text` bytes that PE-sieve's diff catches. Compose with T-008 (indirect syscalls) to avoid this residual.
- **T-013 Kernel Callback Evasion** — silences `PsSetCreateProcessNotifyRoutineEx` / `ObRegisterCallbacks` but the resulting injected page remains in the VAD for Volatility's `malfind` to find.
- **T-016 ETW-TI Bypass** — silences the `EtwThreatIntProv` provider but the memory layout is unchanged for capture-time analysis.
- **T-020 Sleep Obfuscation** — the primary defense against Volatility: encrypts the payload's executable region during sleep cycles so the captured bytes are ciphertext, defeating `hollowfind`'s `.text` diff.
- **T-005 Process Hollowing** — directly detected by PE-sieve's in-memory vs on-disk `.text` comparison. Surviving it requires byte-perfect image replacement (preserve original `.text`, modify only `.data`).
