# Windows Privilege Escalation Primitives (Admin to SYSTEM) — five canonical privilege-based paths from an Administrators-context execution to LocalSystem

## Summary

Five Windows privileges — `SeDebugPrivilege`, `SeTakeOwnershipPrivilege`, `SeCreateTokenPrivilege`, `SeTcbPrivilege`, and `SeLoadDriverPrivilege` — constitute the canonical admin-to-SYSTEM elevation primitive set used across modern Windows red-team tradecraft. Each turns a granted privilege into SYSTEM-context execution via a different mechanism. The technical anchor of this card is the `SeDebugPrivilege` chain: with `SeDebugPrivilege` enabled, an attacker calls `OpenProcess(PROCESS_ALL_ACCESS, FALSE, <winlogon.exe PID>)` on `winlogon.exe` (PID 508 typical on Win10 19041+), then `OpenProcessToken` with `TOKEN_DUPLICATE`, then `DuplicateTokenEx(..., SecurityImpersonation, TokenPrimary, ...)` to mint a primary SYSTEM token, then `CreateProcessWithTokenW` to spawn a SYSTEM child. The privilege bypass occurs in `ntoskrnl!SepAccessCheck`: when the target object type is `PsProcessType` or `PsThreadType` and the subject holds `SeDebugPrivilege` with `SE_PRIVILEGE_ENABLED (0x2)`, the DACL walk is skipped and `PROCESS_ALL_ACCESS` is granted unconditionally. The other four variants similarly convert a privilege into a token or kernel foothold: `SeTakeOwnershipPrivilege` grants `WRITE_OWNER (0x80000)` on any securable object regardless of DACL, used to take ownership of a SYSTEM service binary, rewrite the DACL, replace the binary, and restart the service; `SeCreateTokenPrivilege` calls `NtCreateToken` to mint a SYSTEM token directly with `LocalSystem (S-1-5-18)` in `TOKEN_USER.User.Sid` — no process ever touched; `SeTcbPrivilege` (largely vestigial in modern Windows) bypasses the `SeAssignPrimaryTokenPrivilege` check on `CreateProcessAsUserW`; `SeLoadDriverPrivilege` combined with `NtLoadDriver` loads a signed-but-vulnerable kernel driver (BYOVD) for arbitrary kernel R/W, after which the `EPROCESS.Token` field is swapped to System's `_TOKEN` pointer. The vault documents LSASS credential harvest (T-023) and CMSTP UAC bypass (T-021) but no card catalogues the privilege primitive family itself — this card fills that gap and is referenced by T-013, T-016, T-022, and T-023 as the canonical "how do I actually become SYSTEM after I have admin" step.

## Mechanism

Each variant is independent — pick one based on which privilege your admin-context token holds. The default built-in Administrator token carries `SeDebug`, `SeTakeOwnership`, `SeLoadDriver`, and `SeImpersonate`; `SeTcbPrivilege` is held only by SYSTEM itself; `SeCreateTokenPrivilege` is held only by SYSTEM and not present on any interactive admin token unless group policy has explicitly assigned it.

### Variant 1: SeDebugPrivilege — token theft from a SYSTEM process

1. Confirm and enable the privilege: `RtlAdjustPrivilege(SE_DEBUG_NAME /* LUID 20 */, TRUE, FALSE, &fOld)`. Returns `STATUS_SUCCESS (0)` on success. If it returns `STATUS_PRIVILEGE_NOT_HELD (0xC0000061)`, the caller is not in an Administrators-equivalent group or the token was filtered by UAC and not elevated.
2. Identify a SYSTEM-process target PID. The canonical target is `winlogon.exe` (its token is always SYSTEM and the process is always running). Alternatives: `services.exe`, `wininit.exe`, `csrss.exe` (session-bound — pick one in session 0 only for service-context work). Enumerate with `NtQuerySystemInformation(SystemProcessInformation, ...)` walking the `SYSTEM_PROCESS_INFORMATION.NextEntryOffset` chain, matching `ImageName.Buffer == L"winlogon.exe"`.
3. Open the process with full access: `hProc = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid)`. The kernel-side sequence: `NtOpenProcess` → `ObOpenObjectByPointer` → `ObpAccessCheckInt` → `SepAccessCheck`. `SepAccessCheck` special-cases `PsProcessType`: when `SubjectContext->Token->Privileges` contains LUID 20 with `SE_PRIVILEGE_ENABLED`, the function returns `STATUS_SUCCESS` for any `DesiredAccess` mask — no DACL walk, no owner check.
4. Open the target token: `OpenProcessToken(hProc, TOKEN_DUPLICATE | TOKEN_QUERY, &hTok)`. `TOKEN_DUPLICATE (0x0008)` is required so `DuplicateTokenEx` can copy the token; `TOKEN_QUERY (0x0008)` lets you inspect it.
5. Duplicate to a primary form: `DuplicateTokenEx(hTok, MAXIMUM_ALLOWED, NULL, SecurityImpersonation, TokenPrimary, &hPrimary)`. `SecurityImpersonation` (level 2 of 4) is the impersonation level of the duplicate; `TokenPrimary` requests a primary token usable with `CreateProcessAsUser`/`CreateProcessWithTokenW`. Internally this invokes `NtDuplicateToken` → `SepDuplicateToken` which allocates a new `_TOKEN` object from paged pool (`ExAllocatePoolWithTag(sizeof(TOKEN), 'kToK')`), copies the `UserSid`, `Groups`, `Privileges`, `DefaultDacl`, and `PrimaryGroup` fields, and sets `TokenType = TokenPrimary`, `ImpersonationLevel = SecurityImpersonation`.
6. Spawn the SYSTEM process: `CreateProcessWithTokenW(hPrimary, 0, NULL, L"C:\\Windows\\System32\\cmd.exe", CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT, NULL, &si, &pi)`. This RPCs into the secondary logon service (`seclogon.dll` hosted in `svchost.exe -k netsvcs`), passing the token handle. Seclogon internally calls `CreateProcessAsUserW` under its own SYSTEM context; the privilege check on the *caller* is `SeImpersonatePrivilege` (LUID 29), not `SeDebugPrivilege` directly — admin tokens hold this by default. If the caller lacks `SeImpersonatePrivilege`, `GetLastError()` returns `1314 ERROR_PRIVILEGE_NOT_HELD`.
7. Cleanup: `CloseHandle(hProc); CloseHandle(hTok); CloseHandle(hPrimary);`. The new process holds its own primary token.

### Variant 2: SeTakeOwnershipPrivilege — service binary replacement

1. Enable: `RtlAdjustPrivilege(SE_TAKE_OWNERSHIP_NAME /* LUID 9 */, TRUE, FALSE, &fOld)`.
2. Pick a SYSTEM-launched service binary on disk. Target registry: `HKLM\SYSTEM\CurrentControlSet\Services\<svc>` with `ObjectName` absent or set to `LocalSystem`. Vendor-installed service binaries off `C:\` are typical because Windows-side binaries may be protected by TrustedInstaller ACLs even after ownership change.
3. Open with `WRITE_OWNER`: `hFile = CreateFileW(L"C:\\path\\to\\target.exe", WRITE_OWNER, 0, NULL, OPEN_EXISTING, 0, NULL)`. The `WRITE_OWNER (0x80000)` right is granted regardless of DACL because `SepAccessCheck`, when the subject holds `SeTakeOwnershipPrivilege` enabled and the requested access includes `WRITE_OWNER`, short-circuits with success for the owner-write component.
4. Set self as owner: `SetSecurityInfo(hFile, SE_FILE_OBJECT, OWNER_SECURITY_INFORMATION /* 0x1 */, &sidSelf, NULL, NULL, NULL)`. Mutates the SD's `Owner` field to `sidSelf`.
5. Reopen: `hFile = CreateFileW(..., FILE_GENERIC_WRITE, ...)`. The DACL still applies but you are now the owner — owners implicitly have `READ_CONTROL` and `WRITE_DAC` rights even if the DACL doesn't grant them.
6. Add a write ACE: `SetSecurityInfo(hFile, SE_FILE_OBJECT, DACL_SECURITY_INFORMATION /* 0x4 */, NULL, NULL, newDacl, NULL)` where `newDacl` grants `FILE_GENERIC_WRITE | FILE_DELETE_CHILD` to the caller's SID.
7. Replace the binary: `CopyFileExW(L"C:\\attacker\\payload.exe", L"C:\\path\\to\\target.exe", FALSE, NULL, NULL, 0)` or `CreateFileW(GENERIC_WRITE, CREATE_ALWAYS)` + `WriteFile`.
8. Restart the service: `sc.exe stop <svc> && sc.exe start <svc>`, or programmatically via `OpenSCManager(NULL, NULL, SC_MANAGER_CONNECT)` → `OpenService(hSCM, L"<svc>", SERVICE_START | SERVICE_STOP)` → `ControlService(hSvc, SERVICE_CONTROL_STOP, &status)` → `StartService(hSvc, 0, NULL)`. The replacement binary executes as SYSTEM.

### Variant 3: SeCreateTokenPrivilege — direct token minting

1. Enable: `RtlAdjustPrivilege(SE_CREATE_TOKEN_NAME /* LUID 2 */, TRUE, FALSE, &fOld)`. Almost never held by interactive admin tokens — if your token has it, you have found an unusual configuration (custom LSA group policy, or you are already SYSTEM pivoting further).
2. Construct `TOKEN_USER` with `User.Sid = LocalSystem (S-1-5-18)`. Use `CreateWellKnownSid(WinLocalSystemSid, NULL, pSid, &cbSid)`.
3. Construct `TOKEN_GROUPS` with at least the well-known Administrators SID (`S-1-5-32-544`) and the Local System SID. Set `Attributes = SE_GROUP_ENABLED | SE_GROUP_OWNER (0x6)` on the Administrators entry so the new token treats it as an owning group.
4. Construct `TOKEN_PRIVILEGES` with every privilege you want the minted token to carry: `SeTcbPrivilege (1)`, `SeCreateTokenPrivilege (2)`, `SeAssignPrimaryTokenPrivilege (3)`, `SeDebugPrivilege (20)`, `SeImpersonatePrivilege (29)`, etc. Each entry is `LUID_AND_ATTRIBUTES` (8 bytes: 4-byte LUID + 4-byte attributes).
5. Construct `TOKEN_SOURCE` with `SourceName = "Usermint"` and `SourceIdentifier` — an LUID from `AllocateLocallyUniqueId`.
6. Call `NtCreateToken(&hTok, TOKEN_ALL_ACCESS, &oa, TokenPrimary, &user, &primary, &privs, &owner, &primaryGroup, &defaultDacl, &src)`. Internally `NtCreateToken` → `SepCreateToken` checks `SeCreateTokenPrivilege`; on absence returns `STATUS_PRIVILEGE_NOT_HELD`. With the privilege, `SepCreateToken` allocates a `_TOKEN`, populates the `UserSid`, `Groups`, `Privileges` arrays, sets `IntegrityLevel` from the highest-integrity SID in the groups, and returns a usable token handle.
7. Spawn a SYSTEM process: `CreateProcessWithTokenW(hTok, ...)` — same as Variant 1 step 6.

### Variant 4: SeTcbPrivilege — direct primary-token assignment

1. Enable: `RtlAdjustPrivilege(SE_TCB_NAME /* LUID 7 */, TRUE, FALSE, &fOld)`. `SeTcbPrivilege` is heavily vestigial in modern Windows; the only tokens that hold it by default are SYSTEM and the LSA process. On a system where you have acquired it (typically only when you are already SYSTEM and pivoting further), the privilege enables `CreateProcessAsUserW(hTok, ...)` without the `SeAssignPrimaryTokenPrivilege` requirement.
2. Obtain a SYSTEM token via any of variants 1, 3, or `NtOpenProcessToken` against `wininit.exe` (you still need `SeDebugPrivilege` to grab another process's token — `SeTcb` alone does not grant cross-process token access).
3. Call `CreateProcessAsUserW(hTok, NULL, L"C:\\Windows\\System32\\cmd.exe", NULL, NULL, FALSE, 0, NULL, NULL, &si, &pi)`. Internally `NtCreateUserProcess` checks token assignment rights; the `SeTcbPrivilege` check in the process-creation path short-circuits, allowing assignment of any primary token. Without the privilege, the call fails with `ERROR_PRIVILEGE_NOT_HELD (1314)`.
4. Alternative path: `NtCreateProcessEx` with a section handle and a token — entirely NT-level, bypasses the Win32 `CreateProcessAsUser` path entirely. Rarely used in modern tradecraft.

### Variant 5: SeLoadDriverPrivilege — BYOVD to kernel

1. Enable: `RtlAdjustPrivilege(SE_LOAD_DRIVER_NAME /* LUID 10 */, TRUE, FALSE, &fOld)`. Held by Administrators by default.
2. Stage the registry service key for the driver. Write to `HKLM\SYSTEM\CurrentControlSet\Services\<drvname>` the following values:
   - `ImagePath` (REG_EXPAND_SZ): full path to the driver file, e.g., `C:\\Windows\\Temp\\RTCore64.sys`
   - `Type` (DWORD): `1` (`SERVICE_KERNEL_DRIVER`)
   - `Start` (DWORD): `3` (`SERVICE_DEMAND_START`) — load via `NtLoadDriver`, not boot-start
   - `ErrorMode` (DWORD): `0` (`SERVICE_ERROR_IGNORE`)
3. Place the driver file on disk. The file must pass signature verification: on a default x64 Windows 10/11, `NtLoadDriver` invokes `CI.dll!CiValidateImageHeader` which checks the Authenticode signature against the Microsoft root cert chain. Unsigned drivers are rejected with `STATUS_INVALID_IMAGE_HASH (0xC0000428)` regardless of caller privilege. **You cannot load unsigned drivers on production Windows with `SeLoadDriverPrivilege` alone** — this is the most common operator mistake.
4. BYOVD: drop a known-vulnerable-but-legitimately-signed driver. Canonical entries:
   - `RTCore64.sys` (Micro-Star International, "MSI Afterburner", CVE-2019-16098) — IOCTL for arbitrary physical-memory R/W
   - `iqvw64e.sys` (Intel LAN, CVE-2015-2291 and follow-ons) — arbitrary kernel R/W
   - `gdrv.sys` (Gigabyte) — same class
   - `dbutil_2_3.sys` (Dell, CVE-2021-21551) — physical memory R/W
5. Load: `NtLoadDriver(&ustrName)` where `ustrName.Buffer = L"\\Registry\\Machine\\System\\CurrentControlSet\\Services\\<drvname>"`. Returns `STATUS_SUCCESS` (0) or `STATUS_IMAGE_ALREADY_LOADED (0xC000010E)` if the driver was already loaded by another instance.
6. IOCTL the driver for kernel R/W primitives. With arbitrary kernel read: walk `PsActiveProcessHead` (an exported kernel global — the System process EPROCESS pointer is `PsInitialSystemProcess`) to find the System EPROCESS (PID 4). Read its `EPROCESS.Token` field (offset varies per build — retrieve from the kernel PDB via `dt _EPROCESS Token` in WinDbg for the current build).
7. Write that token pointer into your own process's EPROCESS at the same offset. Your process is now SYSTEM — no token handle, no stolen primary token needed for subsequent operations because the kernel `_TOKEN*` in your EPROCESS has been swapped to System's `_TOKEN`.
8. Optionally, the loaded driver can call `PsSetCreateProcessNotifyRoutineEx(callback, TRUE)` to install a kernel callback on every future `NtCreateUserProcess`, providing a persistence hook that survives your process exit.

## OS Internals Context

### Where SeDebugPrivilege bypass actually lives

`SepAccessCheck` (in `ntoskrnl.exe`) is the security routine that consumes `DesiredAccess`, the security descriptor, and the subject's token to produce an access decision. For process and thread objects specifically, there is a fast-path branch: before `SepAccessCheck` walks the security descriptor's `DACL`, it inspects `SubjectContext->Token->Privileges` for `SE_DEBUG_PRIVILEGE` (LUID value 20). If the corresponding `LUID_AND_ATTRIBUTES.Attributes` field has the `SE_PRIVILEGE_ENABLED (0x2)` bit set, the routine returns `STATUS_SUCCESS` for the entire `DesiredAccess` mask regardless of what the DACL would say. This is the structural bypass: not "DACL grants everything to the holder," but "the holder can ignore the DACL on process and thread objects." The bypass does *not* extend to files, registry keys, or other securable types.

The `_TOKEN` object's `Privileges` field is an array of `LUID_AND_ATTRIBUTES` (8 bytes per entry: 4-byte LUID + 4-byte attributes). `SepPrivilegeCheck` worker iterates this array; the `Attributes` bitmask distinguishes `SE_PRIVILEGE_ENABLED (0x2)`, `SE_PRIVILEGE_ENABLED_BY_DEFAULT (0x1)`, and `SE_PRIVILEGE_REMOVED (0x4)`. `RtlAdjustPrivilege` flips only the `ENABLED` bit — a privilege held but not enabled does not satisfy `SepAccessCheck`'s debug bypass, which is why the `RtlAdjustPrivilege(..., TRUE, ...)` call is mandatory before `OpenProcess`.

### Token object layout and duplication

The internal `_TOKEN` structure carries: `TokenSource` (`TOKEN_SOURCE` 16 bytes), `TokenID` (`LUID`), `AuthenticationId` (`LUID`), `ExpirationTime` (`LARGE_INTEGER`), `ModifiedId` (`LUID`), `TokenFlags` (`ULONG`), `SessionId` (`ULONG`), `UserAndGroups` (`SID_AND_ATTRIBUTES*`), `RestrictedSids`, `Privileges` (`LUID_AND_ATTRIBUTES*`), `DefaultDacl`, `UserSid`, `PrimaryGroupSid`, `TokenType` (0 = TokenPrimary, 1 = TokenImpersonation), `ImpersonationLevel` (0–3), `IntegrityLevel`. When `DuplicateTokenEx` runs with `TokenPrimary` output type and `SecurityImpersonation` impersonation level, the duplicate's `TokenType` is set to `TokenPrimary` and `ImpersonationLevel` to `SecurityImpersonation`. A primary token cannot be used for impersonation (cannot be attached to a thread via `NtSetInformationThread(ThreadImpersonationToken, ...)`), but it can be used to create a new process. Conversely, an impersonation token cannot be used directly with `CreateProcessWithTokenW`/`CreateProcessAsUserW` — that is why `TokenPrimary` is requested in the duplicate.

### CreateProcessWithTokenW vs CreateProcessAsUserW

`CreateProcessAsUserW` (kernel32/advapi32) wraps `NtCreateUserProcess`. The caller must hold `SeAssignPrimaryTokenPrivilege` (LUID 3) — the operation is "assign a primary token to a new process." `CreateProcessWithTokenW` is different: it RPCs to the secondary logon service (`seclogon.dll`, hosted in `svchost.exe -k netsvcs` on modern Windows). The seclogon service runs as SYSTEM, has `SeAssignPrimaryTokenPrivilege` itself, and performs the actual `CreateProcessAsUser` call internally. The privilege check on the *caller* is for `SeImpersonatePrivilege` (LUID 29), because the caller is effectively asking seclogon to impersonate them and use their token. Both APIs check the source token's impersonation level — the level must be at least `SecurityImpersonation` (level 2). `SecurityIdentification` (level 1) is insufficient; `SecurityAnonymous` (level 0) is rejected outright. This is why `DuplicateTokenEx` is called with `SecurityImpersonation` rather than `SecurityIdentification`.

If the seclogon service is stopped, `CreateProcessWithTokenW` fails with `ERROR_NOT_FOUND` or `RPC_S_SERVER_UNAVAILABLE`. Operators using this chain should verify the service state first: `sc.exe query seclogon` (the service key is `HKLM\SYSTEM\CurrentControlSet\Services\seclogon`, image `%SystemRoot%\system32\seclogon.dll`).

### EPROCESS and token stealing from kernel

In kernel mode, every process has an `_EPROCESS` block. The `Token` field is actually an `EX_FAST_REF`: a pointer with the low 4 bits reserved for ref-counting (so the actual `_TOKEN*` is `Token & ~0xF`). Token theft from the kernel reads `&PsInitialSystemProcess->Token` and writes it into `&MyEPROCESS->Token`, preserving the low 4 bits (which encode the reference count) — typically `or`-ing with the existing low bits or setting them to a safe default.

`PsInitialSystemProcess` is an exported kernel global — the System process (PID 4) EPROCESS pointer. From kernel mode, walking `ActiveProcessLinks` (a `LIST_ENTRY` inside EPROCESS; offset varies per build) lets you locate any process by image name. From the vulnerable-driver BYOVD path, the driver exposes this primitive via IOCTL.

Modern Windows includes Protected Process Light (PPL) — `EPROCESS.Protection` is a `_PS_PROTECTION` byte; values like `PsProtectedSignerAutogenerated | PsProtectedTypeProtected` indicate PPL. Stealing a token from a PPL process from user-mode is blocked, but from kernel mode (e.g., via BYOVD) it is trivially bypassable — the protection only blocks `NtOpenProcess` and `NtSetInformationProcess`, not direct kernel writes.

### NtLoadDriver and code integrity

`NtLoadDriver(PUNICODE_STRING DriverServiceName)` accepts a *registry* path, not a file path — a frequent operator error is passing a file path and getting `STATUS_OBJECT_TYPE_MISMATCH (0xC0000024)`. The kernel (`IopLoadDriver`) reads `ImagePath` from the service key, resolves it to a file path, then invokes `MmLoadDriverImage` → `MiLoadImageSection` → `CiValidateImageHeader` (in `CI.dll`). `CiValidateImageHeader` walks the PE's `IMAGE_DIRECTORY_ENTRY_SECURITY` (`DataDirectory` index 4) to find the `WIN_CERTIFICATE` blob, verifies the Authenticode chain against the Microsoft Trusted Root, and rejects unsigned or improperly-signed drivers with `STATUS_INVALID_IMAGE_HASH (0xC0000428)`.

Bypassing signature enforcement requires one of: enabling test-signing via `bcdedit /set testsigning on` (requires reboot, leaves a watermark on the desktop), disabling DSE via kernel-level patching of `g_CiOptions` (a kernel variable at a non-exported address, discoverable via signature scan or via the `nt!g_CiOptions` symbol if you have the PDB), or using a vulnerable *signed* driver to flip the `g_CiOptions` byte — the meta-attack where BYOVD lets you disable DSE so you can then load your own unsigned driver. The BYOVD primitives catalogued in Variant 5 use legitimately-signed drivers as their entry vector for the kernel R/W primitive itself; the unsigned-driver load is a follow-on capability.

### PsSetCreateProcessNotifyRoutineEx (kernel-side, used post-BYOVD)

Once you have kernel R/W via BYOVD, you can call `PsSetCreateProcessNotifyRoutineEx(PCREATE_PROCESS_NOTIFY_ROUTINE_EX, TRUE)` to register a callback that fires on every `NtCreateUserProcess`. The callback receives a `PS_CREATE_NOTIFY_INFO*` containing `CreatingThreadId`, `ParentProcessId`, `FileObject`, `ImageFileName`, `CommandLine`, and a `CreationStatus` field — modifying `CreationStatus` to a non-success NTSTATUS blocks the process from starting. This is the same mechanism EDR uses (Defender, CrowdStrike, etc.). Installing a malicious callback here gives you process-creation visibility across the box with no user-mode indicator — every new process, regardless of who spawned it, passes through your kernel routine. `PsRemoveCreateProcessNotifyRoutineEx` is the cleanup; failing to deregister at unload causes a BSOD on the next callback table walk.

## Key Implementation Details

Prerequisites for the canonical SeDebug chain: the caller's token must hold `SeDebugPrivilege` AND `SeImpersonatePrivilege` both — the first to grab the SYSTEM token, the second to spawn a process with it. Default Administrators tokens have both; UAC-filtered admin tokens (medium IL) have `SeDebugPrivilege` removed until elevation. Verify before launching the chain by calling `GetTokenInformation(hTok, TokenPrivileges, ...)` and inspecting the `LUID_AND_ATTRIBUTES` array for LUIDs 20 and 29 with `SE_PRIVILEGE_ENABLED` or `SE_PRIVILEGE_ENABLED_BY_DEFAULT`.

`OpenProcessToken` requires `TOKEN_DUPLICATE (0x0008)` — without it, `DuplicateTokenEx` returns `ERROR_ACCESS_DENIED (5)`. The `winlogon.exe` token has `ProtectionLevel = 0` (no PPL) on most builds — accessible from any SYSTEM-context caller. On Win10 1709+ with Credential Guard enabled, `winlogon.exe` runs under PPL — `OpenProcess` then returns `STATUS_ACCESS_DENIED` despite `SeDebugPrivilege`. This is the most common reason a working SeDebug chain fails on hardened hosts. Alternative targets when PPL is active: `wininit.exe` (no PPL by default), `services.exe` (no PPL). `lsass.exe` is heavily PPL-guarded under LSA Protection and is the wrong target for token theft.

`DuplicateTokenEx` with `MAXIMUM_ALLOWED` for the desired access passes the original token's effective permissions through. If you need to tweak the token (drop specific groups for stealth), use `SetTokenInformation` after duplication — but the `TOKEN_ADJUST_*` access rights must have been granted on the duplicate, and `MAXIMUM_ALLOWED` includes them.

For `CreateProcessWithTokenW`, the `lpEnvironment` parameter should typically be NULL (inheriting the caller's environment) or a freshly-created environment block from `CreateEnvironmentBlock(hPrimary, NULL, TRUE)` against the duplicated token. Inheriting from the admin-context caller produces a SYSTEM-context child with `USERPROFILE` pointing at the admin's profile — a telltale artifact that detection rules key on.

`RtlAdjustPrivilege` lives in `ntdll.dll`/`kernel32.dll` and is not formally documented for use outside the OS — but it is the fastest single-call enable for a known LUID. The function signature is `NTSTATUS RtlAdjustPrivilege(ULONG Privilege, BOOLEAN Enable, BOOLEAN Client, PBOOLEAN PreviousValue)`. Setting `Client = TRUE` adjusts the impersonation token (only meaningful if currently impersonating), `FALSE` adjusts the process primary token. For token-theft chains use `FALSE`.

## Why It Matters

These five primitives are the **administrative-to-SYSTEM boundary** in Windows. Without one of these, you cannot natively cross from Administrators membership to a SYSTEM-context execution — every SYSTEM-targeted technique downstream (LSASS dumping via T-023, token impersonation in Kerberos attacks, service-host pivots) requires one of these primitives as a precondition. The SeDebug chain in particular is the lowest-friction path on a default install: no file drops, no registry changes, no service modification, just three API calls against a process already running. On hardened hosts with Credential Guard and PPL, SeDebug against `winlogon.exe` or `lsass.exe` is blocked, and operators move to `SeTakeOwnership`-via-service-replacement (more telemetry, more artifacts) or BYOVD (most powerful, requires file drop and registry service entry).

The primitives compose with: T-013 (process injection — used to inject the spawned SYSTEM shell back into a more legitimate host process for stealth), T-016 (token impersonation — `SeDebug` is the privilege that *enables* T-016-style token impersonation from admin context), T-022 (LSASS access — having a SYSTEM token means the next-stage LSASS query is in-system), T-023 (LSASS credential harvest — directly requires one of these primitives first), T-021 (CMSTP UAC bypass — gets you to admin; this card gets you from admin to SYSTEM). Operators reaching for any SYSTEM-targeted technique should reach for this card first.

## Detection Considerations

- **Telemetry sources**: ETW `Microsoft-Windows-Kernel-Process` (Event ID 1, process create) records the parent PID and the new process's token — a SYSTEM-spawned child from a non-SYSTEM parent is anomalous. ETW `Microsoft-Windows-Seclogon` emits events on `CreateProcessWithTokenW` RPC activity originating from non-seclogon processes. Sysmon Event ID 1 with `IntegrityLevel = System` and a non-SYSTEM parent is a strong signal. `ObRegisterCallbacks` with `PsProcessType` and `OB_OPERATION_HANDLE_CREATE` lets EDR see all `OpenProcess(PROCESS_ALL_ACCESS)` calls — `winlogon.exe` / `lsass.exe` handle opens by non-SYSTEM processes are flagged. The kernel callback `PsSetCreateProcessNotifyRoutineEx` is what legitimate EDR uses to capture the new SYSTEM-context process. Microsoft Defender for Endpoint's `DeviceProcessEvents` surfaces `InitiatingProcessParentFileName != "services.exe" && Account == "SYSTEM"` as a detection. ETW-TI (Threat Intelligence) provider `Microsoft-Windows-Threat-Intelligence` emits `EtwThreatIntProvRundown_ProcessCreate` for the spawn, with `TokenSource` logged.
- **Bypass options**: Avoid `winlogon.exe` and `lsass.exe` — pick `wininit.exe` or `services.exe` to dodge process-specific detection rules. Use `NtCreateThreadEx` against the stolen token's process: instead of spawning a new SYSTEM process, inject a thread into `wininit.exe` itself (still requires `SeDebugPrivilege` for the `OpenProcess`). Stage the new process inside a host that already runs as SYSTEM (e.g., a scheduled task at-boot, with the parent `taskhostw.exe` — but the task creation itself is telemetry). Kill the ETW-TI provider sessions before the spawn — `EtwNotificationUnregister` against the TI provider GUID requires kernel access (BYOVD territory).
- **Residual artifacts**: A SYSTEM-spawned `cmd.exe` leaves behind `Microsoft-Windows-EventLog` ID 4688 with `SubjectUserName = SYSTEM` and `ParentProcessName` pointing at your admin-context binary. Sysmon Event 1 with `User = NT AUTHORITY\SYSTEM` and a parent in the Administrators group's user SID is a persistent artifact. The token duplication itself is not audited at the kernel level by default, but `Advanced Security Audit Policy → Privilege Use → Sensitive Privilege Use` if enabled logs Event ID 4673 with `Privileges = SeDebugPrivilege` on the `OpenProcess` call. `seclogon` activity is logged as Event 4648 (explicit credential logon attempt) with `ProcessName` of the calling admin process. The `RtlAdjustPrivilege(SE_DEBUG_NAME, TRUE, ...)` call itself produces Event ID 4673 if Privilege Use auditing is on. For BYOVD, the `NtLoadDriver` call produces a `Microsoft-Windows-Kernel-PnP` event and Sysmon Event ID 6 (Image Load) for the driver; the service-control 7036 start/stop event fires; the loaded driver's image is visible in `Get-Module`-equivalent enumerations from kernel mode.

## Common Mistakes

1. **Forgetting `RtlAdjustPrivilege` before `OpenProcess`**: the privilege is *present* in the token but not *enabled* — `SepAccessCheck` only honors the `SE_PRIVILEGE_ENABLED` bit, not mere presence. The `OpenProcess` call then returns `ERROR_ACCESS_DENIED (5)`. Run `RtlAdjustPrivilege(SE_DEBUG_NAME, TRUE, FALSE, ...)` first; check the return.
2. **Targeting `lsass.exe` on a host with LSA Protection enabled**: PPL blocks `OpenProcess` despite `SeDebugPrivilege` — `STATUS_ACCESS_DENIED`. Pick `wininit.exe` (no PPL by default), `services.exe` (no PPL), or a generic `svchost.exe` running as SYSTEM. `lsass.exe` is also EDR honeypot territory.
3. **Calling `DuplicateTokenEx` with `SecurityIdentification` instead of `SecurityImpersonation`**: the lower impersonation level is sufficient for some operations but `CreateProcessWithTokenW` rejects it with `ERROR_BAD_IMPERSONATION_LEVEL (1346)`. Always specify `SecurityImpersonation`.
4. **Passing a file path to `NtLoadDriver`**: the argument is a *registry service name* like `\Registry\Machine\System\CurrentControlSet\Services\<name>`, not `C:\Path\To\driver.sys`. Passing a file path returns `STATUS_OBJECT_TYPE_MISMATCH (0xC0000024)`. Write the `ImagePath` value in the registry service key and pass the service name to `NtLoadDriver`.
5. **Dropping an unsigned driver and expecting `SeLoadDriverPrivilege` to bypass signature enforcement**: it does not. Code integrity (`CI.dll!CiValidateImageHeader`) is invoked regardless of caller privilege. The privilege only satisfies the privilege check in `NtLoadDriver` itself — it does not bypass DSE. Use a known-vulnerable legitimately-signed driver (BYOVD).
6. **Not setting `TokenPrimary` in `DuplicateTokenEx`**: the default `TokenType` of the source token may be `TokenImpersonation` if it came from another process's impersonation token. `CreateProcessWithTokenW` requires a primary token and fails with `ERROR_BAD_IMPERSONATION_LEVEL`. Explicitly specify `TokenPrimary` as the duplicate type.
7. **Inheriting the caller's environment block in `CreateProcessWithTokenW`**: the new SYSTEM-context child gets `USERPROFILE` pointing at the admin's profile, `USERNAME` of the admin, etc. — a beacon for detection rules. Pass `lpEnvironment = NULL` only if you want this, or build a clean env via `CreateEnvironmentBlock(hPrimary, NULL, TRUE)`.
8. **Failing to deregister `PsSetCreateProcessNotifyRoutineEx` before driver unload**: the callback table still holds a pointer to your driver's routine; the next process creation dereferences unmapped memory and bugchecks with `PAGE_FAULT_IN_NONPAGED_AREA`. Always call `PsRemoveCreateProcessNotifyRoutineEx` in the driver's `DriverUnload` routine.

## Composition with Other Techniques

A realistic admin-to-kernel kill chain combining these primitives with adjacent vault techniques:

1. **T-021 CMSTP UAC bypass** — gets you from medium-IL admin to high-IL admin. Elevation completes; you now have a token with `SeDebugPrivilege` present (but not yet enabled).
2. **Variant 1 SeDebug chain (this card)** — `RtlAdjustPrivilege(SE_DEBUG_NAME, TRUE, ...)`, then `OpenProcess(PROCESS_ALL_ACCESS, winlogon_pid)`, `OpenProcessToken`, `DuplicateTokenEx(..., TokenPrimary, ...)`, `CreateProcessWithTokenW(hPrimary, 0, NULL, L"C:\\Windows\\System32\\cmd.exe", ...)`. Now you have a SYSTEM `cmd.exe`.
3. **T-013 process injection** — inject your actual beacon into the spawned SYSTEM shell's process space to get the beacon running as SYSTEM without leaving a `cmd.exe` window artifact. The SYSTEM `cmd.exe` exits; the beacon continues inside the new host (e.g., a `svchost.exe` running as SYSTEM — using `NtCreateThreadEx` against it).
4. **T-022 LSASS access** — from SYSTEM context, open `lsass.exe` with `PROCESS_VM_READ` and dump via `MiniDumpWriteDump` or `NtQueryInformationProcess` paths. This is what you came for; the SYSTEM token was a stepping stone.
5. **T-023 LSASS credential harvest** — extract the credentials, exfiltrate.
6. **(Optional) Variant 5 BYOVD** — if host hardening (Credential Guard, Defender for Endpoint with kernel callbacks) makes Variant 1 unreliable, drop a BYOVD driver at step 2 instead: register `HKLM\SYSTEM\CurrentControlSet\Services\RTCore64`, `NtLoadDriver`, IOCTL for kernel R/W, swap the `EPROCESS.Token` of your admin-context process to the System EPROCESS token. Skip the spawn entirely; your existing process becomes SYSTEM invisibly to user-mode ETW.

The chain T-021 → this card (V1) → T-013 → T-022 → T-023 is the canonical "I'm an admin, I want LSASS creds in five steps" path on a default-Windows 10/11 box. Substituting V1 with V5 (BYOVD) is the canonical path on a hardened host.

## Historical Context

The `SeDebug` → `winlogon.exe` → `DuplicateTokenEx` → `CreateProcessWithTokenW` chain has been documented since at least 2007 (Metasploit's `getsystem` via impersonation techniques). The technique became default red-team canon and was used by Stuxnet-era operators. Microsoft's mitigations have been incremental: PPL for `lsass.exe` under LSA Protection (Win8.1+), PPL for `winlogon.exe` under Credential Guard (Win10 1709+), and the longer-term push to remove `SeDebugPrivilege` from default admin tokens — a configuration that breaks debugging tools and has not become the default. The BYOVD meta-attack emerged prominently around 2018–2020 with the catalog of vulnerable signed drivers (RTCore64, iqvw64e, dbutil_2_3, gdrv, etc.); Microsoft's response has been the Vulnerable Driver Blocklist (HVCI-blocked driver list), introduced in 2019 and updated quarterly. As of 2024, the blocklist is opt-out via GPO (`Microsoft\Windows\Device Guard` → `Deploy HVCI`) and on by default for fresh Windows 11 installs — meaning canonical BYOVD drivers like `RTCore64.sys` are blocked on modern hardened hosts, and operators must find newer vulnerable drivers not yet on the blocklist. The `SeCreateTokenPrivilege` path has remained unchanged since NT 3.1 — the privilege has always been SYSTEM-only and the operator must come by it through unusual configuration or via a prior SYSTEM foothold. `SeTcbPrivilege`'s "act as part of the operating system" semantics have been progressively narrowed; in modern Windows it is essentially vestigial, with most security checks moved to `SeImpersonatePrivilege`.
