# Memory Forensics Detection Layer (PE-sieve, Moneta, Volatility) — How userland scanners fingerprint in-memory implants

## Summary

PE-sieve (Hasherzade, 2018+), Moneta (forrest-orr, 2021), and Volatility (Volatility Foundation) constitute the open-source tier of memory-forensics tooling that catches in-memory implants when signature-based on-disk AV fails. PE-sieve and Moneta are live user-mode scanners; Volatility operates offline against captured full-system or per-process dumps. The three converge on three orthogonal signals. (1) `VirtualQueryEx` / `NtQueryVirtualMemory(MemoryBasicInformation)` returns a `MEMORY_BASIC_INFORMATION` whose `Type` discriminates `MEM_IMAGE=0x1000000` (legitimately section-mapped DLL) from `MEM_PRIVATE=0x20000` (manually-allocated implant) and whose `AllocationProtect` discriminates `PAGE_EXECUTE_WRITECOPY=0x80` (loader-mapped with copy-on-write, the only legit value for executable image regions) from `PAGE_EXECUTE_READWRITE=0x40` (manually mapped or post-load flipped). (2) `PEB.Ldr.InLoadOrderModuleList` (`PEB_LDR_DATA` offset `0x10`) is walked, and for each `LDR_DATA_TABLE_ENTRY.DllBase` the in-memory `.text` bytes are SHA-256 hashed and compared against the on-disk image — any divergence flags module stomping (T-007), Threadless injection (T-008), inline-hooked NTDLL (T-016), or any variant where `.text` does not byte-match the original file. (3) `GetMappedFileNameW` (which wraps `NtQueryVirtualMemory(MemoryMappedFilenameInformation=2)`) returns the `\Device\HarddiskVolume*\path\foo.dll` backing string, distinguishing manually-mapped payloads (no backing file) from stomped DLLs (legitimate file backing preserved). Volatility bypasses the PEB entirely and walks the per-process `_EPROCESS.VadRoot` (`_RTL_AVL_TABLE` of `_MMVAD` nodes) — catching PEB-unlinked modules the live scanners structurally cannot see. The vault's T-095 card documents NTDLL unhook variants but does not enumerate which scanner primitive catches each variant; this card closes that gap by mapping each scanner's heuristic to the specific injection/evasion card it defeats.

## Mechanism

### Variant 1: PE-sieve — module-list walk with on-disk byte comparison

1. Acquire a handle via `OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ = 0x0410)`. For `PsProtectedSignerLsa` / PPL-L targets, `SeDebugPrivilege` is insufficient and the call returns `ERROR_ACCESS_DENIED`; PE-sieve then falls back to `PROCESS_QUERY_LIMITED_INFORMATION (0x1000)`, which permits `VirtualQueryEx` but blocks `ReadProcessMemory`, degrading `.text` hashing.
2. Resolve the remote PEB: `NtQueryInformationProcess(hProcess, ProcessBasicInformation=0, &pbi, sizeof(pbi), NULL)` returns a `PROCESS_BASIC_INFORMATION` whose `PebBaseAddress` field points at the target's PEB.
3. Read `PEB.Ldr` (PEB offset `0x18` on x64, `0x0C` on x86) — a pointer to a `PEB_LDR_DATA` in the remote address space.
4. Walk `PEB_LDR_DATA.InLoadOrderModuleList` (`+0x10`), a `LIST_ENTRY` of `LDR_DATA_TABLE_ENTRY` records. For each entry read `DllBase` (`+0x30`), `FullDllName` (`+0x48`), `BaseDllName` (`+0x58`), `SizeOfImage` (`+0x40`), and `LoadReason` (`+0x428` on Windows 10+).
5. For every `DllBase`, call `VirtualQueryEx(hProcess, dllBase, &mbi, sizeof(mbi))` and capture `mbi.AllocationProtect`, `mbi.Type`, `mbi.Protect`, `mbi.RegionSize`.
6. Apply the **legitimate-image invariant**: a DLL mapped by the loader has `Type == MEM_IMAGE` AND `AllocationProtect == PAGE_EXECUTE_WRITECOPY (0x80)` because the section was created with `SEC_IMAGE (0x01000000)` and the kernel maps `.text` copy-on-write. PE-sieve flags:
   - `AllocationProtect == PAGE_EXECUTE_READWRITE (0x40)` ⇒ manually-mapped or stomped.
   - `Type == MEM_PRIVATE (0x20000)` ⇒ unbacked implant (e.g. Cobalt Strike sleep beacon, reflective DLL injection).
   - `Type == MEM_MAPPED (0x40000)` ⇒ manually-mapped section from a non-image file (e.g. shellcode `.shc` payload).
7. Call `GetMappedFileNameW(hProcess, dllBase, buf, MAX_PATH)` which dispatches to `NtQueryVirtualMemory(MemoryMappedFilenameInformation=2)`. Returns `\Device\HarddiskVolumeN\Windows\System32\ntdll.dll`. An empty return means no file backing ⇒ manually-mapped. A stomped DLL still reports the legitimate path (the file is unchanged on disk) — this alone is insufficient and PE-sieve treats it as one column in a multi-column decision.
8. Read the on-disk PE file via `CreateFileW(... GENERIC_READ, FILE_SHARE_READ ...)`, map with `CreateFileMappingW(PAGE_READONLY | SEC_COMMIT)` and `MapViewOfFile(FILE_MAP_READ)`.
9. Parse the on-disk PE: `IMAGE_DOS_HEADER.e_lfanew` at offset `0x3C` → `IMAGE_NT_HEADERS64` at file offset `e_lfanew`, verify signature `0x00004550`. Walk `OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXCEPTION=3]` for the unload table (sometimes checked) and the section table for `.text` (`IMAGE_SCN_CNT_CODE | IMAGE_SCN_MEM_EXECUTE`).
10. Read the in-memory `.text` from the target at `DllBase + section.VirtualAddress` for `section.SizeOfRawData` bytes via `ReadProcessMemory`. Read on-disk `.text` at `section.PointerToRawData` for the same length.
11. Hash both buffers with `BCryptCreateHash` / `BCryptHashData` (SHA-256). Mismatch ⇒ flag. The hash granularity catches: 5-byte `JMP rel32` inline hooks, 12-byte `MOV RAX, imm64; JMP RAX` trampolines, full `.text` replacement (module stomping), and any per-export overwrite pattern that lives inside the hashed range.
12. For `MEM_PRIVATE` regions not covered by the loader list, run a "scraped PE" pass: enumerate `VirtualQueryEx` results, identify `MEM_PRIVATE + PAGE_EXECUTE_READWRITE` regions, scan the first page for `MZ` magic (`0x5A4D`) at offset 0 followed by `e_lfanew` → `PE\0\0` (`0x00004550`). If a valid PE is reconstructed, dump it to `%TEMP%\__pe-sieve_<pid>_<timestamp>\`.
13. Emit JSON with per-module `status` (`Trust` / `Suspicious` / `Replaced` / `Implanted`), per-region `protection`, `type`, `mapped_path`, and `sha256_in_mem` / `sha256_on_disk`.

### Variant 2: Moneta — region-generic anomaly scan

1. Acquire `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` against the target PID.
2. Enumerate the entire user virtual address space via `VirtualQueryEx` with stride `mbi.RegionSize` from `0x0000` through `0x000007FFFFFFFFFF` (the user/kernel boundary on x64; the top 2 bits clear).
3. For each region capture `State`, `Protect`, `Type`, `AllocationProtect`, `RegionSize`. Apply the suspicion filters:
   - `Type == MEM_PRIVATE && Protect == PAGE_EXECUTE_READWRITE` ⇒ manually-mapped shellcode or reflective payload.
   - `Type == MEM_PRIVATE && Protect == PAGE_EXECUTE_READ` ⇒ reflective-loaded image post-`VirtualProtect` downgrade (the operator was hygiene-aware but the region is still private).
   - `Type == MEM_IMAGE && Protect == PAGE_EXECUTE_READWRITE` ⇒ a code page in a legitimately-loaded DLL that has been flipped to RWX (runtime patching, .NET JIT in older runtimes, ACG-violating implants).
   - `Type == MEM_IMAGE && AllocationProtect == PAGE_EXECUTE_READWRITE` ⇒ image was never mapped copy-on-write; manually mapped via `NtMapViewOfSection` with a writable section.
   - `Type == MEM_MAPPED && Protect == PAGE_EXECUTE_READWRITE` ⇒ shellcode staged as a mapped section.
4. For each suspicious region, optionally read the first 64 bytes via `ReadProcessMemory` and test for `MZ` / `PE` magic or known-bad signatures from the Moneta allowlist.
5. Emit a row-per-region console table with `BASE`, `SIZE`, `TYPE`, `PROTECT`, `ALLOC-PROTECT`, `PATH`, `NOTES`.

### Variant 3: Volatility — offline VAD-tree and pool-scan forensics

1. Acquire a memory image: `winpmem` (`winpmem_mini_x64.exe -o dump.raw`) loads `\Device\pmem` via a kernel driver (`pmem`), copies physical pages to disk. Alternative: a `LiveKd`-style `.dmp` or `Task Manager > Create dump file` per-process minidump.
2. Volatility parses the raw image by walking the `_EPROCESS` list from the kernel symbol `PsActiveProcessHead` (profile-resolved) or via the `_NP_SINGLE_THREADED` pool-scan fallback (`POOL_TAG = 'Proc'`).
3. For each process, walk `EPROCESS.VadRoot` — an `_RTL_AVL_TABLE` of `_MMVAD_SHORT` nodes. Each node encodes `StartingVpn`, `EndingVpn`, `u.VadFlags.Protection` (5-bit index into `MmProtectToValue[]`), `u.VadFlags.VadType` (`VadImageMap=2`, `VadDeviceDriverMemory=3`, `VadWriteWatch=4`), `Subsection` pointer to `_CONTROL_AREA`.
4. The `malfind` plugin reports any `_MMVAD` whose decoded `Protection` is `PAGE_EXECUTE_READWRITE (0x40)` or `PAGE_EXECUTE_WRITECOPY (0x80)` AND whose backing indicates private prototype PTE state. Output is a `0x...`-prefixed hexdump with magic detection (`MZ`, `PE`, `0xeb 0x??` short jumps).
5. The `ldrmodules` plugin enumerates all three PEB loader lists (`InLoadOrder`, `InMemoryOrder`, `InInitializationOrder`) AND walks the VAD tree separately, then cross-references. A module present in the VAD but absent from all three loader lists is the canonical "PEB-unlinked" implant detection.
6. `moddump` / `dlldump` reconstruct PEs from memory regions by RVA-to-file-offset translation, allowing offline reversing of dumped payloads.

## OS Internals Context

**VAD tree and the kernel's record of virtual address ranges.** Every user-mode address range in a Windows process is represented by an `_MMVAD` node in the per-process `EPROCESS.VadRoot` (an `_RTL_AVL_TABLE` on Windows 10+; an `_MMVAD` binary tree on legacy builds). Each `_MMVAD_SHORT` carries `StartingVpn` (a virtual page number, 52-bit effective on x64 with the upper 11 bits reserved), `EndingVpn`, and a packed `u.VadFlags` union where `VadFlags.Protection` is a 5-bit index into the kernel array `MmProtectToValue[]` that translates the encoded bits to one of `PAGE_NOACCESS=0x01` through `PAGE_EXECUTE_WRITECOPY=0x80`. The `_MMVAD_LONG` subtype adds `Subsection` (a pointer into the `_CONTROL_AREA.UserReference` chain), `FirstPrototypePte`, `LastPte`. When `VirtualQuery` returns `Type=MEM_IMAGE`, the kernel found an `_MMVAD` whose `VadFlags.VadType == VadImageMap` and whose `Subsection->ControlArea->Segment->FilePointer` resolves to a real `_FILE_OBJECT`. PE-sieve and Moneta live entirely in user space, so they only see the user-mode projection of this kernel state via `MEMORY_BASIC_INFORMATION`; Volatility reads the `_MMVAD` directly, bypassing the PEB entirely.

**AllocationProtect vs Protect.** `MEMORY_BASIC_INFORMATION` carries two protection fields. `AllocationProtect` is the *original* protection specified when the region was reserved or the section was mapped; `Protect` is the *current* protection, which `VirtualProtect` / `NtProtectVirtualMemory` can change at any time. When the loader maps `ntdll.dll`, it calls `NtMapViewOfSection` on a section object created with `SEC_IMAGE`, which sets `AllocationProtect = PAGE_EXECUTE_WRITECOPY (0x80)` — this is the **inviable invariant** the scanners exploit. An attacker who flips `.text` to `PAGE_EXECUTE_READWRITE` to write trampolines and forgets to flip it back leaves `Protect = 0x40` while `AllocationProtect` stays `0x80` — Moneta catches this asymmetry. An attacker who `VirtualFree`s and re-maps as `MEM_PRIVATE` flips `Type` from `MEM_IMAGE` to `MEM_PRIVATE` — PE-sieve catches this on the loader walk. An attacker who uses `NtCreateSection(SEC_IMAGE, PAGE_EXECUTE_WRITECOPY)` and `NtMapViewOfSection` with `PAGE_EXECUTE_WRITECOPY` and then writes via `WriteProcessMemory` from a *different* process — preserving the target's view — is the only configuration that preserves both fields. This is the technique behind clean NTDLL unhooking via `\KnownDlls\ntdll.dll` shadow copies.

**PEB loader lists — three lists, one structure.** `PEB_LDR_DATA` exposes `InLoadOrderModuleList` (`+0x10`), `InMemoryOrderModuleList` (`+0x20`), and `InInitializationOrderModuleList` (`+0x30`). Each module is registered on all three; the lists are `LIST_ENTRY` links embedded in `LDR_DATA_TABLE_ENTRY`. The loader inserts `ntdll.dll` first, then `kernel32.dll`, then `kernelbase.dll`. A module can be unlinked from one list and not the others (an old attacker trick called "selective list unlinking"); `ldrmodules` calls this out by showing the per-list presence bit. `PEB_LDR_DATA` also contains `Initialized` (`+0x08`), `LdrpHashTable` (`+0x3C` on Win10+, the module hash buckets used by `LdrpHashModule` for `LdrGetProcedureAddress` fast-path resolution) — PE-sieve does not cross-check the hash buckets; an attacker who fakes a `LDR_DATA_TABLE_ENTRY` without updating hash buckets is detected only by `ldrmodules` or by EDRs that re-derive the hash table.

**LDR_DATA_TABLE_ENTRY fields scanners care about.** Beyond `DllBase` (`+0x30`), `FullDllName` (`+0x48`), `BaseDllName` (`+0x58`), `SizeOfImage` (`+0x40`), `LoadReason` (`+0x428`, where `LoadReason = 1 DynamicLoad`, `2 StaticLoad`, `3 AsImageLoad`), `LoadCount` (`+0x448`), `EntryInProgress` (`+0x140` in legacy builds, varies on Win11), and `TimeDateStamp` (`+0x440`). The loader maintains `EntryInProgress` non-NULL during `LdrpCallInitRoutine` (TLS / `DllMain` dispatch); a stale `EntryInProgress` on a "loaded" module is a signature of a manually-inserted LDR entry that never ran the loader phases.

**Prototype PTEs and shared image backing.** `SEC_IMAGE` sections share backing across processes via **prototype PTEs** stored in the `_SUBSECTION` chain hanging off `_CONTROL_AREA.SubsectionBase`. When a process writes to a copy-on-write `.text` page, the memory manager splits the page: the prototype PTE in the subsection is left unchanged, and the process's local PTE (`_MMPTE_HARDWARE`) is mutated to point at a new PFN with the modified bytes. The original on-disk `.text` bytes are preserved in the prototype chain, and a fresh map of the same section object will see the original bytes. This is why a clean NTDLL unhook — map a second view of `\KnownDlls\ntdll.dll` from a `SEC_IMAGE` section, `memcpy` the `.text` into the existing process view, then unmap the second view — defeats PE-sieve. The bytes match the on-disk image again; `AllocationProtect` remains `PAGE_EXECUTE_WRITECOPY`; no kernel state changes.

**ETW Threat Intelligence provider and the kernel callback gap.** EDR products hook via `PsSetCreateProcessNotifyRoutineEx`, `PsSetCreateThreadNotifyRoutine`, `ObRegisterCallbacks` (handle creation), `CmRegisterCallbackEx` (registry), and `MiniFilter` altitudes for filesystem. None of these fire when an attacker reads their own process's `PEB.Ldr`, calls `VirtualQuery` on their own regions, or `ReadFile`s `ntdll.dll` from disk. The ETW Threat Intelligence provider (`{F4E1897C-BB5F-5C1C-5C1C-5C1C5C1C5C1C}` — placeholder GUID, real provider is `Microsoft-Windows-Threat-Intelligence`) emits events for kernel-mediated actions (`NtAllocateVirtualMemory`, `NtProtectVirtualMemory`, `NtMapViewOfSection`, `NtWriteVirtualMemory`, `NtSetInformationThread`) — but `VirtualQuery`, `ReadProcessMemory` against the calling process, and `NtQueryInformationProcess(ProcessBasicInformation)` on the calling process do not raise TI events. This is the gap that makes userland memory scanners possible as **post-hoc** detection rather than real-time blocking. Scanners run after the implant has executed; they cannot stop the operation, only flag it after.

**Why Volatility catches PEB-unlinked modules that PE-sieve cannot.** Because `ldrmodules` walks `_MMVAD` independently of `PEB.Ldr`. If an attacker unlinks a `LDR_DATA_TABLE_ENTRY` from all three loader lists, PE-sieve (which seeds its enumeration from `InLoadOrderModuleList`) will skip the module entirely. But the `_MMVAD` node still exists in the process `VadRoot`, the `Subsection` chain still resolves to the `_FILE_OBJECT`, and `ldrmodules` reports the asymmetry: present in VAD, absent in PEB lists. The only way to defeat `ldrmodules` is to free the `_MMVAD` itself, which means unmapping the section — and then the implant has no executable backing.

## Key Implementation Details

Three privileges gate scanner coverage. `PROCESS_QUERY_INFORMATION (0x0400)` and `PROCESS_VM_READ (0x0010)` together permit enumerating `PEB.Ldr` and reading `.text` for hash comparison. `PROCESS_VM_OPERATION (0x0008)` is required only for `VirtualProtectEx`-based probes — neither PE-sieve nor Moneta uses this. For system-protected processes (LSASS under PPL, secure `MsMpEng.exe`, `SearchIndexer.exe` under certain configurations), `SeDebugPrivilege` plus `PROCESS_QUERY_LIMITED_INFORMATION (0x1000)` is the userland ceiling; PPL-L processes (signer `PsProtectedSignerLsa`, level `< 2`) are unreachable by user-mode scanners and only Volatility operating on a kernel-captured dump can inspect them.

The PEB location varies by bitness. On x64: `PEB` is at offset `0x60` from the `TEB` (read in-process via `gs:[0x60]`, cross-process via `NtQueryInformationProcess(ProcessBasicInformation)`). On x86: `gs:[0x30]`. Under WOW64, the 64-bit PEB lives at `gs:[0x60]` from the 64-bit TEB (read via the `Wow64Info` shared user-page region at `0x7FFE0000` adjacent to `KUSER_SHARED_DATA`), and the 32-bit PEB lives at `0x30` from the 32-bit TEB. PE-sieve ships both 32- and 64-bit builds; a 32-bit PE-sieve binary cannot scan a 64-bit target (handle architecture mismatch). A 64-bit scanner reading a 32-bit target must read the 32-bit `PEB_LDR_DATA` via the WoW64 translation layer — a known footgun in older builds of PE-sieve before the multi-arch refactor; the symptom is `STATUS_PARTIAL_COPY (0x80000007)` on `ReadProcessMemory` of the 32-bit `PEB`.

`MEMORY_BASIC_INFORMATION` on x64 is `0x30` (48) bytes: `BaseAddress (8)` + `AllocationBase (8)` + `AllocationProtect (4)` + `__alignment1 (4)` + `RegionSize (8)` + `State (4)` + `Protect (4)` + `Type (4)` + `__alignment2 (4)`. `MEMORY_BASIC_INFORMATION32` is `0x1C` (28) bytes. Calling `NtQueryVirtualMemory` from a 64-bit scanner against a 32-bit target requires the `NtWow64QueryVirtualMemory64` shim or a manual wow64 thunk — failure to use the right structure produces `STATUS_INFO_LENGTH_MISMATCH (0xC0000004)` and the scanner exits with no output, which the operator may misread as "clean."

The constants are stable across all Windows versions since Vista: `MEM_IMAGE = 0x1000000`, `MEM_PRIVATE = 0x20000`, `MEM_MAPPED = 0x40000`; `PAGE_EXECUTE_WRITECOPY = 0x80`, `PAGE_EXECUTE_READWRITE = 0x40`, `PAGE_EXECUTE_READ = 0x20`, `PAGE_READWRITE = 0x04`, `PAGE_WRITECOPY = 0x08`. These are the **single most-checked fields** in user-mode scanner code paths. Implant authors who hardcode `PAGE_EXECUTE_READWRITE` for code regions with no need to write to them post-initialization are advertising themselves; the cost-correct choice is `PAGE_EXECUTE_READ` after the initial `VirtualProtect` from `PAGE_READWRITE` or after the loader phase writes the payload.

## Detection Evasion Ladder

Ordered from lowest-sophistication (caught by Moneta in seconds) to highest (requires Volatility + kernel-driver acquisition + analyst time):

1. **Flip `.text` to `PAGE_EXECUTE_READWRITE` and never flip back.** Moneta flags on first region scan; PE-sieve flags the protection asymmetry. The most common operator mistake.
2. **Use `VirtualAlloc(MEM_PRIVATE, PAGE_EXECUTE_READWRITE)` for the implant body.** Caught by Moneta's first-pass filter — `MEM_PRIVATE + RWX` is the single highest-signal row in the output.
3. **Write payload, then downgrade to `PAGE_EXECUTE_READ`.** Defeats Moneta's RWX filter but not PE-sieve (still `MEM_PRIVATE` with no `MEM_IMAGE` backing).
4. **Strip the `MZ` magic from manually-mapped images, relocate the PE header to a non-zero offset.** Defeats Moneta's magic-detection pass on private memory.
5. **Use `NtCreateSection(SEC_IMAGE) + NtMapViewOfSection(PAGE_EXECUTE_WRITECOPY)` instead of `VirtualAlloc`.** Defeats Moneta's `MEM_PRIVATE` filter and preserves `AllocationProtect = 0x80`. Still detected by PE-sieve's loader-list walk (the module is not in `PEB.Ldr`).
6. **Insert a fake `LDR_DATA_TABLE_ENTRY` for the mapped section.** Defeats PE-sieve's "unbacked private" scan. PE-sieve's hash comparison still fires if `.text` differs from any on-disk image; the operator must point `FullDllName` at a real file that matches.
7. **Match `.text` SHA-256 against on-disk (preserve legit `.text` or restore via `\KnownDlls\ntdll.dll` shadow copy).** Defeats PE-sieve. For NTDLL unhook, this is the canonical T-095 "clean unhook" variant.
8. **Unlink the `LDR_DATA_TABLE_ENTRY` from all three PEB loader lists.** Defeats PE-sieve entirely. Only `ldrmodules` in Volatility catches the VAD-vs-PEB asymmetry.
9. **Inject into a PPL-protected process (`MsMpEng.exe`, secure `SearchIndexer.exe`).** Defeats all user-mode scanners (PE-sieve, Moneta cannot acquire `PROCESS_VM_READ`). Only Volatility on a kernel dump survives.
10. **Block dump acquisition.** Kill `\Device\pmem` driver load (kernel-mode callback `PsSetLoadImageNotifyRoutine` blocks `pmem.sys`), deny `SeCreatePagefilePrivilege`, corrupt the live `KdDebuggerData` block to break `LiveKd`. Defeats Volatility.

## Common Mistakes

1. **Forgetting the post-write `VirtualProtect` downgrade.** Operator writes the payload with `PAGE_READWRITE`, then flips to `PAGE_EXECUTE_READWRITE` to execute, and never flips to `PAGE_EXECUTE_READ`. The RWX region is the loudest signal in Moneta. The fix is a second `NtProtectVirtualMemory` to `PAGE_EXECUTE_READ (0x20)` after the payload is staged.
2. **Using `VirtualAlloc` for a manually-mapped DLL.** `VirtualAlloc` always produces `MEM_PRIVATE` — there is no API combination that yields `MEM_IMAGE` from `VirtualAlloc`. To get `MEM_IMAGE`, the operator must use `NtCreateSection(SEC_IMAGE) + NtMapViewOfSection`. Forgetting this gives PE-sieve a slam-dunk private executable region.
3. **Unhooking NTDLL by writing a "fresh" copy downloaded from the internet.** Build-specific patch levels mean the internet-downloaded `ntdll.dll` differs from the host's `\Windows\System32\ntdll.dll` by N bytes in `.text`. PE-sieve hashes the on-disk file the module claims to back — the mismatch fires on every patched export. The fix is to map `\KnownDlls\ntdll.dll` (a kernel-managed section that is byte-identical to the disk image used by the loader).
4. **Unlinking only `InLoadOrderModuleList` and leaving `InMemoryOrderModuleList` and `InInitializationOrderModuleList` intact.** `ldrmodules` reports the per-list presence bit — the asymmetry is the detection signal. The unlink must touch all three `LIST_ENTRY` heads.
5. **Running 32-bit PE-sieve against a 64-bit process.** The scanner either returns `ERROR_NOT_SUPPORTED` or produces no output; the operator reports "clean" to their team. Always match scanner bitness to target bitness, or use the 64-bit build with the WoW64 thunk.
6. **Assuming PPL protection covers the implant.** PE-sieve cannot read `MsMpEng.exe` under Defender's PPL, but the implant's parent process is not PPL — the operator should ensure the implant's host process is PPL, not just that the implant was injected into one. If the operator injects into `MsMpEng.exe` but the staging happened in a non-PPL `svchost.exe`, the staging memory is scannable.

## Composition with Other Techniques

A realistic kill chain that survives a PE-sieve + Moneta sweep:

1. **T-095 NTDLL unhook** via the `\KnownDlls\ntdll.dll` shadow-copy variant. Map a fresh `SEC_IMAGE` section of `\KnownDlls\ntdll.dll`, `memcpy` `.text` from the shadow view into the existing process view, unmap the shadow view. Result: `AllocationProtect` unchanged (`PAGE_EXECUTE_WRITECOPY`), `.text` SHA-256 matches on-disk, no kernel state change. PE-sieve sees clean NTDLL.
2. **T-007 Module stomping** of a lesser-used DLL (`d3d11.dll` is a good choice — loaded into many processes, rarely inspected). Stomp `.text` but preserve the first `0x1000` bytes matching the on-disk image — many scanners hash only the first page or sample-spans to amortize cost. Map via `NtCreateSection(SEC_IMAGE) + NtMapViewOfSection(PAGE_EXECUTE_WRITECOPY)` rather than `VirtualAlloc`.
3. **T-008 Threadless injection** for the payload's initial dispatch — overwrite an exported function in the stomped DLL with a `JMP` to the payload body. No thread creation means no `PsSetCreateThreadNotifyRoutine` callback, no `RtlUserThreadStart` ETW event.
4. **Post-execution hygiene.** `NtProtectVirtualMemory` the payload body from `PAGE_EXECUTE_READWRITE` to `PAGE_EXECUTE_READ`. Restore the stomped export to its on-disk bytes via a second `\KnownDlls`-backed memcpy. Unlink the stomped module from `InLoadOrderModuleList` only if the post-execution state is the final rest state (otherwise `ldrmodules` flags the asymmetry).

End state against the scanner suite: PE-sieve sees clean NTDLL, legitimate module list, no `MEM_PRIVATE` executable regions, no hash deltas. Moneta sees no `RWX`, no `MEM_PRIVATE` with executable protection. Volatility (if a dump is taken) sees the stomped DLL's `_MMVAD` with `VadImageMap` backing — but the bytes match on-disk because of step 1's hygiene. Only a Volatility analyst correlating thread start addresses against the stomped DLL's export table catches this — and that requires manual triage.

## Why It Matters

Memory scanners are the only detection surface that catches module stomping (T-007) and Threadless injection (T-008) when the loader has not raised any of the kernel callbacks an EDR would normally key on. A stomped DLL never appears in `PsSetCreateProcessNotifyRoutineEx`, never raises `ObRegisterCallbacks` beyond the initial handle (which itself looks identical to the legitimate loader's handle), and never produces an `NtMapViewOfSection` Threat Intelligence event against a private section — because the section object was already mapped by the legitimate loader before the implant touched it. The only telemetry surface left is *post-hoc* `.text` byte comparison, which is exactly what PE-sieve does. Operators who reach for module stomping without modeling how PE-sieve walks `PEB.Ldr` are leaving fingerprints on a four-second scan.

Conversely, understanding the scanner internals tells operators where the blind spots are: PEB-unlinked modules defeat PE-sieve entirely until a Volatility capture is taken; clean NTDLL unhook via `\KnownDlls` shadow copy is byte-equivalent to on-disk and passes every PE-sieve hash check; manually-mapped payloads in `MEM_PRIVATE` with `PAGE_EXECUTE_READ` (not RWX) and no `MZ` header slide past Moneta's regex pass. The composition with T-016 (NTDLL unhook typology) is direct — the *post-unhook* state is what PE-sieve will see, and the question of whether the unhook variant leaves `AllocationProtect` or hash deltas maps one-to-one to the variant's detectability. The vault's T-011, T-013, and T-003 cards document injection primitives whose post-execution memory state is what these scanners fingerprint; this card is the missing counterpart.

## Detection Considerations

- **Telemetry sources**: the scanners themselves operate via `NtQueryVirtualMemory`, `VirtualQueryEx`, `ReadProcessMemory`, and `NtQueryInformationProcess(ProcessBasicInformation)` against the target. None of these raise ETW Threat Intelligence events (the TI provider keys on `NtAllocateVirtualMemory`, `NtProtectVirtualMemory`, `NtMapViewOfSection`, `NtWriteVirtualMemory` — kernel-mediated *mutating* syscalls, not *querying* syscalls). The only host-side tell that an EDR can hook is the `CreateProcess` event for `pe-sieve.exe` / `moneta.exe` itself and the `ObRegisterCallbacks` pre-operation when the scanner acquires `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` against the target PID. A defender with `PsSetCreateProcessNotifyRoutineEx` + `ObRegisterCallbacks` can flag the scanner binary and kill it before the scan completes.
- **Bypass options**: (1) operate within a process that PE-sieve doesn't scan (PPL-protected, e.g. inject into `MsMpEng.exe` or `SearchIndexer.exe` under certain build configurations); (2) unlink from all three PEB loader lists and accept that Volatility-on-dump will catch you — defeat the dump by avoiding `\Device\pmem` driver presence; (3) preserve `AllocationProtect == PAGE_EXECUTE_WRITECOPY` by mapping via `NtCreateSection(SEC_IMAGE)` rather than `VirtualAlloc`; (4) restore `.text` bytes from `\KnownDlls\ntdll.dll` shadow copy so SHA-256 matches on-disk; (5) place payload in `MEM_PRIVATE + PAGE_EXECUTE_READ` with the first page stripped of `MZ` magic and the PE header relocated to a non-zero offset (defeats Moneta's PE-header regex); (6) block dump acquisition by killing `pmem.sys` load via a kernel image-load callback.
- **Residual artifacts**: every scanner leaves output files in the run directory — PE-sieve's per-PID JSON and a `%TEMP%\__pe-sieve_<pid>_<timestamp>\` dump folder containing extracted `.exe`, `.dll`, and `.shc` artifacts (forensic-grade retrievals that survive scanner exit and are themselves IOCs); Moneta leaves a console log or CSV in the working directory. Volatility produces no live artifacts (offline tool) but the dump file itself (`dump.raw`, `*.dmp`, `*.vmem`) is a complete byte-image of the host's memory at capture time and is detected by host-based DLP rules if written to a network share or exfiltrated.

## Related Techniques

- **T-007 Module Stomping** — the canonical PE-sieve target; this card documents the `.text`-hash divergence that flags it.
- **T-008 Threadless Injection** — caught by PE-sieve when the payload is injected into a DLL's code section because the in-memory `.text` no longer matches on-disk; the no-thread property bypasses ETW and kernel callbacks but not post-hoc byte comparison.
- **T-016 NTDLL Unhook Typology** — the *post-unhook* state is what PE-sieve evaluates; the variant chosen (fresh-section memcpy vs. downloaded-file overwrite) determines whether the unhook survives a PE-sieve pass.
- **T-011 (injection/evasion)** — operates against the same `MEMORY_BASIC_INFORMATION` fields; PE-sieve scans it post-execution.
- **T-013 (injection/evasion)** — region-level artifacts enumerated by Moneta; the evasion question is whether the region's `Type` / `Protect` / `AllocationProtect` triple matches the legitimate-image invariant.
- **T-003 (injection primitive)** — seed technique for the artifacts these scanners fingerprint; this card is the detection-layer counterpart.
