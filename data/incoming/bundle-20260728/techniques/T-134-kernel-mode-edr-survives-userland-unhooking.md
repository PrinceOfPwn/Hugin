# Kernel-Mode EDR Survives Userland Unhooking — The Callback Surface That `VirtualProtect` Cannot Touch

## Summary

Restoring `ntdll.dll` to its on-disk image (the T-016 clean-NTDLL-unhook primitive) defeats inline hooks placed by user-mode EDR products in the `Nt*` export prologues, but it does **nothing** to suppress the kernel-side telemetry surface that modern EDRs rely on as their primary signal source. A kernel driver registered via `PsSetCreateProcessNotifyRoutineEx`, `PsSetLoadImageNotifyRoutine`, `PsSetCreateThreadNotifyRoutine`, `ObRegisterCallbacks`, `CmRegisterCallbackEx`, and `FltRegisterFilter` continues to receive notification events for process creation, image load, thread creation, handle duplication, registry mutation, and file I/O regardless of whether the user-mode `ntdll` syscall stubs are intact or restored. The callback infrastructure lives entirely inside `ntoskrnl.exe` — its dispatch lists (`PspCreateProcessNotifyList`, `PspLoadImageNotifyList`, `PspCreateThreadNotifyList`) and the `ObpTypeIndex`-driven `OBJECT_TYPE.TypeInfo` callback table are not addressable from user mode and are not modified by anything a userland unhook touches. Consequently, the T-016 unhook is necessary for evading inline-hooked EDRs but is **not sufficient** against any product that has registered kernel callbacks. An operator who runs T-016 against CrowdStrike Falcon, SentinelOne, Microsoft Defender for Endpoint, or similar kernel-resident products will see their injection, persistence, and lateral-movement primitives still generate alerts because the process-creation, image-load, and handle-duplication events still fire and still get correlated against the EDR's rule engine. The vault's T-016 card documents the mechanics of the userland unhook; this card exists to make the operational constraint explicit and to enumerate the kernel callback classes that must be addressed — typically via a signed or BYOVD-loaded kernel driver — to achieve full telemetry suppression. The vault's T-016 (Clean NTDLL Unhook) is the prerequisite; this card is the next layer up.

## Mechanism

The kernel callback surface that survives a userland unhook is not a single primitive — it is a family of six notification mechanisms, each registered through a distinct `ntoskrnl.exe` export, each driving a separate kernel-linked list of subscriber callbacks, and each intercepting a distinct phase of process / image / thread / handle / registry / file lifecycle. The operator must enumerate which of these are registered by the target EDR before assuming that T-016 alone provides evasion.

### Variant 1: PsSetCreateProcessNotifyRoutineEx (Process Create / Exit)

1. The EDR driver calls `PsSetCreateProcessNotifyRoutineEx(NotifyRoutine, FALSE)` from its `DriverEntry` once per registration.
2. `ntoskrnl.exe` inserts the routine pointer into the `PspCreateProcessNotifyList` (a `LIST_ENTRY` head protected by the `PspSystemThread` guarded mutex and the process-creation path lock).
3. When `NtCreateUserProcess` (or the legacy `NtCreateProcessEx` path) commits a new `EPROCESS`, `PspInsertProcess` walks `PspCreateProcessNotifyList` and invokes each callback with `(_In_ PEPROCESS Process, _In_ HANDLE ProcessId, _In_opt_ PPS_CREATE_NOTIFY_INFO CreateInfo)`.
4. The `PS_CREATE_NOTIFY_INFO` structure exposes `ImageFileName` (full NT path of the new image), `CommandLine`, `FileObject` (pointer to the executable's `FILE_OBJECT`, allowing the driver to hash the on-disk bytes), `ParentProcess` (EPROCESS of the parent), `CreatingThreadId` (the CID of the creator), and `CreationStatus` (`NTSTATUS` — **writable by the callback**, so a driver can deny creation by overwriting with `STATUS_ACCESS_DENIED`).
5. On process exit, the callback is re-invoked with `CreateInfo == NULL`, signaling teardown; the driver sees the exit code via `Process->ExitStatus`.
6. This notification fires regardless of whether the new process's `ntdll` was hooked, unhooked, or never instrumented. The notification is generated by `ntoskrnl`, not by the userland hook.
7. Detection of an injected process via this callback bypasses the entire userland unhook: the EDR sees `process X spawned by parent Y with command line Z and image hash H` even if `X`'s `NtAllocateVirtualMemory` stub was pristine at the moment of allocation.

### Variant 2: PsSetLoadImageNotifyRoutine (Image Load)

1. The EDR driver calls `PsSetLoadImageNotifyRoutine(LoadImageRoutine)` from `DriverEntry`.
2. The routine is appended to `PspLoadImageNotifyList`, a separate `LIST_ENTRY` head.
3. On any `MmLoadSystemImage`, `NtMapViewOfSection` with `SEC_IMAGE`, or `LdrLoadDll`-driven user image load, `PspCallLoadImageNotifyRoutines` iterates the list and invokes each callback with `(_In_opt_ PUNICODE_STRING FullImageName, _In_ HANDLE ProcessId, _In_opt_ PIMAGE_INFO ImageInfo)`.
4. The `IMAGE_INFO` structure exposes `ImageBase`, `ImageSelector` (legacy), `ImageSize`, `MappedData PVOID` (kernel-mapped view of the section for hashing), `ImageFlags` (`IMAGE_FLAGS_SYSTEM_IMAGE`, `IMAGE_FLAGS_KERNEL_LDR`, `IMAGE_FLAGS_MAPPED_AS_LITTLE_ENDIAN`, `IMAGE_FLAGS_LITTLE_ENDIAN`), and on Vista+ the extended `ExtendedInfo` union granting access to `ImageCharacteristics`, `MachineType`, `DefaultBase`, and `ImageSectionNumber`.
5. This is the signal EDRs use to catch reflective DLL injection (which never produces an `IMAGE_INFO` event because no section is mapped) **and** classical `LoadLibrary`-based injection (which always produces one). Both paths are detected from the kernel; userland unhooking of `LdrLoadDll` does not affect the kernel-side `PspCallLoadImageNotifyRoutines` dispatch.
6. The `MappedData` kernel pointer allows the EDR driver to compute a SHA-256 of the freshly loaded image bytes and compare against a known-bad signature list — the hash is computed from the section's prototype PTE-backed physical pages, not from the userland view, so a `ProcessInstrumentationCallback` or section-swap attack that alters the userland bytes **cannot** defeat the hash computed in kernel mode.

### Variant 3: PsSetCreateThreadNotifyRoutine (Thread Create / Exit)

1. Registered via `PsSetCreateThreadNotifyRoutine(ThreadNotifyRoutine)`; appended to `PspCreateThreadNotifyList`.
2. `PspCreateThread` walks the list on every thread creation in any process and invokes `(_In_ HANDLE ProcessId, _In_ HANDLE ThreadId, _In_ BOOLEAN Create)`.
3. On `Create == TRUE`, the driver receives the new thread's owner PID and TID before the thread has executed its first instruction — the `ETHREAD.StartAddress` field is accessible via the `EPROCESS` obtained from `ProcessId`, allowing the driver to inspect the start routine against a blocklist of `LoadLibraryA`, `CreateThread` injection start addresses, or unsigned module entry points.
4. This is the primary signal for `CreateRemoteThread`-style injection and `RtlCreateUserThread`-in-remote-process injection. The thread's `StartAddress` is the giveaway: a thread starting at `LoadLibraryA` or at an address inside a freshly mapped `SEC_IMAGE` section that is **not** in the module list (`PEB.Ldr.InLoadOrderModuleList`) is the canonical "hollowed module" signature.
5. Unhooking `ntdll!NtCreateThreadEx` does not block this callback — `NtCreateThreadEx` still routes through `KeInitThread → PspCreateThread`, which still dispatches the notification.

### Variant 4: ObRegisterCallbacks (Process / Thread Handle Duplication)

1. The driver allocates an `OB_CALLBACK_REGISTRATION` populated with `Version = OB_FLT_REGISTRATION_VERSION`, `OperationRegistrationCount`, and one or more `OB_OPERATION_REGISTRATION` entries of ` ObjectType = *PsProcessType` (or `*PsThreadType`) and `Operations = OB_OPERATION_HANDLE_CREATE | OB_OPERATION_HANDLE_DUPLICATE`.
2. `ObRegisterCallbacks(&Registration, &RegistrationHandle)` inserts the callback into the per-object-type `OBJECT_TYPE.TypeInfo` callback chain — specifically the `PreOperation` and `PostOperation` slots, which fire inside `ObpCallPreOperationCallbacks` and `ObpCallPostOperationCallbacks`.
3. `PreOperation` receives a `POB_PRE_OPERATION_INFORMATION` exposing `Operation` (`OB_OPERATION_HANDLE_CREATE` or `OB_OPERATION_HANDLE_DUPLICATE`), `ObjectType`, `Object` (the `PEPROCESS` / `PETHREAD` being opened), `DesiredAccess` (`PROCESS_VM_READ | PROCESS_VM_WRITE | PROCESS_VM_OPERATION | PROCESS_CREATE_THREAD | PROCESS_TERMINATE | PROCESS_SUSPEND_RESUME | PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_SET_INFORMATION` etc.), `KernelHandle`, and a writable `DesiredAccess` field.
4. The callback can **mask off** access rights: a security product routinely strips `PROCESS_VM_WRITE | PROCESS_VM_OPERATION | PROCESS_CREATE_THREAD` from handles opened by unprivileged callers against protected processes, returning the now-reduced mask so the caller's subsequent `WriteProcessMemory` / `VirtualProtectEx` / `NtCreateThreadEx` calls fail with `STATUS_ACCESS_DENIED`.
5. This is the surface that defeats process-hollowing tooling which acquired a `PROCESS_VM_WRITE` handle **before** the unhook — the kernel ob-callback has the final word on the handle's rights, regardless of the API path the caller used to obtain it.
6. The `PreOperation` callback fires on every `OpenProcess`, `NtOpenProcess`, `NtOpenProcessEx`, `OpenObjectByHandle` duplication via `NtDuplicateObject`, and even on `NtQueryInformationProcess(ProcessHandleTracing)` paths that materialize handles internally.

### Variant 5: CmRegisterCallbackEx (Registry)

1. Registered via `CmRegisterCallbackEx(Callback, Altitude, DriverObject, Context, &Cookie, &Reserved)`; appended to `CmpCallbackListHead` keyed by an altitude string (e.g. `"329000"` for EDRs, lower altitude fires earlier).
2. The callback fires on every registry operation with the `REG_NOTIFY_CLASS` enum specifying the phase: `RegNtPreSetValueKey`, `RegNtPreDeleteKey`, `RegNtPreDeleteValueKey`, `RegNtPreCreateKeyEx`, `RegNtPreRenameKey`, `RegNtPreQueryValueKey`, `RegNtPreEnumerateKey`, `RegNtPreQueryKey`, and their Post counterparts.
3. Each callback receives a `_REG_NOTIFICATION_INFORMATION` union specific to the class — for `RegNtPreSetValueKey` it carries `KeyValueInformation` (`KEY_VALUE_INFORMATION_CLASS`), `ValueName` (`PUNICODE_STRING`), `ValueSetType`, `Data`, `DataSize`. The driver can rewrite `Data` to neutralize malicious values, or set `Status = STATUS_ACCESS_DENIED` to block the write outright.
4. This is the surface that catches IFEO Debugger persistence (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\<image>\Debugger`), SilentProcessExit persistence (`ReportingMode=1` + `MonitorProcess=`), LSASS notification package additions (`HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Notification Packages`), and RunKey insertion (`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run`). None of these are affected by a userland unhook.

### Variant 6: FltRegisterFilter (Mini-Filter)

1. The driver registers a mini-filter via `FltRegisterFilter(DriverObject, &Registration)`, where `Registration` is a `FLT_REGISTRATION` populated with `Size`, `Version = FLT_REGISTRATION_VERSION_1`, `NameBuffer` Unicode string, `DefaultQuery`, and an array of `FLT_OPERATION_REGISTRATION` entries terminating with `{0, 0, NULL, NULL}`.
2. Each `FLT_OPERATION_REGISTRATION` maps a ` MajorFunction` (`IRP_MJ_CREATE`, `IRP_MJ_READ`, `IRP_MJ_WRITE`, `IRP_MJ_SET_INFORMATION` for `FileRenameInformation` / `FileEndOfFileInformation` / `FileAllocationInformation`, `IRP_MJ_DEVICE_CONTROL`) to a `PreOperationCallback` and `PostOperationCallback`.
3. The FltMgr altitude system orders mini-filters along a virtual stack — EDRs typically sit in the `"3289xx"`-`"3290xx"` range (between filter manager's own housekeeping and the filesystem filter layer). Altitude allocation is managed by Microsoft; an unsigned driver cannot register at an arbitrary altitude.
4. `PreOperationCallback` receives a `FLT_CALLBACK_DATA` with `Iopb->Parameters` containing the `DeviceIoControl.IoControlCode`, the `MajorFunction`, the `TargetFileObject`, and the operation buffers. A write I/O pre-callback lets the driver inspect the bytes before they hit the disk — the canonical on-write scan path that catches malware droppers writing PE files to `%TEMP%`.
5. Userland unhooking does not affect mini-filters; the I/O manager's dispatch through `IoCallDriver → IopfCallDriver → fltmgr!FltpDispatch` runs entirely in kernel mode, on the IRQL-3 (PASSIVE) path of the calling thread's IRP.

### Variant 7: ETW Threat Intelligence (TiLog) — Survives Unhooking

1. Microsoft Defender's ELAM driver and the `MsSecCore` / `Microsoft-Windows-Threat-Intelligence` provider emit events from the kernel via `EtwTraceKernelEvent` on the `NT Kernel Logger` or a dedicated threat-intelligence ETW session.
2. The provider fires on `EtwThreatIntProv` events such as `KERNEL_THREAT_INT_PROV_PROVIDERS::KTI_IMAGE_LOAD`, `KTI_ALLOCVM_REMOTE`, `KTI_PROTECTVM_REMOTE`, `KTI_WRITEVM_REMOTE`, `KTI_QUEUE_USER_APC_REMOTE`, `KTI_SET_THREAD_CONTEXT_REMOTE` — these are emitted **directly** from `MmMapViewOfSection`, `NtAllocateVirtualMemory` (cross-process), `NtProtectVirtualMemory` (cross-process), `NtWriteVirtualMemory` (cross-process), `NtQueueApcThread`, and `NtSetContextThread` paths in `ntoskrnl.exe`.
3. To consume these events a process must hold `SYSTEM` privileges and the `Microsoft-Windows-Threat-Intelligence` session must be in `EVENT_ENABLE_PROPERTY_SI`-style enablement — only one consumer at a time.
4. Hooking or patching `ntdll` does not silence this; the events are emitted from kernel code that runs **before** the userland syscall stub returns to the caller. The only ways to suppress TiLog events are (a) prevent the EDR process from running, (b) corrupt the ETW logger's `TRACE_ENABLE_INFO` such that the enable mask reads zero, or (c) install a kernel driver that hooks `EtwTraceKernelEvent` itself.

## OS Internals Context

The kernel callback infrastructure is implemented as a set of singly-linked lists of routine pointers, each protected by a guarded mutex acquired at `PASSIVE_LEVEL` and traversed inline during the system call paths that own the relevant lifecycle event. The `PspCreateProcessNotifyList`, `PspLoadImageNotifyList`, and `PspCreateThreadNotifyList` heads live in the `.data` section of `ntoskrnl.exe`; on a patched Windows 11 22H2 build, `PspCreateProcessNotifyList` is referenced by `PspInsertProcess` via a relative offset from `nt!PspCreateProcessNotifyList+0x0` and the count by `nt!PspCreateProcessNotifyListCount`. Each entry is a `LIST_ENTRY` whose owning structure is the callback's context (typically just the function pointer itself for the older `PsSetCreateProcessNotifyRoutine` API, or a `PSP_NOTIFY_CALLBACK` record for the Ex variant). The list mutation is serialized by `PspSystemThread` calling `KeAcquireGuardedMutex(&PspNotifyEnableMask)`, and the dispatch is wrapped in a `try/except` (`__try` / `__except`) so that a faulting callback raises a bug-check `0x1000007E` (`SYSTEM_THREAD_EXCEPTION_NOT_HANDLED_M`) rather than corrupting process state.

The `PsSetCreateProcessNotifyRoutineEx` variant, available from Vista onward, distinguishes itself from the legacy `PsSetCreateProcessNotifyRoutine` by passing `PS_CREATE_NOTIFY_INFO` instead of a bare boolean. The Ex1 sub-variant adds the `FileObject` to the structure, allowing the driver to call `IoQueryFileDosDeviceName` on it and to map the file via `MmGetSystemRoutineAddress("FsRtlMdlReadEx")` to hash the bytes before they're even mapped into the new process's address space. The Ex2 sub-variant adds native pack/unpack of `PS_ATTRIBUTE_LIST` style attributes — this is the form Defender for Endpoint uses to gain access to the `CommandLine` recorded via the `ProcessParameters` of the new `PEB`. The callback fires **after** the new process's PEB is set up but **before** any user-mode thread in the new process executes; this is the only window where the driver can rewrite `CreationStatus` to deny the creation cleanly. A driver that attempts to deny after the first user-mode instruction has run must instead terminate the process via `NtTerminateProcess` from the callback context, which the kernel allows via a queued APC on the new process's initial thread.

The `ObRegisterCallbacks` infrastructure is more intricate. Each `OBJECT_TYPE` (`PsProcessType`, `PsThreadType`, `ExWindowObjectType`, `IoFileObjectType`, etc.) carries a `TypeInfo` of type `OBJECT_TYPE_INITIALIZER` containing the pre/post Open, Close, Parse, DumpProcedure, and (since Vista) `OpenProcedure` / `CloseProcedure` callbacks **and** a chain of registered `CALLBACK_ENTRY` nodes for runtime-registered ob-callbacks. The runtime chain lives on `OBJECT_TYPE.CallbackList` (a `LIST_ENTRY` per object type, protected by the per-type `OBJECT_TYPE.Mutex`). On every handle creation or duplication, `ObpCallPreOperationCallbacks` iterates the chain and invokes each `OB_PRE_OPERATION_CALLBACK` synchronously; the `Version` field of `OB_CALLBACK_REGISTRATION` controls whether the callback receives `OB_PRE_OPERATION_PARAMETERS_V1` or `OB_POST_OPERATION_PARAMETERS_V1`. The `DesiredAccess` field in the pre-operation info is **writable** — the canonical EDR pattern is to compute a "mask" of restricted accesses (`PROCESS_VM_WRITE | PROCESS_VM_OPERATION | PROCESS_CREATE_THREAD | PROCESS_TERMINATE` for `PsProcessType`) and AND it out of `DesiredAccess` when the source process is below SYSTEM integrity and the target is at or above protected level. The resulting handle is committed with the masked access mask by `ObpCreateHandle`, and the caller's subsequent `NtWriteVirtualMemory`, `NtProtectVirtualMemory`, `NtCreateThreadEx` calls fail with `STATUS_ACCESS_DENIED` deep in the syscall — past the userland ntdll stub, past any hook that the unhooking would have removed.

The mini-filter infrastructure is owned by `fltmgr.sys`. On registration, `FltRegisterFilter` allocates a `FLT_FILTER` structure (an extension of `DRIVER_OBJECT`), inserts the filter into a global filter list ordered by altitude (`FlpAttachedToVolume` per-volume ordering), and registers a `IRP_MJ_*` dispatch table in the FilterManager's `FLT_REGISTRATION` field. Mini-filter altitudes are decimal strings (e.g. `"328990"`) where Microsoft assigns bands — `320000-329999` for anti-malware, `450000-459999` for copy-on-write shadow copy filters, etc. The pre-operation callback runs in the **calling thread's context**, in the **calling process's address space**, at `PASSIVE_LEVEL` or `APC_LEVEL` depending on the major function — meaning the mini-filter can read user-mode buffers via `try/except` and reference the calling `PEPROCESS` via `PsGetCurrentProcess`. The I/O manager path is `IoCallDriver` → `IopfCallDriver` → `fltmgr!FltpDispatch` → `FltProcessFileOperation` → per-callback pre-operation invocation. **Nothing in this chain touches userland ntdll**; an unhook is irrelevant to it.

The registry callback chain lives on `CmpCallbackListHead`, a `LIST_ENTRY` in `ntoskrnl.exe`'s `.data` section protected by `CmpCallbackListLock` (`KGUARDED_MUTEX`). Each entry is an `EX_CALLBACK_ROUTINE_BLOCK` containing the `Function` pointer and a `Context` field. The list is traversed on every CM registry API path: `CmSetValueKey`, `CmDeleteValueKey`, `CmDeleteKey`, `CmCreateKey`, `CmRenameKey`, `CmEnumerateKey`, `CmQueryKey`, `CmQueryValueKey`. Each routine receives the `REG_NOTIFY_CLASS` enum indicating the pre/post phase, and a `REG_NOTIFY_INFORMATION` union whose layout depends on the class. The `Status` field in the pre-notification structure is writable — setting it to `STATUS_ACCESS_DENIED` blocks the operation; setting it to `STATUS_CALLBACK_BYPASS_FAST_PATH` (an undocumented status used by some kernel-mode scanners) hands the operation back without running further callbacks. The `Altitude` string assigns ordering; Microsoft requires EDR vendors to register for an altitude, but several public rootkits have reused string-based altitudes of known vendors to interpose themselves ("altitude squatting") — a phenomenon detectable by enumerating the loaded filter list via `CmGetCallbackVersion` and `EnumWindows`-style iteration, but rarely exploited by defenders.

ETW Threat Intelligence is a newer surface (introduced Windows 8, matured in RS3+) that subsumes several of the older hooks. The kernel-side emitter `EtwTraceKernelEvent` checks the `EnableMask` field of the `TRACE_ENABLE_INFO` of the `Microsoft-Windows-Threat-Intelligence` provider GUID (`{F4E1897C-BB5D-5666-F283-C9C611BBBEE}` — illustrative; consult `evntprov` headers for actual) before tracing. If `EnableMask & 0x1` is set, the corresponding `KTI_*` opcode fires. The provider emits events from inside the syscall path itself: `nt!NtAllocateVirtualMemory` checks `CrossProcess` flag and emits `KTI_ALLOCVM_REMOTE` before returning the result to the caller; `nt!NtWriteVirtualMemory` emits `KTI_WRITEVM_REMOTE` before returning. The events contain the source PID, target PID, base address, size, and the protection / first bytes written. The only way to suppress these is to either prevent the `Microsoft-Windows-Threat-Intelligence` logger from being enabled (requires patching the `EtwEnableInformation` table in kernel, requires a kernel driver), or to ensure the consumer process is not running (process termination from an unsigned caller fails on protected processes via `PsProtectedSigner`-level enforcement).

## Key Implementation Details

The first implementation fact an operator must internalize: an unhook is a **userland-only** operation. `VirtualProtectEx` on the `ntdll` section, or mapping a fresh `ntdll` via `NtCreateSection(SEC_IMAGE)` followed by `NtMapViewOfSection`, modifies the user-mode view of the section's PTEs in the caller's process context. The kernel-mode `ntoskrnl.exe` callback lists are untouched. The result is that the operator's syscall **succeeds** in userland — no hook is in the way to redirect execution or return `STATUS_ACCESS_DENIED` early — but the syscall still routes through `KiSystemCall64 → KiSystemServiceRepeat → nt!NtXxx` in kernel, and the kernel code path still calls `PspCallProcessNotifyRoutines`, `PspCallLoadImageNotifyRoutines`, `PspCallCreateThreadNotifyRoutines`, and `ObpCallPreOperationCallbacks` as appropriate. Unhooking does not "blind" these paths; it only removes the userland guardrails.

The second: every modern EDR has a kernel driver, and every modern EDR driver registers multiple callback classes. CrowdStrike Falcon's `csagent.sys` registers process, thread, image-load, and registry callbacks; Defender's `WdNisDrv.sys` (with ELAM early-launch anti-malware) registers the same plus mini-filter; SentinelOne's `SentinelMonitor.sys` is similar. Operators targeting any of these must assume the **full** callback surface is live; "I only hooked one ntdll function so the rest of the telemetry is dead" is a common but mistaken reasoning. The correct threat model is: assume all six classes above are active; enumerate them via loaded-driver list and `PsSetCreateProcessNotifyRoutine`'s versioned export to verify.

The third: WOW64 boundary matters for the userland unhook side, not for the kernel callback side. A 32-bit process on a 64-bit Windows has a 64-bit `ntdll.dll` (the WOW64 host) plus a 32-bit `ntdll.dll` (the WOW64 syswow layer); unhooking only the 32-bit view leaves the 64-bit hooks in place, and unhooking only the 64-bit view leaves the 32-bit syswow trampolines in place — but neither affects the kernel callbacks, which fire on the underlying 64-bit `ntoskrnl` syscalls. The kernel callbacks fire **regardless of bitness** of the caller; they see the caller's `PEPROCESS` and the operation arguments.

The fourth: `PsSetCreateProcessNotifyRoutineEx` requires the registering driver to be signed with a `Windows Hardware Certification` EV certificate and to link against `/INTEGRITYCHECK`. Unsigned or test-signed drivers cannot register Ex callbacks — `PsSetCreateProcessNotifyRoutineEx` returns `STATUS_ACCESS_DENIED` if the caller's image is not `IMAGE_DLLCHARACTERISTICS_FORCE_INTEGRITY`. This is what makes the kernel callback surface a hard wall: an operator without a kernel driver (signed or loaded via BYOVD like `RTCore64.sys`, `gdrv.sys`, `iqvw64e.sys`, `procexp152.sys`) cannot register new callbacks and cannot unregister existing ones. The bypass surface is limited to (a) BYOVD to gain arbitrary kernel write and either zero out the callback list or zero out specific `CALLBACK_ENTRY.Function` pointers, (b) patching `EtwTraceKernelEvent`'s enable mask, (c) blocking the consumer process from running, (d) using primitives that don't trigger the registered callbacks — `ProcessInstrumentationCallback` for in-process instrumentation, APC injection to a co-resident thread rather than `NtCreateThreadEx` to dodge the thread-notify, manual section mapping with `PAGE_NOACCESS` prot-and-deref to dodge `LoadImage` notification, etc.

## Why It Matters

This card exists as the operational complement to T-016. The vault's T-016 card (Clean NTDLL Unhook) correctly describes the mechanics of restoring the userland `ntdll.dll` to its on-disk image — a technique that is **necessary** against any EDR that uses inline userland hooks but **not sufficient** against any EDR that has a kernel driver. The vault must make this constraint explicit because the failure mode of "I ran T-016, I'm not seeing the userland hook anymore, therefore I'm evading the EDR" is one of the most common mistakes operators make against modern products; the kernel-side callbacks still fire, the rule engine still correlates them, the alert still lands — just with a cleaner-looking userland call stack that itself becomes a heuristic ("the process's ntdll matches on-disk exactly but the process is doing injection-like operations" is itself a Defender for Endpoint heuristic).

The card matters because it enumerates the **next** surface that must be addressed. For full telemetry suppression against a kernel-resident EDR, the operator's toolchain needs: (a) a BYOVD-loaded or signed-driver kernel component that can zero specific `CALLBACK_ENTRY.Function` pointers or unregister specific `EX_CALLBACK_ROUTINE_BLOCK` entries, (b) ETW-TI suppression via `EtwEnableInformation` mask zeroing or consumer-process termination, (c) operation selection that avoids the kernel-observable APIs in favor of section-mapping / APC / instrumentation-callback primitives. The card composes forward with T-047 (cross-session delivery), with the instrumentation-callback pattern, and with the section-mapping manual-map pattern as alternatives to the kernel-observable `NtCreateThreadEx` / `NtWriteVirtualMemory` paths. It is the prerequisite reading before any "I evaded the EDR" claim can be made responsibly.

## Detection Considerations

- **Telemetry sources**: The kernel-side telemetry itself — `PspCallProcessNotifyRoutines`, `PspCallLoadImageNotifyRoutines`, `PspCallCreateThreadNotifyRoutines`, `ObpCallPreOperationCallbacks`, `CmpCallCallbacks`, `FltpProcessFileOperation` pre/post, and `EtwTraceKernelEvent` for the Threat-Intelligence provider. None of these are affected by the userland unhook. From the operator's perspective, "detection" means **observing that the EDR still has the kernel callbacks active**: enumerate `ntoskrnl!PspCreateProcessNotifyList` head via kernel reads, enumerate `CmpCallbackListHead`, enumerate the per-object-type `OBJECT_TYPE.CallbackList`, enumerate `FltGetFilterInfo` for loaded mini-filters. The presence of a non-zero count in any of these is the signal that the userland unhook alone is insufficient.
- **Bypass options**: (1) BYOVD — exploit a known vulnerable signed driver (e.g. `RTCore64.sys` CVE-2019-16098, `gdrv.sys` Gigabyte driver, `iqvw64e.sys` Intel LAN driver, `procexp152.sys` CVE-2018-19788, `dbutil_2_3.sys` Dell) to gain arbitrary kernel write, then zero out `CALLBACK_ENTRY.Function` pointers in `PspCreateProcessNotifyList` and `PspLoadImageNotifyList`. (2) Patch the EDR driver's in-memory registration table so its callback pointer is nulled — requires the BYOVD primitive. (3) For ETW-TI, find the `TRACE_ENABLE_INFO` for the Threat-Intelligence provider GUID and zero its `EnableMask` — requires kernel write. (4) Avoid the kernel-observable path entirely: use `ProcessInstrumentationCallback` to execute in-process without cross-process handle opens, use manual section mapping with `PAGE_NOACCESS` round-trip to skip `LoadImage` notification, use APC injection to a co-resident thread to skip `CreateThread` notification, use `NtCreateProcessEx` style fork-bomb instead of `CreateRemoteThread`. (5) Kill the consumer process — for EDRs where telemetry is consumed by a single process (`MsMpEng.exe` for Defender, `CSFalconService.exe` for CrowdStrike), terminating that process (requires `SeDebugPrivilege` AND a bypass of the process's `PS_PROTECTED_SIGNER` level, which is itself a kernel-protected surface) renders the telemetry useless even if the callbacks still fire.
- **Residual artifacts**: After any of the bypass approaches, residual artifacts include (a) the loaded BYOVD driver image in the `PsLoadedModuleList`, which is itself enumerable via `EnumDeviceDrivers` from user mode; (b) the `CALLBACK_ENTRY.Function` field zeroed but the `LIST_ENTRY` still in place, detectable by enumerating the notify list and checking that `Count > 0` but `Function == NULL` (an EDR that periodically re-validates its registrations can detect this); (c) for ETW-TI mask zeroing, the `EnableMask` of the Threat-Intelligence provider reads zero while the logger session is still active — detectable via `EtwQueryTraceInformation` from a privileged consumer; (d) any terminated EDR consumer process leaves event-log entries (`Security` channel 4625 for logon failure if the operator killed it, `System` channel service-crash events for `MsMpEng.exe` / `CSFalconService.exe`); (e) for the section-mapping-with-PAGE_NOACCESS approach, the VAD tree of the target process shows a `MMVAD` node with `Protection = MM_NOACCESS` covering the section's `StartingVpn`-`EndingVpn` range — detectable via `NtQueryVirtualMemory(MemoryWorkingSetExInformation)` from a privileged diagnostic process.

## Composition with Other Techniques

A realistic kill chain to fully suppress telemetry against a kernel-resident EDR, given the constraint documented in this card:

1. **T-016 Clean NTDLL Unhook** — restore userland `ntdll.dll` to on-disk bytes. Defeats userland hooks in `NtCreateThreadEx`, `NtAllocateVirtualMemory`, `NtWriteVirtualMemory`, `LdrLoadDll`. Necessary because subsequent userland syscalls need to execute cleanly.
2. **T-NNN BYOVD Load** — exploit `RTCore64.sys` (CVE-2019-16098) or `dbutil_2_3.sys` to gain arbitrary kernel write primitive. Loaded as a service via `OpenSCManager` + `CreateService` + `StartService`; the BYOVD driver is signed, so it loads even with `Test-Signing` off and `CI` policy default.
3. **Kernel-mode callback zeroing** — using the BYOVD's arbitrary-write primitive, walk `ntoskrnl.exe`'s exported `PspCreateProcessNotifyList` (locate via pattern scan of the `PspCallProcessNotifyRoutines` function for the `lea rcx, [nt!PspCreateProcessNotifyList]` reference), `PspLoadImageNotifyList`, `PspCreateThreadNotifyList`, and `CmpCallbackListHead`; for each entry whose `Function` matches the EDR driver's address range (compare against the EDR driver's image base obtained from `PsLoadedModuleList`), zero the `Function` field (or `CALLBACK_ENTRY_BLOCK.Function` for Ex variants). This effectively un-registers the EDR's callbacks without triggering the unregister path (which would itself be a signal if the EDR's driver self-monitors its list).
4. **ETW-TI mask zeroing** — locate the `EtwEnableInformation` (or `EtwpEnableInformation` on older builds) array in `ntoskrnl.exe`, find the entry whose `ProviderId` matches the Threat-Intelligence provider GUID, and zero its `EnableMask`. This silences the kernel-side threat-intelligence events.
5. **Operation selection** — even after steps 3 and 4, prefer primitives that don't trip the residual surface: use `ProcessInstrumentationCallback` for in-process instrumentation, manual section mapping without `SEC_IMAGE` for module loading, APC injection to a co-resident thread for cross-process operations. This composes with this card's "Variant 1-7" enumeration: each kernel callback that survives unhooking has a corresponding bypass primitive listed in the Variant Comparison Table.

The kill chain above is non-trivial — it requires a BYOVD, kernel-mode code, and careful primitive selection. The card's purpose is to make the requirement for these layers explicit so that operators do not believe T-016 alone is sufficient.

## Common Mistakes

1. **Treating T-016 as a complete evasion** — assuming that because the userland hooks are gone, the EDR cannot see the operation. The kernel callbacks still fire; the alert still lands. T-016 must be composed with kernel-side suppression or with operation selection that avoids kernel-observable APIs.
2. **Forgetting `PsSetLoadImageNotifyRoutine` on manual mapping** — operators who manually map a DLL by reading it from disk and `memcpy`-ing into a `VirtualAlloc`'d region sometimes believe they've dodged the LoadImage notification. They have. But if they accidentally use `SEC_IMAGE` flag on the section, or if they call `NtMapViewOfSection` with an image-aligned section, the `LoadImage` notification still fires. The correct manual-map uses `PAGE_READWRITE` section and manual PE-header parsing — never `SEC_IMAGE`.
3. **Ignoring `ProcessInstrumentationCallback` on cross-process handles** — operators acquire `PROCESS_VM_WRITE` handles cross-process for `WriteProcessMemory`. The `ObRegisterCallbacks` pre-operation strips this access right for unprivileged callers. The operator sees `STATUS_ACCESS_DENIED` from `WriteProcessMemory` and blames it on a hook; it's not a hook, it's a kernel ob-callback. The fix is to either elevate to SYSTEM integrity (so the ob-callback bypasses the masking for SYSTEM callers, depending on the EDR's rules) or to not use cross-process handles at all — use APC injection to a co-resident thread.
4. **Mis-attributing ETW-TI alerts to userland hooks** — operators see a Defender alert describing exact bytes written via `NtWriteVirtualMemory` cross-process and conclude the userland hook caught it. It did not; ETW-TI emitted the event from inside `nt!NtWriteVirtualMemory`. Unhooking will not silence this; only ETW-TI mask zeroing or operation selection will.
5. **Overlooking `ProcessInstrumentationCallback` as a separate signal** — Defender registers a `ProcessInstrumentationCallback` (the `NtSetInformationProcess(ProcessInstrumentationCallback, &PROCESS_INSTRUMENTATION_CALLBACK_INFORMATION{Version=0, Reserved=0, Callback=...})` mechanism introduced in Windows 8.1, exposed at the per-process level via `KPROCESS.InstrumentationCallback` field) that fires on every syscall entry from within the instrumented process. This is **separate** from the userland `ntdll` hook and from the kernel callback surface. Unhooking does not disable it; an operator targeting a process with an active `ProcessInstrumentationCallback` must either zero the `KPROCESS.InstrumentationCallback` field (kernel write) or run in a process where it was never set.
6. **Assuming `TASKKILL` of the EDR consumer process will work** — `MsMpEng.exe` runs as `NT AUTHORITY\SYSTEM` with `PS_PROTECTED_SIGNER_ANTIMALWARE_LIGHT` (signer level 6, lightly protected) — `OpenProcess(PROCESS_TERMINATE)` returns `STATUS_ACCESS_DENIED` from the ob-callback path **before** the syscall returns to the caller. The operator cannot kill it without kernel-mode code, even with `SeDebugPrivilege`. The same applies to `CSFalconService.exe` (Protected Signer Light) and most modern EDR consumer processes.

## Related Techniques

- **T-016 Clean NTDLL Unhook** — the prerequisite userland unhook; this card documents its operational limit and the kernel callback surface that survives it. Composition: T-016 must be paired with kernel-side callback suppression (BYOVD + list zeroing) or operation selection that avoids kernel-observable primitives.
- **T-NNN BYOVD Kernel Primitive** — (when present in the vault) the kernel-side enabler for zeroing `PspCreateProcessNotifyList` entries, `CmpCallbackListHead` entries, and `EtwEnableInformation` mask. Without a kernel primitive, the kernel callback surface documented here is essentially unbypassable.
- **T-NNN ProcessInstrumentationCallback** — (when present) the in-process instrumentation-callback primitive that lives at the per-process `KPROCESS.InstrumentationCallback` field; an alternative to userland `ntdll` hooks that survives a T-016 unhook and must be addressed separately.
- **T-NNN APC Injection to Co-resident Thread** — (when present) the operation-selection alternative to `NtCreateThreadEx` that avoids the `PsSetCreateThreadNotifyRoutine` callback by leveraging an existing thread in the target process rather than creating a new one.
- **T-NNN Manual Section Map without SEC_IMAGE** — (when present) the operation-selection alternative to `LdrLoadDll` that avoids the `PsSetLoadImageNotifyRoutine` callback by mapping the image as `PAGE_READWRITE` and manually parsing PE headers.
